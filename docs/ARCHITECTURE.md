# skysa-notes — Architecture and decisions

Local-first markdown note-taking PWA that syncs to a dedicated, app-owned folder on the user's cloud storage (Google Drive, OneDrive, Dropbox). WebDAV was planned too and is deferred indefinitely (§5.4). Notes are plain `.md` files in a normal directory tree, so the user can open, edit, and back them up with any other tool.

This repo is the complete, self-hostable product: one Cloudflare Worker serving the SPA and a small API, plus the operator's own provider app registrations. This document is the design record: the source of truth for the architecture and for every decision behind it. Update it when a decision changes. It is not a to-do list — open work lives in GitHub issues — and §10 is the record of how the product was built, kept because the sections before it and comments in the code cite decisions by phase and by heading.

---

## 1. Core decisions (settled)

| Decision | Choice | Why |
|---|---|---|
| Storage model | App creates and owns a dedicated root folder on each provider; never touches anything outside it | Keeps every provider on user-consent-only scopes; avoids Google restricted-scope (CASA) review |
| File format | One markdown file per note, folders = notebooks, optional YAML frontmatter | Human-readable, portable, diffable, editable by other tools |
| Identity | Notes identified locally by UUID; remote identity is provider file id (Drive/Graph/Dropbox) or path (WebDAV) | Ids survive renames on id-based providers; WebDAV has nothing else |
| Client | Vite + React + TypeScript SPA, `vite-plugin-pwa` (Workbox) for the service worker, TanStack Router, Dexie (IndexedDB) for local store | Local-first app gets nothing from SSR; vite-plugin-pwa is the best-maintained PWA tooling in the React ecosystem |
| Backend | Hono + TypeScript on Cloudflare Workers, D1 via Drizzle | Tiny, streams bodies natively (WebDAV proxy), Workers-native |
| Repo | pnpm workspace: `apps/web`, `apps/api`, `packages/core` (providers, sync, markdown — framework-agnostic) | Keeps the hard parts testable without any UI or server framework |
| Hosting | Cloudflare Workers for the API, Workers static assets for the SPA (same origin), D1 for the database | One deploy, same-origin cookies, SQLite dialect in dev and prod |
| App folder name | `skysa-notes`, defined once as `APP_FOLDER_NAME` in `packages/core/src/config.ts`; changeable before launch | Provider registrations must match — see §5 |
| Accounts | A device may hold several connected sources at once, each its own silo — its own notes, its own queue, its own credential — and shows one at a time (Phase 7) | Nothing aggregates them, on the server or off it |
| Sign-in | There is none, and there will not be one. Identity *is* the storage connection: a connection is reached by the credential the device that made it holds, and nothing on the server knows that two connections belong to one person | Decided 2026-09-18 (§6, "No sign-in separate from storage"). Auth and data are coupled on purpose; a separate account layer would put a subject on the server that every privacy claim here then has to be re-argued around |
| Distribution | One public repo that is the complete, self-hostable product. No operator-specific configuration or credentials in the tree | A clean clone must deploy end to end on a fresh Cloudflare account |
| License | AGPL-3.0 — version 3 only, SPDX `AGPL-3.0-only`, not "or any later version" — with a CLA for contributors; trademark on the name/logo held separately | Real open source; network copyleft keeps modified deployments open; CLA preserves relicensing options. See §13 |
| Provider enablement | `ENABLED_PROVIDERS` env selects which of `gdrive,onedrive,dropbox,webdav` an instance offers | Operators who disable WebDAV remove the only path where content transits the server and the only SSRF surface |
| Note content | The server never stores note content, only tokens and connection metadata. For OAuth providers content never transits the server at all; WebDAV content streams through the proxy and is never persisted | Core privacy promise |
| Token flow | Backend does Authorization Code + PKCE with every OAuth provider, stores refresh tokens encrypted, mints short-lived provider access tokens for the client; **client talks directly to provider APIs for file content** | Uniform auth across providers, no client secrets in bundle, no file bytes through our server (except WebDAV) |
| Offline | Full read/write offline against IndexedDB; sync queue drains when online | It's a PWA; sync is a background concern |
| Conflicts | Never lose data. On conflict, keep the remote version at the original path and write local as `<name> (conflict <YYYY-MM-DDTHH-mm>).md` | Simple, predictable, recoverable |
| Editor | Rich-text (WYSIWYG) by default, raw markdown mode as a toggle; **the markdown string is the only source of truth** — the rich editor is a view over it | Notes are files; the editor must never own state the file can't represent |

Rows above that mention WebDAV describe the deferred design (§5.4); nothing in the repo implements it.

Non-goals for v1: real-time collaboration, sharing, full-drive access, mobile-native wrappers, attachments/images, syntax beyond CommonMark + GFM (tables, task lists, strikethrough).

## 2. Architecture overview

```
┌──────────────────────────── Browser (PWA) ────────────────────────────┐
│  UI (React)                                                            │
│   └─ Notes store (Dexie/IndexedDB) ── Sync engine ── Provider adapter  │
│                                              │                         │
│  Service worker (Workbox via vite-plugin-pwa): app-shell cache, bg sync │
└──────────┬───────────────────────────────────┼─────────────────────────┘
           │ sk1_ credential (bearer)          │ provider access token (bearer)
           ▼                                   ▼
┌── Backend (Hono on CF Workers) ──────┐   ┌── Provider APIs ──────────────┐
│  /api/auth/*      OAuth start/callback│   │  Google Drive v3 (CORS ok)    │
│  /api/connection  one silo's state   │   │  Microsoft Graph (CORS ok)    │
│  /api/token       mint access token  │   │  Dropbox v2 (CORS ok)         │
│  /api/webdav/*    proxy (CORS shim)  │──▶│  WebDAV server (via proxy)    │
│  D1: storage_connections, grants     │   └───────────────────────────────┘
└──────────────────────────────────────┘
```

Key property: the backend is only required for (a) connecting/refreshing an account and (b) WebDAV, which is deferred (§5.4). Once a client holds a valid access token it syncs peer-to-provider. If the backend is down, the app still works offline and can sync to OAuth providers until the access token expires.

## 3. Note format and directory layout

Remote root folder (app-owned), `skysa-notes/` (`APP_FOLDER_NAME`):

```
skysa-notes/
├── .notesapp.json            # marker file, see below
├── Inbox/
│   └── quick-thought.md
├── Work/
│   ├── 2026-q3-planning.md
│   └── Meetings/
│       └── 2026-09-14-standup.md
└── Personal/
    └── reading-list.md
```

Marker file `.notesapp.json`, written by `ensureRoot()` on first connect and never modified by the sync engine afterward (a new device does not overwrite it):

```json
{
  "schemaVersion": 1,
  "app": "skysa-notes",
  "createdAt": "2026-09-14T13:02:11Z",
  "createdBy": {
    "appVersion": "0.1.0",
    "provider": "dropbox",
    "clientId": "018f3c4e-...",       // random UUID per browser install, stored in IndexedDB syncState
    "userAgent": "Mozilla/5.0 ..."
  }
}
```

`createdBy` exists only for debugging (which install created this folder, with what version). It contains no account identifiers. `schemaVersion` gates future layout migrations; if a client sees a higher version than it understands, it opens read-only with a banner.

Note file:

```markdown
---
id: 018f3c4e-...          # UUID, written by the app; used to re-link after moves on path-based providers
title: 2026 Q3 Planning
created: 2026-09-14T13:02:11Z
updated: 2026-09-14T15:40:03Z
tags: [planning, work]
---

# 2026 Q3 Planning

Body is plain CommonMark. ...
```

Rules:
- Frontmatter is optional on read (files created by other tools are valid notes). The app adds it on first write.
- Filename is a slug of the title; the app renames the file when the title changes, and only then — a name is never re-derived from a title that did not change, so a rule about names that is tightened later applies to the next rename and not to the files already there. A slug is at most 120 code points and at most 216 bytes of UTF-8, cut between grapheme clusters, and always well-formed UTF-16: a lone surrogate makes `encodeURIComponent` throw inside an adapter, which is a counted failure on an ordered queue. 216 is what lets a name the app chose take one conflict suffix whole inside the 255 bytes ext4 and APFS allow a name — where the provider's desktop client puts the folder — (28 for ` (conflict 2026-09-15T14-32)`, 3 for `.md`, 4 each for the two `-999` counters). It promises nothing past that: a copy of a copy, or a long name from another tool, is fitted where the conflict name is made, by cutting the end of the stem — never the suffix, the counter or the extension — and the name is checked against the folder as cut.
- `id` in frontmatter is the stable identity **when the app can use it**. An `id` the user wrote that the app cannot — YAML reads `id: 202409141302` as a number, and coercing it would collide `0123` with `123` — is declined and left exactly as written, a conflict copy included. That is held in one place, `writeFrontmatter`, which neither sets an `id` over it nor lets the YAML writer respell it (`0123` would come back as `123`) whatever else the patch changes: the note is then what a note with no `id` is, known to the device by an id the file never sees and matched by `remoteId` and path.
- A frontmatter block is closed by `---`, or by YAML's document-end marker `...` (pandoc writes it). `...` closes one only if the YAML above it parses without a single error, as a mapping, and names something metadata is named, because `...` is also an ellipsis and a clean parse is the evidence it was not one. Where both readings exist, `---` stands unless something other than blank lines lies between the `...` and it: YAML ended its document at `...`, so what follows was never metadata — it is a pandoc block and the top of the note run together as far as the note's first thematic break (a slide deck's `# Slide 1`, which YAML takes for a comment and raises no error over; a paragraph over a setext underline). The rule looks at the text and not at how well it parsed, so it answers the same before and after the app's own write, which may tidy blank lines away (it does for the rare block it has to stringify whole). A block the parser had to repair is kept, erring towards frontmatter — refusing one costs the note its `id`, and the next write then puts a second block above the first — unless a blank line in it is followed by a sentence: a line of more than one word with no `key:` in it (a key may hold spaces: Obsidian writes `date created:`) that is not a template tag. One word is a slip in real frontmatter (`url:http://…` with the space left out), not prose. Then the whole file is body, where the user can see it, rather than prose hidden from both editors and dropped from a conflict copy. That question is asked when a file is split and never of a block already stored. A block goes back into the file with the closer it had, with two exceptions that keep the rule above answering the same for the file the app writes as for the one it read: a body that opens with a `---` line would be read as the block's closer, or as prose run into it, so the block is written between `---` fences; and a block edited until it no longer names any metadata would stop being read as one at all, and gets them too. What goes back inside it is the text that was there, with only the keys whose value the app actually changed rewritten: being named in a patch is not a change (a save names every field the store holds), differing from what the file reads as is, and a time is compared as an instant — so `zip: 02134`, `0x1F`, a twenty-digit integer, a quoting style, a comment, a list's layout and `created: 2024-09-14` all keep the user's bytes, a patch that changes nothing returns its input, and `updated` is rewritten on a save because the app does change it. The changed pairs' lines are spliced into the original text rather than the document being stringified and repaired afterwards, since text never handed to the stringifier cannot be respelled by it. The splice is kept only if it means what the patched document means, not merely if it parses — under a scalar that keeps its trailing blank lines (`|+`), the blank line a deleted pair leaves behind parses as one more line of a key nobody touched — and otherwise the block is stringified whole, as every block once was. A key with no value (`tags:`, as a template leaves it) owns its own line and no more, though `yaml` hands it every comment down to the next key. A value carrying an anchor is not written over, since another line may read it through an alias, and the writer never throws: a block `yaml` cannot evaluate or write is handed back as it came. A seeded fuzz in the same test file holds all of this over blocks put together at random. A `created` the app could not read as a time (`created: last spring`) is declined as an `id` is: the store's fallback, the time of the import, is never written over it. An `id` given as an alias is read through it (`id: *other`), like any other the app declines. The fences are anchored on `\n`, `\r\n` and `\r` only; U+2028 and U+2029 are not line endings, and read as ones they split a block inside a quoted title. `tests/markdown/frontmatter.test.ts` carries the splitter this replaced and a table of inputs the two must agree on, with each intended difference named.
- Folder names are user-facing notebook names. Reserved prefix: anything starting with `.` is ignored by the UI.
- Line endings: `\n`, `\r\n` and `\r` are **read** as one thing, because CommonMark says they are — the parser folds before remark sees the text, and both editors fold what they hand back. **Written**, in three parts, because each answers a different question:
  - The *body* is never rewritten by the act of saving metadata. A note nobody edited comes back byte for byte, including a line ending sitting between two lines of a fenced code block.
  - The *frontmatter block* is written the way that file writes lines — the body's first line ending; failing that the block's own interior endings; failing both, `\n`. Not "whichever ending appears somewhere in the body": one `\r\n` in a code sample would otherwise flip every line of an otherwise-`\n` file. The third fallback is reachable and bounded: a block has interior endings only with two or more keys, so a one-key CRLF note whose body has no line ending either is rewritten `\n`. Carrying the ending the fences had would close it, and only `splitFrontmatter` ever sees that.
  - A body that has been through *either editor* is `\n` throughout, and the block follows it. That is where normalization happens, and it happens only after a real user edit — including the endings between the lines of a code fence, which CommonMark counts as line endings rather than as the block's content. The raw editor has always done this; the rich editor now does it too, rather than the two disagreeing.
  (Amended twice: this first read "normalized to `\n` on write", which made adding an id on import a whole-file rewrite of every Windows-authored note; the amendment then claimed no file the app writes mixes endings, which was not true of a body carrying one inside a code fence, and is now stated as a promise about the block rather than about the file.) UTF-8 only.

## 4. Provider adapter interface

Every provider implements this. The sync engine only talks to this interface.

```ts
export interface RemoteEntry {
  remoteId: string;        // provider file id; the path itself on WebDAV
  path: string;            // relative to app root, POSIX separators, normalized
  kind: 'file' | 'folder';
  version: string;         // etag / rev / cTag / headRevisionId — opaque, compare for equality only
  modifiedAt: string;      // ISO
  size?: number;           // UTF-8 bytes; absent for folders
}

/** What read/move/delete need, which is all the local store keeps. */
export type EntryRef = Pick<RemoteEntry, 'remoteId' | 'path'>;

/** A path, an id, or both: Dropbox's DeletedMetadata has no id, and an id feed may know no path. */
export type DeletedEntry =
  | { path: string; deleted: true; remoteId?: string }
  | { path?: undefined; deleted: true; remoteId: string };

export type ChangeEntry = (RemoteEntry & { deleted?: false }) | DeletedEntry;

export interface ChangeSet {
  entries: readonly ChangeEntry[];
  cursor: string;          // opaque; persist per connection
  more: boolean;
}

export interface WriteOptions {
  /** Omitted means "create": a file already there is a ConflictError. */
  expectedVersion?: string;
}

export interface StorageProvider {
  readonly kind: ProviderKind;
  /** Whether `list` reports everything a folder holds. False on Drive (§5.1). */
  readonly listsEverything: boolean;
  readonly ensureRoot: () => Promise<{ rootId: string }>;
  readonly list: (folderPath: string) => Promise<RemoteEntry[]>;
  readonly read: (entry: EntryRef) => Promise<{ content: string; version: string }>;
  readonly write: (path: string, content: string, opts: WriteOptions) => Promise<RemoteEntry>;
  readonly createFolder: (path: string) => Promise<RemoteEntry>;
  readonly move: (entry: EntryRef, newPath: string) => Promise<RemoteEntry>;
  readonly delete: (entry: EntryRef) => Promise<void>;
  readonly changes: (cursor?: string) => Promise<ChangeSet>;
}

export class ConflictError extends Error { constructor(readonly remote: RemoteEntry) { … } }
export class AuthError extends Error {}          // engine asks the backend for a fresh token
export class NotFoundError extends Error {}      // entry gone, or expectedVersion for an absent path
export class CursorResetError extends Error {}   // cursor unusable; discard it and full-scan
export class UnreadableError extends Error {}    // the file is there and is not UTF-8 text; carries the path asked with
```

Three shapes differ from the sketch this section used to carry. Members are property signatures rather than methods, which is both the house style (`EntitlementProvider`) and what `functional/prefer-property-signatures` requires. `kind` reuses `ProviderKind` from `config.ts` so `PROVIDER_KINDS` stays single-sourced with the marker schema. And `read`/`move`/`delete` take an `EntryRef`, not a whole `RemoteEntry`: a note record persists only `remoteId`, `remoteVersion` and `path`, so passing the full entry would have every caller inventing a `kind` and a `modifiedAt` — and let an adapter come to depend on the invented value.

`NotFoundError` and `CursorResetError` are additions. A cursor can go stale on every provider (Dropbox answers `reset`, Graph `410 resyncRequired`, WebDAV invalidates its sync-token) and without a type for it the engine cannot tell a dead cursor from a transient failure, so it retries forever. `NotFoundError` is what lets `ConflictError.remote` stay non-optional.

Each error carries a `code` alongside its class, and ships with an `isXError` guard. `instanceof` is the ergonomic check and is correct today, since `@skysa/core` resolves to one module per bundle; the code keeps the guards honest if core is ever published and a consumer ends up holding two copies of it either side of a sync boundary.

Semantics the signatures do not carry:

- `listsEverything` is what the engine asks before removing a folder because a listing showed it empty (§7). It is false on Google Drive alone: `drive.file` shows the app only the files it created, so a folder that lists empty may hold a file the user put there, and deleting it would take that file. Every other capability question is answered by behaviour rather than a flag; this one cannot be, because the wrong answer is silent and costs a file.
- `write` is create-or-update, never a blind overwrite. No `expectedVersion` means "I expect nothing here" — literally WebDAV's `If-None-Match: *` — so a file already at that path is a `ConflictError`. That is what makes §7's "remote deleted, local dirty → re-create on push" safe: if the file came back in the meantime the write conflicts instead of clobbering it. An `expectedVersion` for a path with no file is a `NotFoundError`.
- `createFolder` and `delete` are idempotent, so a queued op is always safe to replay.
- `move` may or may not change `version` — Dropbox's `rev` survives it, OneDrive's `eTag` does not — so the caller stores the returned entry rather than assuming either way. `remoteId` survives a move on every id-based provider; on WebDAV it *is* the path and so cannot, which is why renames there are re-linked through frontmatter `id`.
- A deletion is identified by its id when it has one and by its **path** when it has not. Dropbox's `DeletedMetadata` carries a name and a path and nothing else — no id, no rev, no timestamp — so `ChangeEntry` is a union rather than an entry with a flag. Anything richer would have adapters fabricating fields and the engine trusting them. And the path may be missing where the id is not: an id feed asked about a file its tree never placed — one this device pushed after its cursor, deleted by another device before this one pulled again — has no path to give, and dropping the deletion leaves the note on this device for ever.
- `list` is one level. `changes` covers the whole tree at every depth. Neither filters hidden paths: `.notesapp.json` has to reach the engine, and the UI filters with `isHidden`.
- `rootId` is opaque, non-empty and stable. A provider whose root has no id of its own — a Dropbox app folder, where the root simply *is* `/` — returns a synthetic constant.
- Content is UTF-8 text, and `read` says when it is not. The body is taken as bytes and decoded strictly (`providers/text.ts`); bytes that are not UTF-8 are an `UnreadableError` carrying the path, never text with U+FFFD where the bytes were. A lossy decode looks like a note, and the first push then writes the damage over the original. Text holding a U+0000 is refused the same way: UTF-16 without a BOM, and most binaries, are valid UTF-8 to a decoder with a NUL for every other byte, and markdown never carries one. A UTF-8 BOM is stripped, as `response.text()` always did, so hashes do not move; it is still lost on the first push, as it always was. A probe that only asks whether a file exists takes `UnreadableError` for yes (§7). Binary attachments are out of scope (§14).
- No `AbortSignal` in the adapter interface: operations are short and the engine discards results it no longer wants. **But the `fetch` an adapter is given is cancelled with its session (2026-09-23).** The web app's `timedFetch` (`apps/web/src/sync/providers.ts`) combines each request's own 60 s timeout with the scheduler session's signal, so ending a session — Cancel on an import, a disconnect, a switch of source — stops a download in flight instead of leaving it to run out its timeout. The contract is unchanged; an adapter sees an aborted `fetch` as the network error it is.
- A provider asking us to slow down is `RateLimitError`, with the `retryAfterMs` it gave: Dropbox and Graph answer 429, Graph also 509 for the bandwidth cap, and Drive a 403 whose reason names the quota (`rateLimitExceeded`, `userRateLimitExceeded`, `dailyLimitExceeded`, `sharingRateLimitExceeded`). **A 503 is not a rate limit, `Retry-After` or not.** Graph's throttling guidance names one status — "use the HTTP error code 429 to detect throttling" — and its error table calls 503 "temporarily unavailable for maintenance or is overloaded" whose delay is "the length of which can be specified in a `Retry-After` header". So the header does not tell an outage from throttling: both carry one. Since a rate limit is not counted against the op (§7), a 503 read as one would retry for ever — never blocked, never surfaced, with every op behind it waiting — so it stays the counted failure any other 5xx is. Drive's newer error bodies put the condition in `error.status`, and `RESOURCE_EXHAUSTED` there is read as a quota **only where Drive gave no `errors[]` reason at all**: the reason is the more specific answer and some are deliberately left out, `storageQuotaExceeded` above all, which is a full Drive that no wait fixes and which `google.rpc.Code` gives the same `RESOURCE_EXHAUSTED` as a per-user quota. (Drive's errors page documents no `status` field; whether it ever sends one is on the Phase 4 live-check list.) `Retry-After` is read as seconds or as an HTTP date: seconds is what Graph documents and a date is legal (RFC 9110 §10.2.3) and is what some fronts send, so both are read, and of a value `Headers.get` has joined from a header sent twice ("7, 30") the *longer* wait is taken — coming back early is refused again, coming back late costs only the wait. Dropbox's `retry_after` comes out of the JSON body instead; an unreadable value says nothing rather than zero, and the caller falls back to its own backoff. It is a type of its own for two reasons: it says nothing about the request, so the engine does not count it against the op's attempts (§7), and the provider's own answer for how long to wait beats any backoff we could guess. Other transport failures (5xx, a dropped connection) stay plain errors on the engine's per-op backoff.

Adapter contract tests: the scenario suite is `describeProviderContract(name, harnessFactory, { stableIds })` in `packages/core/tests/providers/contract.ts` — a helper rather than a test file, so Vitest's `tests/**/*.test.ts` glob does not collect it on its own. `tests/providers/contract.test.ts` is the registry every adapter is added to: the in-memory fake in CI, and live accounts via `PROVIDER_LIVE_TESTS=1` locally. `stableIds: false` exempts path-based providers from the move-preserves-id scenarios.

Scenarios: idempotent `ensureRoot` including write-the-marker-only-if-absent, path normalization at the adapter edge, byte fidelity on read-back, the four `write` cases above, one-level `list` including hidden entries, idempotent `createFolder`, move (file, into a folder, whole folder rebasing its descendants, onto an occupied path), idempotent recursive `delete`, and a `changes` feed that scans current state on a cold start rather than replaying history, reflects each step, survives being persisted, and is drained through its `more` loop. And a file that is not UTF-8 text: `read` is an `UnreadableError`, while `list`, `changes`, `move` and `delete` treat it as any other file and leave its bytes as they were. No adapter can write such a file, so the harness may offer a way in underneath (`plant`, `bytesAt`) — the fake's `writeBytes`, which the wire stubs serve as the download — and a live registration, which has none, skips these.

The in-memory fake in `src/providers/fake.ts` is deliberately the strictest provider in the repo: where this section leaves a case open it takes the least forgiving reading, because a lenient fake lets the engine grow assumptions that only fail against a real account. It never creates a missing parent, re-versions even a byte-identical write, and never reuses an id. Its `pageSize`, `folderChanges` and `setFault` options are what let the engine's drain loop, folder rebasing, and auth-retry paths be tested at all.

## 5. Provider specifics

### 5.1 Google Drive
- Scope: `https://www.googleapis.com/auth/drive.file` plus `openid email` for identity. Non-restricted; standard OAuth verification only.
- Root: a folder `APP_FOLDER_NAME` (mimeType `application/vnd.google-apps.folder`) at the top of My Drive, tagged `appProperties: { notesapp: "root" }` and found by that tag, never by name, so a user who renames or moves it keeps their notes, whatever it is called. **Only `ensureRoot` and a round from nothing make one**: a pull on a stored cursor, and every read and write, only look (a search that misses the folder for a moment is an error to retry, never a second folder). Where one is made, the search is asked again, and every tagged folder but the earliest is folded into it — what is inside moved across (the marker trashed instead where the earliest has one), and a folder put in the trash only when a fold finds it already empty, since a device whose last pull was against it may still be writing into it; that device's next pull resets and folds again. That settles two devices connecting at once, and a folder restored from the trash beside the one made while it was gone, with nothing written to either left unread; names that meet in the move are separated by the scan that follows. A pull on a stored cursor is reset (`CursorResetError`) when an earlier tagged folder exists, when the folder is trashed or gone (asked of the folder itself when the search does not list it), or when the feed says so — read from `removed` and `trashed` as Drive sent them, not from the tree, which takes a name no path can hold as gone.
- Names are not unique on Drive: a folder may hold two `a.md`. A path is resolved by walking names from the app folder (`name = '…' and '<parent>' in parents and trashed = false`, with `'` and `\` escaped, compared exactly afterwards), and where a name matches more than once the **canonical** item — earliest `createdTime`, then lowest id — is what the path means, on every device. No id cache: one would send a write into the wrong folder after a remote rename, and notes sit a few levels deep.
- Nothing on Drive is conditional: v3 has no `If-Match` and nothing like create-if-absent.
  - Create: look up the name (taken → `ConflictError`, parent missing → `NotFoundError`), upload with `POST /upload/drive/v3/files?uploadType=multipart` (`text/markdown`, bytes exactly as given), then **search again**: if another device's file of that name was made earlier, ours goes to the trash (a third device may already have written into it) and `ConflictError` names theirs, so the engine makes its conflict copy. A folder is made the same way, and one that exists already is returned.
  - Update: by id, never by path — a file deleted since the caller saw it is `NotFoundError`, never made again. `headRevisionId` is compared with the expected version (`ConflictError` if it moved), then `PATCH /upload/drive/v3/files/{id}?uploadType=media`. A write landing between the two is overwritten; the next `changes` pass reports the result. Nothing written on this device is lost, and what the other device wrote in that moment may be — inherent to v3.
  - Move: `PATCH files/{id}` with `{ name }`, and `addParents`/`removeParents` only when the folder changes. The destination is looked up first, so a replayed move returns without a `PATCH`.
  - Delete: `PATCH { trashed: true }` — to the trash, not gone for good, so the user can restore a note from Drive as from OneDrive's recycle bin. A 404 is success.
- Reading: `GET files/{id}` for `headRevisionId`, **then** `?alt=media`, both on `www.googleapis.com` with the token. In that order the version reported is never newer than the bytes; Drive can download a past revision only if it was kept forever, so the two cannot be pinned together.
- Version: `headRevisionId`, which changes with content and not with a rename or a move (like Dropbox's `rev`). Folders have none. A file with none (a Google Docs file, which this app never makes) is left out of `list` and `changes`.
- Changes: the cursor is JSON `{ v, phase, token, start, root, nodes, pending }`, the tree kept in `packages/core/src/providers/idTree.ts` as for OneDrive (§5.2). A round from nothing asks `changes.getStartPageToken` **first**, then scans `files.list q=trashed = false` — every file the app can see, which under `drive.file` is every file it made — and follows `changes.list` (`includeRemoved`, `newStartPageToken` ends a round) from that token after. A `removed` change (deletion or loss of access) or a file with `trashed` (set too when a folder above it is trashed) is gone. On a stored cursor, a 404, a 410, or a 400 whose error names the page token (in `location`, reason or message) is `CursorResetError`; any other 400 is a failure to retry, not a rescan. What Drive actually answers for a dead token is undocumented.
- Drive lists no parents of a changed item, so a round's end means only that every ancestor of what it listed is in the tree or was listed: a folder that becomes placed without having been (moved in from outside the app folder, or rescued from one deleted) has its contents **listed recursively into the same page** (`arrivals`), since the feed will not name them. An item a round ends without placing has left the app folder — moved elsewhere in Drive, or into a folder the user made in the Drive UI, which `drive.file` cannot see — and is reported deleted where it was.
- **Two items at one path never reach the engine**, which holds one note per path: with two, it would move one note aside locally on every pull, alternately, and an edit to the one moved aside would be written to a path with no file behind it for ever. When a page places two items with one folder and name, the adapter asks Drive whether both are still there — the search, and then each one the search leaves out, by id, since the feed can announce a file before the index lists it and a clash passed over is not asked about again until one of them changes; if so the canonical one keeps the name and each other is renamed beside it with `PATCH { name }` to `conflictFilename`/`conflictFolderName` (§7's rule applied to two remote files), and reported there. A tree that still holds a file under a name it has since left is not a duplicate, so the tree alone never triggers a rename. Two devices separating the same pair at once each rename the same file; the last `PATCH` wins, and the next pull reports the name that stuck. So a pull can write to Drive, which no other adapter's does.
- Known gaps. The engine commits page by page, where the feed means a round — the gap §5.2 describes, and Phase 6's item answers for both. A folder emptied here is not removed from Drive: no listing can show that it is empty, so the directory a renamed or deleted notebook leaves behind stays, and the notebook can come back empty after a re-scan (§7, "A folder is removed only where a listing can prove it empty"). A search that misses the existing app folder at a reset still makes a second one — unless it is the folder this page last made, found or confirmed, which is asked for by id and counted unless it is in the trash or out of reach (so a first connect, where `ensureRoot` and the first pull's reset come seconds apart, makes one) — and the scan under it deletes this device's clean notes until a later round finds the earlier folder, resets back to it, and folds the second into it (the files are untouched remotely). A pull on a stored cursor costs one tag search before its page. Files the user adds through the Drive UI are invisible under `drive.file`.
- Measured against a live account, 2026-09-21, since none of it is on Drive's reference pages. **The change feed lags**: a new file took 1.4–2.8s to appear in `changes.list` on an idle account, and longer under the load of a suite run. **It also repeats itself**: one file creation was reported *twice*, about two seconds apart, with the same `version` and nothing having happened in between — so a cursor taken after the first echo still has the second coming, and anything reading the feed has to be idempotent on a repeat it has already applied (the engine is: it compares versions). **Name lookup does not lag**: a file was findable by name in 0.3–0.4s, which is what `verify-after-create`, every path walk and finding the app folder at a reset all depend on, and was the worry that made this worth measuring. **Deletion lags the other way**: the search index keeps listing a deleted file for a moment, so a scan run straight after a mass deletion finds files whose parent is already gone, cannot place them, and reports them as deletions by id — reachable by a test harness emptying a shared folder between scenarios, not by a user.
- A page token Drive will not take answers **400**, with `message: "Invalid Value"` and `reason: "invalid"` — neither of which says anything about a token. Only `location: "pageToken"` does, so the `locations` check in `isDeadToken` is the one doing the work and the message regex beside it is a fallback that would not fire here. Confirmed 2026-09-21; `CursorResetError` follows, as §7 needs.
- Trashing and renaming a folder are reported differently, also measured 2026-09-21. **Trashing lists what is inside it**: the folder and every descendant arrive, each with `trashed: true`. **Renaming lists the folder alone**, with no descendant reported — checked with the feed drained quiet first, because a child created moments earlier echoes into the round and looks like the rename listing it. Deleting a folder in the same round as moving a subfolder of notes out of it leaves the notes where the remote has them (§7, "A round is one batch"): the subfolder arrives at its new parent, the old parent arrives removed, and the note under the subfolder survives untrashed.
- `?alt=media` was served **200 from `www.googleapis.com` itself**, with no `Location` header and so no redirect to `*.googleusercontent.com` — which the CSP blocks and which cannot be allowed narrowly, since the wildcard would take in Apps Script web apps (§9). Measured once, for a small file; a large one may yet be served differently.
- A first connect leaves **one** app folder, where `ensureRoot` and the first pull's reset both go looking for it seconds apart. Confirmed after a real connect: one `skysa-notes` folder, not two.
- Tokens: backend exchanges the auth code with `access_type=offline&prompt=consent` to get a refresh token. Access tokens last 1h; client requests a new one from `/api/token` on `AuthError` or proactively at 55m.

### 5.2 OneDrive (Microsoft Graph)
- Scopes: `Files.ReadWrite.AppFolder offline_access openid email`. User consent only.
- Root: `GET /me/drive/special/approot` — Microsoft creates `/Apps/<AppName>` automatically, where `<AppName>` is the Entra app registration display name. Register it as `skysa-notes` to match `APP_FOLDER_NAME`; no ensureRoot creation logic beyond writing `.notesapp.json`.
- Files, create: `PUT /me/drive/special/approot:/{path}:/content?@microsoft.graph.conflictBehavior=fail` (simple upload, fine for markdown; add a resumable session only if a file ever exceeds 250 MB). Graph's default for an upload is to **replace**, so the `fail` is what keeps a create from being a blind overwrite; a name in use answers `409`. The adapter looks the path up before raising `ConflictError`; Graph does not say what an upload into a missing folder does (it may make the folders), so a refusal with nothing at the path and no parent folder is `NotFoundError` for the parent.
- Files, update: `PUT /me/drive/items/{id}/content` with `If-Match: <eTag>` → `412` when stale. **By id, never by path**: an upload by path creates a file that is not there, and a file deleted since the caller last saw it is exactly what an expected version is meant to catch. The adapter looks the path up first for the id (and answers a stale or missing file without uploading); `If-Match` covers the moment between.
- Neither the `conflictBehavior=fail` → `409` nor the `If-Match` → `412` behaviour of an upload is in Graph's reference pages — they come from the OneDrive docs' issue tracker and Microsoft Q&A — and the move page documents only `if-match`, not `conflictBehavior`. All three wait on the live run in Phase 3.
- Folders, create: `POST /me/drive/items/{parentId}/children` with `{ name, folder: {}, '@microsoft.graph.conflictBehavior': 'fail' }`. **The parent goes in by id, never by path** — the same rule the update above follows, and for a blunter reason: Graph answers a `POST .../children` whose parent is addressed by path with a bare `400 invalidRequest`, at every depth, whatever the name and `conflictBehavior` say. Measured against a live personal account 2026-09-21: `POST special/approot/children` 400, `POST approot:/{parent}:/children` 400, `POST /me/drive/items/{parentId}/children` 201. `GET .../children` by path is fine, and so is `PUT approot:/{path}:/content`, which is why an app folder could hold its marker and refuse the first notebook beside it. The root's id is cached, so only a nested folder costs the lookup. The wire stub accepted the path form and so could not catch this: it now refuses it as Graph does.
- Move: `PATCH /me/drive/items/{id}?@microsoft.graph.conflictBehavior=fail` with `{ name, parentReference: { id } }`. The parent is named by its real id (Graph refuses `root` there), so a move costs a lookup of the destination and its parent. The destination is looked up *first*: a queued move the entry has already made returns without a request, and a rename that changes only the case of a name is still sent.
- Reading: `/content` answers with a `302`, which a cross-origin request carrying an Authorization header may not follow. The adapter reads the item for its eTag and `@microsoft.graph.downloadUrl`, then fetches that URL **without** the token: it is pre-authenticated, needs no preflight, and is not on Graph — `*.files.1drv.com`, `my.microsoftpersonalcontent.com`, or `*.sharepoint.com` for work accounts. Those are the hosts §9's `connect-src` needs besides `graph.microsoft.com`.
- Version: `eTag`. It changes on a move, where Dropbox's `rev` does not — which §7's `syncedHash` answers for a note renamed while it holds unpushed edits. `cTag` changes only with content, but delta on OneDrive for Business omits it, so it cannot be the version.
- Changes: `GET /me/drive/special/approot/delta`, following `@odata.nextLink`; the `@odata.deltaLink` is the next start. `410` — and, on a link we stored, a `400` (a token Graph cannot read) or a `404` (the app folder it was for is gone) — is `CursorResetError`; the same on the very first request is an ordinary failure, since starting again would ask the same thing. Deleted items carry a `deleted` facet and **no `name` at all** — not on Business and not on a personal account either, which the note here used to imply. Verified against a live personal account 2026-09-21: a deletion arrives as its id, its `parentReference`, the `deleted` facet and a `file`/`folder` facet, and nothing else. The adapter never asks for one (it resolves a deletion by id through the tree), so nothing depended on it, but the wire stub was sending a name no caller could really have and no longer does.
- Paths: **delta never includes `parentReference.path`**, and a renamed folder's descendants are not reported. The adapter therefore keeps the tree — id → parent id, name, kind — **in the cursor** (`packages/core/src/providers/idTree.ts`, which Google Drive's adapter shares; what is Graph's own — the link, dead-link rules, the anchoring refusal — stays in `onedrive.ts`), and resolves every path from it once the whole page is applied, so an edit inside a folder renamed in the same page gets the new path. Consequences: a folder rename is reported as the folder alone (the engine's folder-only path, as for Drive); a deletion is reported at the path the item had before the page, and one the tree never placed by its id alone (the engine finds nothing for an id it does not hold); an item whose parent has not arrived yet is carried in the cursor, with the path it had, until the round ends. Graph lists every parent of a changed item unless asked not to (`deltaExcludeParent`), so an item the round ends without placing has left the app folder — the user can move things out of it — and is reported deleted where it was. A deletion's old path is walked up the tree as it was, through any held item by the path *it* had, so a note deleted inside a folder still waiting on its new parent is reported where it was. Every deletion Graph lists is reported, even inside a folder also reported deleted: the engine matches it by id, and a filter by path cannot tell two folders that held the same old path within one round apart. At the end of a round anything else the tree can no longer place (what was inside a folder that was deleted or moved away) is dropped from it without being reported — something above it that was placed before moved or went, and that is reported. A file delta lists with no eTag is left out rather than thrown over, since one would stop every pull. A first scan that has items but none naming the app folder as parent is refused rather than reported as an empty folder, which would delete every clean note; the app folder's id is read afresh at the start of every scan. The cursor grows by a few hundred bytes per item in `syncState`, and every link read back from it must be on `graph.microsoft.com` before a token is sent to it. Outside delta, the path an item was asked for plus the name Graph returns gives its path.
- Graph lists the app folder itself in its delta; the adapter drops it (§7 guards the same in the engine).
- What a round reports, measured against a live personal account 2026-09-21, with a cursor held across each: **deleting a folder of notes** lists the folder and every note in it, each as a nameless tombstone. **Moving a subfolder of notes out of a folder and deleting that folder in one round** lists the moved subfolder at its new parent and the old parent as deleted — and says nothing about the notes inside the subfolder, which is the case the id tree exists for: their paths rebase from their parent's move, not from an entry of their own. **Renaming a folder while moving a note into it, in one round** lists the folder under its new name and the note under that folder, and the note ends up inside it. All three match what §7's "A round is one batch" assumes.
- Graph says to apply a round's changes after its last page, and the engine does (§7, "A round is one batch"). Within a page every path is where the item is once the page is in, so the adapter lists the page's folders first, outermost first, and everything else after in the order it happened: a file listed ahead of the rename of the folder it lands in would otherwise be carried off by that rename.
- The two resync codes are told apart. Graph answers a dead token with `410` and one of them, and they disagree about whose copy may have lost something: `resyncChangesApplyDifferences` says "Replace any local items with the server's version (including deletes)", which is what a scan does anyway, while `resyncChangesUploadDifferences` says "Upload any local items that the service didn't return" — a server-side restore. So `CursorResetError` carries `uploadDifferences`, and the rescan it starts deletes nothing (§7, "A rescan that uploads"). The code is read from `code`, from `innerError` and `innererror` alike, and from the `details` list, since the page says only "an error response containing one of the error codes below" and missing it is the direction that costs notes; anything unrecognised, `resyncRequired` included, falls back to today's reset and never to uploading. A folder moved *into* the app folder from elsewhere is reported alone; whether Graph lists what is inside it is one of the live checks.
- OAuth (`apps/api/src/oauth/onedrive.ts`): Authorization Code + PKCE against `login.microsoftonline.com/{MICROSOFT_TENANT}/oauth2/v2.0/{authorize,token}` as a confidential Web client, `response_mode=query`, `prompt=select_account` — without it Microsoft silently uses whatever account the browser is signed in to, which on a shared machine may be someone else's, and in storage-first that account then signs in as the user it is connected to.
- Account id: the ID token's **`sub`**, read from the token endpoint's response without a signature check (OIDC Core §3.1.3.7 allows it for a token received directly over TLS), and refused unless its `aud` is this client. Not `oid`, which needs the `profile` scope and is the same across every app a user signs in to; `sub` is pairwise — derived from the app, the user and the tenant they signed in through — which is all a connection needs, though an operator who changes `MICROSOFT_TENANT` to a tenant where their users are guests makes every returning user look new. Display name: the `email` claim, else "OneDrive"; it is unverified and a tenant admin can set it to anything, so it is stored with `email_verified = false` and must never link accounts (§6). So no Graph call is needed to name the connection. Claims are read at the code exchange only: the ID token a refresh returns is one Microsoft says not to rely on.
- Tokens: refresh tokens issued to the backend and **rotated on every refresh** — `/api/token` stores the new one; access tokens ~1h. Microsoft has no per-app revoke, so disconnecting deletes the row and answers `revoked: false` (§9).

### 5.3 Dropbox
- App type: **App folder** access. Scopes: `files.metadata.read files.metadata.write files.content.read files.content.write account_info.read`.
- Root: with App folder access, the API root *is* `/Apps/<AppName>`, where `<AppName>` is the app name set in the Dropbox App Console (immutable after creation — create it as `skysa-notes`). All paths are relative to it. ensureRoot just writes `.notesapp.json` at `/`.
- Files: `POST content.dropboxapi.com/2/files/upload` with `mode: { ".tag": "update", update: rev }` for conflict-safe overwrite (Dropbox returns a conflict error rather than auto-renaming when `autorename: false`). `mode: add` for create. **`strict_conflict: true` is required**: without it an `update` whose rev no longer matches still succeeds when the file has since been deleted, which is exactly the case the expected version exists to catch.
- `Dropbox-API-Arg` is an HTTP header, so it must be ASCII: every character above printable ASCII has to be `\uXXXX`-escaped or a notebook named in a non-Latin script fails at the transport with an unhelpful 400.
- Errors: only a **409** carries an endpoint-specific `error_summary`; any other status may carry plaintext or an intermediary's HTML, so a tag is only ever read out of a 409, and by whole `/`-separated segment rather than substring. Otherwise a 503 whose body happens to say `conflict` would have the conflict rule copy the user's note aside over an outage. Match by segment, not equality — Dropbox says the tail carries detail that can change. A conflict does not include the current entry, so the adapter fetches it with `files/get_metadata` before raising `ConflictError`; that extra round trip happens only on the conflict path.
- `strict_conflict` also means Dropbox answers `conflict` for an `update` whose file has been **deleted**, where §4 calls for `NotFoundError`. The adapter tells them apart by looking the path up after a conflict: no entry plus an expected version is the deleted case. The engine's re-create-on-push path depends on it.
- `path_display` is nullable in Dropbox's spec. Defaulting a missing one to the empty string would produce an entry pointing at the app-folder **root**, which a later `delete` would act on, so the adapter refuses such metadata loudly instead.
- A cursor Dropbox cannot parse comes back as a plain **400**, not as `reset`. Both mean discard and re-scan; only one is typed, so the adapter maps a 400 from `list_folder/continue` to `CursorResetError` too. Without it a truncated cursor is retried forever.
- Folders have no `rev` and no `server_modified`. The adapter reports both as empty rather than inventing them, and nothing compares either for a folder.
- `create_folder_v2` answers with a `CreateFolderResult` whose `metadata` is declared as `FolderMetadata`, not as the `Metadata` union — so alone among the endpoints the adapter reads entries from, **it carries no `.tag`**, and a shared mapper that reads one calls every folder the app creates a file. `list_folder`, `get_metadata`, `move_v2` and `delete_v2` all tag what they return. Verified against a live account 2026-09-21, after the wire stub had tagged it anyway and hidden exactly that bug; `toFolderEntry` sets the kind from the endpoint rather than from the payload.
- `create_folder_v2` **creates missing parents itself**, in the one call (verified 2026-09-21: `a/missing/deep/child` under an empty `a` succeeded). So a `mkdir` whose parent another device removed does not fail, and the engine's `ensureRemoteFolder` retry is unreachable on Dropbox. Note the corollary: it silently re-creates a folder the user deleted elsewhere, rather than refusing.
- A `rev` is lowercase hex of at least 9 characters, and Dropbox validates that **shape before it compares the value**: a malformed one is a plain 400, not a conflict and not a missing file. Nothing in the engine can send one, since every rev it holds came from Dropbox, but a test that makes one up never reaches the behaviour it means to check — which is why the contract suite takes a per-provider `staleVersion`.
- Worse for a test than the shape rule, and the reason the suite now seeds and deletes a real file rather than inventing a version: an `update` **whose rev Dropbox has never issued** finds nothing to conflict against, so where the path is absent it simply **creates the file**, `strict_conflict: true` or not. Measured 2026-09-21: absent path + unknown rev → created; deleted path + unknown rev → created; deleted path + that file's real former rev → `conflict`, which is the case above and the only one the engine can produce; present path + non-matching rev → `conflict`.
- Version: `rev`.
- Changes: `files/list_folder` with `recursive: true` on first sync (returns cursor), then `files/list_folder/continue`. Optional later: `files/list_folder/longpoll` for near-instant sync while the tab is open.
- A round's entries are to be processed in order, each `DeletedMetadata` taking whatever is at its path then, and children included; a renamed folder comes back as its old path deleted and the new folder with everything in it listed again. Neither is on the API reference page; both are Dropbox staff answers ([processing order](https://www.dropboxforum.com/discussions/101000014/why-should-i-remove-the-entry-and-all-its-children-for-each-deletedmetadata-when/535415), [renamed folders](https://www.dropboxforum.com/t5/Dropbox-API-Support-Feedback/Handling-renamed-folders-in-list-folder-list-folder-continue/td-p/225665)). The wire stub replays what happened in order but reports a move as the new place alone, with no deletion of the old path; `randomRemote.test.ts` also runs the fake's feed told as Dropbox tells it — the old path deleted by path alone, then the new place, with and without the children listed again. An id-less deletion under a folder the round renames cannot be told apart from the rename's old path, so the engine asks the provider (§7). **Both confirmed against a live account 2026-09-21**: renaming `Work` to `Renamed` reported `Work/a.md` deleted, `Work/b.md` deleted, `Work` deleted, then `Renamed` and both its children — children before their parent on the way out, parent before its children on the way in.
- Paths: use `path_display`; Dropbox also gives an `id` (`id:...`) — store both, prefer id for identity.
- Tokens: `token_access_type=offline` → refresh token. Access tokens ~4h.
- Note: production apps need Dropbox "production" approval once past the dev user cap; App-folder apps have a light review.

### 5.4 WebDAV
*Deferred indefinitely (2026-09-17).* WebDAV is not being built. What follows is the design as planned, kept so it need not be worked out again if that changes; nothing in this repo implements it.

- Auth: URL + username + password (app password recommended). Stored encrypted on the backend; the client never sees them.
- Transport: **all WebDAV traffic goes through `/api/webdav/*`** because most servers don't emit CORS headers. The proxy forwards method/headers/body verbatim, injects Basic auth, restricts to the configured base URL, and streams bodies. Supported methods: `PROPFIND`, `GET`, `PUT`, `MKCOL`, `MOVE`, `DELETE`, `REPORT`.
- Root: the user supplies a base URL that *is* the app folder (e.g. `https://cloud.example.com/remote.php/dav/files/david/Notes/`). ensureRoot does `PROPFIND depth 0`, `MKCOL` if 404, then writes `.notesapp.json`.
- Files: `PUT` with `If-Match: <etag>` for updates, `If-None-Match: *` for creates. Version = `ETag` (strip weak prefix `W/` and normalize quotes).
- Changes: no universal delta. Strategy in order of preference:
  1. RFC 6578 `sync-collection` REPORT if the server advertises it (Nextcloud/ownCloud/SabreDAV do) — cursor is the `sync-token`.
  2. Fallback: full recursive `PROPFIND depth infinity` (or depth 1 walk if infinity is refused) diffed against the last snapshot. Cap frequency (e.g. on app open + every 5 min while active).
- Identity: path-based. After a `changes()` pass, re-link renamed files by reading frontmatter `id` of any "new" file whose size/etag suggests it might be a moved note. Accept that renames done outside the app look like delete+create in the worst case.

## 6. Backend

Hono app in `apps/api`, deployed to Cloudflare Workers with `wrangler`. Keep it boring.

- Runtime: Workers only. Use Web Crypto (`crypto.subtle`) for AES-GCM, `fetch` for provider calls, no Node built-ins. `wrangler dev` locally (Miniflare) with a local D1.
- Database: D1 via `drizzle-orm/d1`, migrations with `drizzle-kit generate` + `wrangler d1 migrations apply`. Same SQLite dialect locally and in prod.
- Secrets: provider client ids/secrets and `SECRETS_KEY` via `wrangler secret put`; never in `wrangler.toml`.
- Static SPA served from the same Worker via `[assets]` in `wrangler.toml` (SPA fallback to `index.html`), so `/api/*` and the app share an origin and cookies are first-party.
- **Composition root:** `apps/api` exports `createApp({ entitlements, rateLimiter, fetch, providerTimeoutMs, config })` as a library; its own `src/worker.ts` calls it with the defaults. An operator who needs different behavior writes their own Worker entry that imports `createApp` and passes their own implementations, instead of forking. Nothing in `apps/api` reads env directly except `worker.ts`.
- Cookies with `hono/cookie` — one, the short-lived OAuth flow cookie; there are no sessions (see "Per-connection credentials"). Request validation with `zod`. (`@hono/zod-validator` was declared up front and never used — the routes validate with `zod` directly — so it was removed. Re-add it when a route actually wants the middleware; the removal is not a decision against it.)
- **Entitlement seam:** every route that mints a token or proxies WebDAV calls `entitlements.check({ connectionId, provider, accountId, displayName })` from an `EntitlementProvider` interface in `core`. The repo ships `AlwaysAllowed`. Operators of a shared instance can substitute their own (an allowlist of accounts, for example) through `createApp`; no such policy logic lives in the repo. *Revised in Phase 7:* it took a `userId` until connections stopped aggregating under a user, and an account is what an operator's rule can actually be written about. **The OAuth callback asks as well**, once it knows which account it is and before it stores anything: asked only at `/token`, a refused account still left its refresh token sealed in D1, unusable and unreachable, and its owner learned of the refusal when sync failed. `connectionId` is absent from the subject when the account has no row yet. A refusal stores nothing — no connection, and no grant, whose hash would otherwise be spent — withdraws the consent just given where the provider has a revoke call, and sends the user back with `?connect=refused`; the operator's `reason` is not carried, since free text in a URL is text anyone can put in a link. An account that already has a connection keeps it as it was, and `/token` goes on refusing it — and for that account nothing is revoked, because Google's revoke takes every token the user has granted the app, the one sealed in its row included, and a refusal can be a lapse the operator lifts later. A seam that throws has not said yes: `?connect=failed`, nothing stored. `/token` still asks, because what is allowed today can lapse.
- **Rate-limit seam:** `createApp({ rateLimiter })`, defaulting to `neverLimited`, consulted by `POST /api/auth/connect/:provider/start`, the callback, and `POST /api/token` — the three endpoints that spend an outbound provider call. A seam and not a Cloudflare binding, for the same reason as the entitlement one: a binding would be deployment-specific code in a repo that forbids it.
- **Provider enablement** (`ENABLED_PROVIDERS` env, default `dropbox` — only what is implemented; each OAuth provider listed must have its credentials or the app refuses to boot). `webdav` is accepted and needs no credentials, but WebDAV is deferred (§5.4): nothing is mounted for it and the client offers no way to connect one. If it is ever built, its routes and proxy are mounted only when `webdav` is listed.
- **No sign-in separate from storage.** Decided 2026-09-18, and it closes what used to be two modes behind an `AUTH_MODE` env. Identity and data are coupled: a connection is reached by the credential the device that made it holds, and nothing anywhere aggregates connections under a subject. A person with Dropbox and Google Drive connected has two silos, and the server cannot tell they are one person — which is the property, not a limitation to be fixed later.

  What this closes, so it is not re-opened by accident: no `identities` table, no `IdentityProvider` adapters, no Google/Microsoft sign-in, no merge-by-verified-email, no account linking, no magic link, and no `arctic` dependency — whose deprecation (July 2026) had been an open question since 2026-09-14 and is now moot rather than decided. §14 keeps the reasoning and what it would have cost.

  The gain is that a whole class of question stops needing an answer here: which of two identities a grant belongs to, what a verified email is worth, what happens when a linked provider is unlinked, and who may see a connection someone else made. A shared instance is still possible — that is what the entitlement seam is for — it just gates on the storage account rather than on a user the server invented.

  **Still in the tree, and going:** `AUTH_MODE` (an env var with one legal value), the `users` and `identities` tables (`apps/api/src/db/schema.ts`, unread by any code), and the client's `account-first` branch in `AccountPanel`. They are left standing in the change that made this decision because dropping the two tables is a hand-written D1 migration and this is a documentation change; issue #118 tracks them.

- **One OAuth flow per provider, and it is for storage.** `/auth/connect/:provider` requests storage scopes only. There is no `/auth/login/:provider` and none is coming. *From Phase 4:* the storage request does **not** pass `include_granted_scopes` (see "Storage OAuth, as built"). One consequence of Google's model is worth keeping written down even now that only one flow exists: Google revokes every grant to a project at once, so disconnecting storage revokes the whole project's access for that user — there is simply nothing else left for it to take down.
- WebDAV proxy: stream request/response bodies straight through (`c.req.raw.body` → upstream `fetch` → return `Response`); enforce a 30 s upstream timeout with `AbortSignal.timeout` and a 20 MB cap regardless of Cloudflare plan limits.

### Storage OAuth, as built (Phase 2)

Dropbox is the first storage flow and the shape the others follow.

- **Hand-rolled.** The storage flows are Authorization Code + PKCE and about forty lines each, so they install no OAuth dependency at all. (`arctic` was once planned for sign-in, was deprecated by its author in July 2026, and is moot now that there is no sign-in — see "No sign-in separate from storage".)
- **The PKCE verifier and `state` ride in a short-lived signed cookie** (`skysa_flow`, 10 minutes, `httpOnly`, `sameSite=lax`), not a table. §9 wants `state` bound to the browser that started the flow, which is what a cookie *is*; a table would need a sweep job and a KV binding neither of which exists. The payload is signed because an attacker who could rewrite it could otherwise substitute their own `state` and complete a flow the user never began.
- **`sameSite=lax`, not `strict`**, on both cookies: the callback is a top-level navigation arriving from the provider, and `strict` would drop the cookie exactly when it is needed. `secure` is derived from `APP_ORIGIN` so plain-HTTP local development still works.
- **The HMAC key is derived from `SECRETS_KEY` through HKDF**, not imported from the same bytes that do AES-GCM. One key, two algorithms, is how key-separation bugs start.
- **`token_access_type=offline`**, and a grant that comes back without a refresh token is a 502 rather than a stored connection that would stop working in four hours with no way to recover.
- **A unique index on `connections(user_id, provider)`** (migration `0001_connection_per_provider`) turns reconnecting into an `ON CONFLICT DO UPDATE` instead of a read-then-write race between two tabs. It also makes §12.3 a constraint rather than a UI convention. Reconnecting clears `root_id`: a new grant can point at a different account.
- **`SECRETS_KEY` must decode to exactly 32 bytes**, checked at boot. It was `.min(1)`, which meant an operator mistake surfaced the first time somebody tried to connect an account. (The existing test fixture turned out to decode to 30 bytes.)
- **`returnTo` is confined to this app.** Anything not starting with a single `/` becomes `/`.
- **`/api/token` decrypts the refresh token and returns only the access token.** It is the first `entitlements.check(…)` call site (§6, "Entitlement seam"), and it re-seals a rotated refresh token so the connection survives a rotation Dropbox is allowed to do.
- **Disconnecting revokes best-effort and deletes regardless.** A user who asked to disconnect must not be left connected because the provider was down. `revoked: false` says only that the grant may still be live — the revoke failed, or the provider (Microsoft) has none.
- **One provider per user (§12.3), enforced once a second provider exists (Phase 3).** A signed-in user whose storage is connected at one provider is sent back with `connect=occupied` when they start or finish connecting another, and has to disconnect first. In storage-first any connected account signs in as its user, so a Dropbox and a OneDrive connection side by side would make whoever holds the OneDrive account able to mint the Dropbox tokens. Reconnecting at the same provider replaces, as before. Two consent flows for the same user that overlap — in two tabs, or on two devices, one of which stays signed in after the other disconnected the last connection — can both pass the check; Phase 7's multiple connections have to answer that properly (a unique index, or connections that do not sign anyone in).
- **Only a refused grant asks the user to reconnect.** `invalid_grant` and `interaction_required` from a token endpoint are `reauthorize_required`; anything else — `invalid_client` once a client secret expires, `temporarily_unavailable`, a 5xx, a timeout — is logged by its code alone (`apps/api/src/log.ts`) and answered `502 provider_unavailable`, which the client retries. Told to reconnect over an expired secret, every user would go through a flow that fails the same way, and nothing would tell the operator. A failed code exchange is logged the same way.
- **Google (Phase 4, `apps/api/src/oauth/gdrive.ts`)** follows the Microsoft shape, with Google's differences:
  - The request carries `access_type=offline` (no refresh token otherwise) and `prompt=consent select_account`. Consent is asked for again because a reconnect gets no refresh token without it; `select_account` is there for the shared-machine reason §5.2 gives. There is no `include_granted_scopes`, so the consent screen lists exactly the storage scopes. Revocation is per project either way (§6's two-flows bullet).
  - **Granular consent:** Google lets the user untick Drive and still completes the grant. The exchange checks the response's `scope` for `drive.file`. If it is missing, nothing is stored and the user is sent back with `connect=partial` (a `ScopeNotGrantedError`, which no token endpoint's error code can imitate), which the web app answers with "leave that permission ticked". This is not logged, since it is the user's choice. Nothing is revoked either: Google revokes per project, so a revoke here would also end the same user's working connection on another device.
  - The account id is the ID token's `sub`, read and `aud`-checked as for Microsoft. Unlike Microsoft's, Google's `sub` is the same for every app the account signs in to. The display name is `email`, else "Google Drive", and is stored unverified whatever `email_verified` says (§6).
  - A refresh returns no refresh token, so `/api/token` keeps the stored one.
  - Disconnecting revokes: `POST oauth2.googleapis.com/revoke` with the freshly refreshed access token. That revokes every grant the user gave the Cloud project, which is why `docs/google-oauth.md` asks for a project per deployment.
  - A Workspace admin restricting Drive answers `admin_policy_enforced`, which is `provider_unavailable`, not `reauthorize_required`: reconnecting would be refused the same way.
  - While the Cloud project is in Testing, refresh tokens expire after 7 days. That arrives as `invalid_grant` → `reauthorize_required`, so users reconnect weekly. `docs/google-oauth.md` walks an operator through the project, the client and leaving Testing.

**Test harness.** `@cloudflare/vitest-pool-workers` — which would give the tests Miniflare's real D1 — still peers on `vitest ^4.1.0` against this workspace's 5, so it cannot be installed. The fallback is a ~120-line D1 shim over Node 22's built-in `node:sqlite` (`apps/api/tests/d1.ts`), which keeps the real `drizzle-orm/d1` driver, the real schema and the real migration files; only the process hosting SQLite differs. No new dependency. Swap it for the pool once that supports Vitest 5.

**Deliberately not done:** AES-GCM is used without additional authenticated data. Binding the connection id as AAD would stop a ciphertext copied between rows from decrypting, but an attacker who can write to `connections` has already lost the user the game. Recorded here rather than done, because the seal/open signature is cheaper to change now than after WebDAV credentials use it too.

### Per-connection credentials (Phase 7)

Until Phase 7 a user held **at most one connection**, because in `storage-first` any connected account signed you in as that user: two connections under one user would cross-authorise, and whoever held the OneDrive account would get tokens for the Dropbox one. Phase 7 removes the premise rather than the guard. **There is no shared user.** Each connected storage account is its own silo — auth and data coupled — and the device switches between the ones it holds.

What proves a device's right to a connection is a credential it generated, not a session cookie:

1. The PWA generates 32 random bytes, **awaits** an IndexedDB write of them, and sends `SHA-256` of `sk1_<bytes>` to `POST /api/auth/connect/:provider/start` with `returnTo`. The hash rides in the existing signed `__Host-skysa_flow` cookie beside `state` and the PKCE verifier.
2. The callback commits the connection **and** its grant in one `db.batch`, then redirects as before. The batch being one transaction is load-bearing for the racing-callback recovery, and that in turn assumes D1 enforces foreign keys within it — documented, but proven here only against the `node:sqlite` shim. If it did not, the loser of a race would commit a grant pointing at an id that does not exist, the user would see `connect=ok`, and the device would be 401 for ever with its hash spent. The *security* property does not depend on it: a grant pointing at a dead id reads as claimed and authorises nothing.
3. The PWA presents `Authorization: Bearer sk1_…` from then on.

The plaintext credential never enters a URL, a fragment, history, a `Set-Cookie`, a response body, a Worker log, or the database. "The API never holds the plaintext" is literally true rather than true-except-in-transit — which is what deleted the exchange endpoint, the pending-code table, its TTL and sweep, the double-claim race, and the window where a connection was committed but its credential was never collected.

Each decision, with the reason it would otherwise be got wrong later:

- **`/start` is a same-origin `POST`.** The hash is caller-supplied, so a `GET` would be a session-fixation hole: a link carrying the attacker's hash, consented to by the victim, hands the attacker a live credential to the victim's storage. `hono/csrf` does not cover JSON bodies (it matches only form and text content types, leaning on CORS preflight), so the route checks `Origin === appOrigin || Sec-Fetch-Site: same-origin` itself and keeps `csrf()` as defence in depth.
- **Lookup is by hash, not `<id>.<secret>`.** An id-then-compare needs a constant-time comparison, and `crypto.subtle.timingSafeEqual` is a Workers extension **Node's webcrypto lacks** — and the suite runs on Node against a `node:sqlite` D1 shim. A unique index on the hash sidesteps a hand-rolled comparison tested under the wrong crypto. Idle expiry is part of the same query, so an expired grant is indistinguishable from an unknown one.
- **A hash is claimable once, ever, and `grants` rows are therefore never deleted.** Revoking a device, disconnecting the account (the foreign key is `on delete set null`) and the cap's prune all null `connection_id` and leave the row; `grantHolder` treats a null as revoked. The row that stays is a tombstone, and the unique index over `secret_hash` is what it holds.
  "Once, ever" means once per continuous life of the database, which is not quite unconditional: D1's Time Travel restores a point in time, and the credentials themselves live in each device's IndexedDB and are not rolled back with it. A restore therefore un-spends every hash issued since the restore point while the devices holding those credentials still hold them. Nothing in code can see that; it belongs with the operator, alongside the fact that a deployment reset invalidates every credential at once.
  Review caught this as a live hole rather than a precaution. An earlier draft used a plain insert and reasoned that a repeated hash would fail — true only while the row exists. A hash leaked from a database dump mints nothing on its own, but once its grant is gone it is claimable again, and the attacker needs nothing of the user's: they start a flow with the victim's hash, consent with storage of *their own*, and the row is re-pointed. The victim's device — offline throughout, holding the plaintext, told nothing — comes back, is answered 200, and syncs the user's notes into a stranger's Drive. All three ways a grant used to disappear reached it, and the prune is not even user-initiated. Tested as the attack, once per path (`connect.test.ts`, "a hash is spent once, however its grant stopped being live").
- **A connection no live device reaches is deleted, not kept.** Left behind it is a sealed, live refresh token that nothing can use and nothing can revoke — disconnecting takes a credential. So revoking the last live grant (only a device signing itself out can, since a caller revoking another is itself live) disconnects. The row is deleted by one statement that asks and deletes together (`DELETE … WHERE NOT EXISTS` a live grant), and only then is the grant withdrawn at the provider, best-effort, from the row as it was read: asked first and deleted after the provider's calls, a device whose callback committed in between had the row taken from under it, and a request cut off during those calls left exactly the orphan this removes. The web app has no button that signs out the device it is running on, so today this is the server keeping its own invariant rather than something a user reaches from the panel; the panel's Remove is for other devices, and that never takes the last. A grant idle past its expiry cannot authenticate and does not count as live. Connecting the account again makes a new row, and the device knows its notes by the account's id, not the row's. And the device retires what it replaces: "Connect again" mints a new credential, so once that is kept the device signs out the one it held for the same connection (`claimConnection`), rather than leaving it in the device list as a live key for 180 days. Best effort — a credential already revoked has nothing to retire. What is still not covered, and these are the orphans that do happen: a device that clears its site data while it is the only one, and an account whose every device idles out. The grants expire, but the row stays; there is no sweep, because a Worker has nowhere to run one without a cron trigger every self-hoster would then carry.
- **A device reconnecting with the credential it already holds succeeds.** The same draft refused every repeated hash, which wedged the ordinary case: nothing tells a device to mint a fresh credential before connecting again, and the duplicate rolled back the whole batch — new refresh token included — identically on the retry. A hash whose row already points at *this* connection is that device; only a hash bound elsewhere, or spent, fails the connect.
- **`GET /connections` is gone, replaced by singular `GET /api/connection`.** A one-element array invites the aggregation model straight back, and the client that unbinds on an empty list would keep "working" with the wrong meaning. 404 (or 401 for a revoked credential) means *this connection is gone*; a 5xx or a network failure means nothing.
- **`connections.account_id` is `NOT NULL`** so `(provider, account_id)` can be the upsert target: SQLite NULLs do not conflict, and a nullable target would insert a duplicate on every reconnect forever.
- **A grant cap per connection** (20, pruned inside the same batch), because every live grant is a key to the same storage. Eviction is by `last_used_at`, not `created_at`: pruning by age logs out the device someone actually relies on and keeps the ones they have stopped using, and going by use also means a grant already past its idle expiry is evicted before a live one instead of holding a slot it can no longer use.
- **Migrations `0004`/`0005` are hand-written.** `drizzle-kit`'s SQLite table rebuild emits `PRAGMA foreign_keys=OFF`, which D1 rejects and the test shim silently tolerates — green in tests, wedged on `wrangler d1 migrations apply`. A rebuild written by hand avoids the pragma but not the `DROP TABLE` + `RENAME` pair in the middle, whose partial state no re-run can recover from; so the new shape gets a new table name (`storage_connections`), `0004` never drops the table it reads, and dropping the old one is `0005`'s single statement. Every device reconnects after this: sessions carried that right before, and a grant can only be created by the OAuth callback.
- **`sessions` goes; `users` and `identities` stayed**, annotated at the time as the account-first mode's only callers. That mode was dropped on 2026-09-18, so the two tables now have no caller at all and are owed a migration (issue #118).
- This retires `holdsAnotherProvider`, `session_mismatch`, `claimedBy`, the compensating delete, and the `conflict`/`signin`/`occupied` outcomes — not by relocating them but by removing what made them necessary.

**The device half (`apps/web`).** The store layer was already keyed by connection; what was singular was everything that chose *which* one.

- **The chosen source is a persisted preference** (`sync.activeConnection`), not `syncState.first()`. Every reader and writer in `store/` asks `activeConnectionId`, and the writers ask **inside their own transaction** — asked outside, a note created while an account is being connected can be written under the connection its rows have just been moved off, where nothing shows or syncs it. The panel and the scheduler follow the same preference, so the notes on screen and the notes being synced are always one account's.
- **Connecting a source moves nothing but the device's own rows.** `moveRowsTo` takes the connection to move *from* (`LOCAL_CONNECTION_ID` for a first connect, a detached source of the same account for a reconnect — and on the way out only what the user has been shown and has asked for by name, see "Letting a source go" below: a disconnect on its own moves no row anywhere). It used to move every row not already under the target, which was the same thing while a device could hold one source and is now the bug: connecting a second account would carry the first's notes into a stranger's storage and say nothing.
- **Which account a connection is to lives on its `syncState` row, and nowhere else.** There was a device-wide preference beside it (`sync.notesAccount`) for whose the device's *own* notes were, because a disconnect moved a source's rows into the device's own pile and a reconnect had to know whether to resume them. No disconnect fills that pile now, so what is in it was written before anything was connected and is no account's; the preference, its `MIXED_ACCOUNTS` value and the label read from it are deleted rather than kept for a case that cannot arise. Resume is decided by the row the kept notes are still under: `bindingMode` asks whether a *detached* source has this account, and answers with which.
- **Nothing is asked at bind.** The "these notes belong to another account" prompt (`other-account`, `adoptAccount`, `needsAsking`) went with the pile it was about. The device's own rows are no account's, so copying them into the first source connected is what clicking Connect meant. A detached source of a *different* account is not absorbed by a bind at all: it stays a source of its own, in the list, saying what it holds. **The question is asked before the connect instead (2026-09-23).** Clicking Connect meant copying them only if the user knew it would, and nothing on the way said so. So pressing a provider while the pile holds a note or a notebook first says how many will move and into which provider, with Cancel — which keeps them on this device only — focused (`ConnectButton`, `pileContents`). It is asked before the credential is written or the server is asked, so a cancel leaves nothing anywhere; and on every connect, not only the first, since whatever the pile holds goes into whichever account is next. The bind itself still asks nothing.
- **A source's first import says how it is going, holds the app if it is the first, and can be cancelled (2026-09-23).** A bind of a source the device has not seen (no row for it, nothing resumed) marks its row `importing` (`{ lock, returnTo }`): `lock` when no other live source exists, and `returnTo` the source that was in front. **The pile is copied in and kept, untouched, until the import is through** — it used to be deleted in the bind's own transaction, which left Cancel nothing to go back to. While any source is importing, the pile is hidden from the source bar and `pileContents` counts nothing, so it is neither shown twice nor offered to a second connect; a second bind copies nothing more. The import finishes (`finishImport`) when the scheduler's first pull is `ok` and the push after it is `ok` or `blocked` — a stuck op is the ordinary attention state, not an import that never ends: the pile's rows, folders and ops go, and a pile note saved after the bind (a save another tab had pending) is carried into the source as a note of its own first. **Held:** for the first source the app behind a dialog is `inert` until then (`ImportDialog`, `routes/index.tsx`), since the notes being moved are the ones on screen; a later source says how it is going in the storage panel instead and holds nothing. **Progress** is the engine's `onProgress` (§7), republished by the scheduler at most every 150 ms: an indeterminate bar while the scan lists, a determinate one once it has the count, and the file it is on written faintly beneath, cut in the middle so the file's name survives a long path. The "Storage connected" toast is the dialog's to say for a first source: it waits while the credential brought back is still being taken up, since only the bind says whether the app will be held, and is dropped for good once it is. **Cancel** (`cancelImport`) halts the scheduler for that source — aborting its fetches — asks the server to disconnect, and then throws the source's rows, row and credential away and puts `returnTo` back in front (`abandonImport`), so the device is as it was before Connect was pressed. It refuses to throw away what the user wrote: a later source written in since its bind (`writtenSince`) is kept and the user sent to Disconnect, and one that finished while the cancel was being asked is left alone. A server that cannot be reached offers "Cancel here anyway" (the connection lives on at the server, as with "stop syncing on this device") and "Keep importing". Files already uploaded stay in the provider; connecting again adopts identical files rather than duplicating them.
- **The credential is written down before the binding**, matching `claimConnection`: a binding the device holds no credential for is one `reconcileAccount` gives up on.
- **The panel lists the sources, and the devices holding the one in front.** The device list is the compensating control for the XSS trade below, so it is asked for on open rather than hidden behind a disclosure. Both lists are shown only when there is more than one of the thing, since a list of one is noise beside a panel that already names it.
- **A disconnect names the source it is for.** `detachConnection` is given the connection and has no default, because the answer that lets a source go can arrive after the user has switched to another (`reconcileAccount` settles the connection it *asked about*). Letting go of "the active one" there would take a source the user never touched and leave the one the server dropped live on the device.
- **`verifyResume` cuts its rows loose in place.** It used to send them through `LOCAL_CONNECTION_ID` and back, which was equivalent while the local pile could only be this connection's. It is not now: the return trip moved *everything* under `LOCAL`, so a source let go while another was being verified had its notes swept into that other account's storage — dirty, queued, and with nobody asked. The scheduler calls `verifyResume` itself, so this needed no user mistake at all.
- **Every `await` inside a store transaction must be on a Dexie operation.** `unbindConnection` (since replaced by `detachConnection`) briefly awaited a helper that could answer without touching the database, and Dexie committed the transaction underneath it (`PrematureCommitError`) whenever that path was taken. Reads go at the top and the decision is a pure function.
- **Deliberately not done:** `sync.bindings`, the generation counter behind every `ifUnchangedSince` precondition, stays device-wide. It answers "did this device's binding state change under me", which is a device-wide question; per-connection counters would miss exactly the interleavings the preconditions exist for.
- **Letting a source go removes what the remote has and keeps what it does not, under the source's own name (2026-09-19).** It used to move every row under `LOCAL_CONNECTION_ID`, where they were invisible for as long as any other source was connected — a pile the user could not see, of notes they had been told stay on the device. The remote is the source of truth, so `detachConnection` deletes the rows it has been sent, their ops and the credential, and touches nothing remote. What `unsyncedIn` says it has *not* been sent — unsent notes, queued renames, tombstones it is owed, unmade notebooks, queued `rmdir`s, and everything while `resumeUnverified` — stays exactly where it is, with the notebooks above it, and so does any note an editor still holds text for that the store would not take (`settleEditors` answers with their refs, and every path settles the editors *immediately* before detaching: a disconnect waits on the server, the confirm is not a modal, and "the remote has the note" is not "the remote has the edit"). The `syncState` row stays with them marked `detached` (`at`, and `disconnected` for the user's own Disconnect or "stop syncing", `revoked` for the server ending it, `interrupted` for a row made again), stripped of cursor, root and access token. With nothing unsent the row goes too — and this tab remembers whose it was (`store/goneSources.ts`), so that a save arriving for one of its notes afterwards makes the row again with its account (`ensureDetached`), where the panel can name it and the same account coming back takes the note home. A source made again never takes the screen: what was showing is chosen by name first, the device's own pile included, which the list then offers beside it. Every path is this one — Disconnect, "stop syncing on this device", and the server no longer answering for the credential — so nothing is discarded unasked and nothing is moved to another account unasked, whoever was or was not there to ask. A detached source syncs nothing (no scheduler session, the sync store refuses it as it refuses a missing row, the token source is never asked) but is shown, editable, and says so: a banner over its notes, `{Provider} · {name} — disconnected, N not sent` in the list, and a panel offering Reconnect, Download (`store/exportNotes.ts`) and a two-step Discard that lists the notes by title, focuses Cancel, closes on Escape, says plainly that a delete still owed will be carried out on reconnecting, and can reach only what it listed *as it listed it* (`releaseConnection`'s `seen`, each note with its `updatedAt`, the notebooks and directory removals by path: a note written after the list was shown, or written *into* since, is kept, and the source with it; and a source another tab has connected again meanwhile is refused untouched). `activeConnectionId` falls back to the first *live* source before a detached one, so a source kept for one unsent note never wins the screen from one that works, but a detached source the user chose stays in front. Reconnecting is an ordinary bind: the same connection id clears `detached` in place and queues what is owed; the same account under a new id takes the rows home with `moveRowsTo(…, 'resume', detachedId)` and deletes the detached row; both are `resumeUnverified` if any row is linked to a file. Where that connection is already live and has pulled the file a kept row still names, the pulled row stands: a kept edit becomes a conflict copy beside it (fresh id, no file, owed a write) and a kept rename or tombstone is dropped, with an open editor pointed at whichever row stands for it. A different account absorbs nothing. **And the user is asked first, not told after (2026-09-19).** Pressing Disconnect settles the editors, sends one last push where that has any prospect of working (online, and the scheduler neither stopped nor idle-with-nothing-to-sync; ten seconds, after which the question is asked anyway and whatever the push lands is one thing less on it), reads what is unsent, and then *asks* — with nothing said to the server until it is answered, so a cancel has changed nothing anywhere. With nothing unsent it is the plain confirm. With something unsent it names how much, lists the notes by title (five, the rest behind a `<details>`) with a count per category, says why they cannot be sent where something is in the way, and offers: move them to another connected source, download them, discard them by name, or cancel — Cancel focused, Escape closing, and a failing save in *this* source disabling move and discard, since the rows are then not the whole of what the user wrote. The answer runs the server disconnect and then the release in one act (`letGoOfSource`); a server that refuses leaves everything as it was and "stop syncing on this device" asks the same question again with no server behind it. **Move** (`moveUnsyncedTo`, `moveRowsTo`'s `only`) takes the notes the remote never had in full and the notebooks around them into the named source, as new writing: no `remoteId`, `remoteVersion` or `syncedHash`, dirty, `source` pinned first so the bytes do not change under the engine, `createdAt`, `bodyOrigin` and `editorMode` kept, its own id unless the target holds that id, the target's spelling of the notebook and a free name compared folded, a fresh `write` apiece and a `mkdir` for each notebook the target lacks. Every op of the old source is dropped, and so are its tombstones and the `delete`s and `rmdir`s they stood for — a delete cannot be carried into an account that has no such file, and a dropped tombstone is recorded in `movedRows` so an undo lands in the target. Unsent **renames** are not moved either: the file is safe on the old remote under its old name. Two things follow and are said in a second step before anything moves — a note pushed once and edited since ends up in both accounts, the older version staying where it was, and the unsent deletes and renames are named with "{A} keeps those files as they are". It runs in one transaction with the release and takes the same `seen` care a discard does: what was written since the list was made is neither moved nor let go, and the source stays detached around it — and so is a note an editor still holds text for that the store would not take. That last one is `holding`, and the editors are settled *immediately before the release* on every path, `releaseConnection` included: the detach kept exactly those rows so unsavable text would have somewhere to land, and a release that took no `holding` deleted them again a moment later; and a save that only begins failing while the question is being read walks straight past the dialog's own guard, which was computed before it was asked. Move refuses outright, touching nothing, in three cases: a target that is not a live source; a source still `resumeUnverified`, where everything it holds is listed as unsent and a bulk copy into another account made on a count known to be wrong is exactly what the silo rule is there to prevent; and a list with nothing of the kind it carries, since “move 0 notes” is a discard of the renames and deletes reached through a button that says Move. The undo of a dropped tombstone follows `movedRows` with **both** halves of the forward, id included, and a note brought back into an account that already holds that id is given a fresh one (`freeKeyFor` in `store/notes.ts`, the rule `moveRowsTo`'s `landing` already used): one folder copied into two accounts is enough for two notes to share an id, and a `put` over the other account's row would delete text that, unpushed, exists nowhere else. The detached panel offers the same Move, with the same two steps.

**The security trade, stated rather than buried.** CSRF disappears as a class (a bearer is never sent ambiently) and the blast radius of a theft drops from *every* connection to one. But `httpOnly` was real protection against exfiltration and IndexedDB is not: an XSS today can mint tokens only while the page lives; tomorrow it can post the credential anywhere and use it until someone revokes the device. What holds the line is `script-src 'self'` with nothing inline (`apps/web/public/_headers`, pinned by `tests/csp.test.ts`), which stops being a good policy and becomes a hard requirement, plus HSTS on the shell, a device list that makes theft visible and revocable, and lazy idle expiry (180 days). The `sk1_` prefix reserves a non-extractable-ECDSA proof-of-possession variant that buys the property back; this ships the bearer and keeps the seam. It is written into CLAUDE.md in words, because a hard-rules list implying IndexedDB is safe for a long-lived bearer is exactly the kind of rule that quietly stops being honest.

**Deliberately not done:** no server-side revocation list, no per-device names, and no proof of possession. The device list plus `DELETE` is enough to act on a theft the user knows about; anything more would need something that can say *who* is asking, and after 2026-09-18 there is deliberately no such thing: the credential names a connection, not a person. A revocation list is the one of the three that could still be built on what exists.

### Data model (Drizzle, D1)
```
users               id, email, email_verified, created_at              (no caller; to be dropped — §10)
identities          id, user_id, provider ('google'|'microsoft'), subject, email, created_at   (no caller; to be dropped)
storage_connections id, provider, account_id, display_name, root_id,
                    secret_ciphertext, secret_iv, secret_key_id, created_at, last_used_at
                    -- unique on (provider, account_id); no user
                    -- secret = { refresh_token } for OAuth, { url, username, password } for WebDAV
grants              id, connection_id (null once revoked), secret_hash, created_at, last_used_at
                    -- secret_hash = base64url SHA-256 of the device's `sk1_…` credential, unique
```
Secrets encrypted with AES-256-GCM using `SECRETS_KEY` from env (rotate by re-encrypting; key id stored alongside ciphertext). Never log secrets. Never return them to the client. The credential behind `secret_hash` is never stored at all.

### Endpoints
| Route | Purpose |
|---|---|
| `POST /api/auth/connect/:provider/start` | `{ credentialHash, returnTo? }` → `{ authorizeUrl }`. Storage scopes; PKCE + state + the hash in the flow cookie. Same-origin only |
| `GET  /api/auth/connect/:provider/callback` | Exchange code, upsert connection with encrypted refresh token **and** its grant in one batch, redirect to app |
| `POST /api/connections/webdav` | *(deferred, §5.4)* Validate by `PROPFIND` against the URL, store encrypted creds |
| `GET  /api/connection` | The one connection this credential reaches (no secrets), and this device's `grantId` |
| `GET  /api/connection/grants` | The devices holding this connection, which one is asking, and which have gone idle. No hashes |
| `DELETE /api/connection/grants/:id` | Revoke one device, this one included ("sign out"). The grant's row stays, nulled. The connection survives while any other live device reaches it; with the last one it goes as `DELETE /api/connection` takes it, and the answer says so (`disconnected`, `revoked`) |
| `DELETE /api/connection` | Revoke at provider where supported, delete row; every grant is nulled, not deleted |
| `POST /api/token` | No body → `{ accessToken, expiresAt }` using stored refresh token |
| `ALL  /api/webdav/:connectionId/*` | *(deferred)* Authenticated proxy (see 5.4) |

Everything under `/api/connection*` and `POST /api/token` requires `Authorization: Bearer sk1_…`. Two refusals, and the difference is actionable: `credential_required` (401) means the device never had one and should connect; `credential_revoked` (401) means the one it holds is not known here any more and should be thrown away first.

There are no sign-in routes, here or anywhere: identity is the storage connection (§6). `AUTH_MODE=account-first` refuses to boot, which is now a refusal to honour a setting that describes something this project has decided not to build rather than something it has not built yet — the env var itself goes with the tables (issue #118).

## 7. Local store and sync engine (client)

### IndexedDB schema (Dexie)
```
notes        [connectionId + id (uuid)], path, title, body, frontmatter,
             remoteId?, remoteVersion?, contentHash,
             dirty (bool), deletedLocally (bool), updatedAt
folders      connectionId, path, remoteId?
syncState    connectionId, cursor, lastSyncAt, rootId,
             displayName? (what the server last called the account; a label, never an identity),
             detached? { at, reason: 'disconnected' | 'revoked' | 'interrupted' } (no longer synced
               from this device, kept only for what its remote was never sent; not indexed, so no
               version bump),
             boundAt? (when last bound; a tab's per-binding memory of the source compares to it)
             unreadable? ([{ remoteId, path, movedAside? }]: files that are not UTF-8 text,
                          left alone and listed in the storage panel, with where any note of
                          the user's went that one took the name of; written with the cursor,
                          a notice only)
opQueue      seq, connectionId, op ('write'|'move'|'delete'|'mkdir'|'rmdir'), noteId/path,
             remoteId? (the folder's, for 'rmdir'), attempts, lastError
```

### Sync loop (per connection)
1. **Pull**: `changes(cursor)` → for each remote entry:
   - new/updated remote, local clean → fetch content, upsert local, update `remoteVersion`.
   - new/updated remote, local dirty → **conflict** → apply rule from §1.
   - remote deleted, local clean → delete local.
   - remote deleted, local dirty → keep local, mark `remoteId = null` (will be re-created on push).
   - Persist cursor only after the batch commits to IndexedDB.
   - Cold start on a new device is a full scan (`changes(undefined)`); no remote index file. Revisit only if cold start exceeds ~10 s at ~2k notes.
   - A full scan reports how far it has got (`SyncEngineOptions.onProgress`, 2026-09-23). **It lists every page before it reads a note**, where it used to read each page as it was listed: no provider gives a total up front, and listing first is what gives one before the first download rather than after the last. Nothing is lost by it — a scan's pages carry no cursor, so an interrupted scan starts from the top either way — and pages are still decided and applied one at a time, so notes still appear as they arrive. While listing it says how many notes it has found so far; after, `done` of `found`, counting a note already held at its version as done without reading it (so a resumed import does not claim to download everything again), with the `path` of each file read. The push after it reports `done` of `total` ops and the path about to be sent. Delta rounds report nothing; they are short.
2. **Push**: drain `opQueue` in order. `write` passes `expectedVersion = remoteVersion`; on `ConflictError` → run conflict rule, re-queue. On `AuthError` → request token from backend, retry once, else pause connection and surface in UI. Exponential backoff per op; give up after N attempts and surface.
3. Triggers: app open, tab regains focus, `online` event, 60s interval while visible, Background Sync API when available (best effort), and immediately after a local edit (debounced 2s).

### Folder renames/moves
A remote folder rename or move is applied locally unconditionally, including when notes inside it are dirty: the move is metadata-only and does not conflict with content edits. Dirty notes keep their pending content ops and simply get their `path` rewritten; queued ops that reference old paths are rewritten before push.

A folder renamed, moved or deleted *here* is not one op either: its notes go up as moves or deletes, and an `rmdir` follows them for **each** directory they left, outermost first. The bullets below say when an `rmdir` removes anything — which is only when the folder is still the one the queue meant and holds no file at all.

One op per directory and not one for the outermost, though the outermost really does take its subdirectories with it on every provider, so each of the others sends nothing. The op is not only how the directory is removed: it is also how the *pull* knows the directory is spoken for. A sync pulls before it pushes, so between the move and the push the old directories are still on the remote, and the rows that named them have been re-pathed and stripped of their ids — which is what stops a full scan reading the id at the old path as a remote rename and undoing the move. To that pull they are directories nobody owns. `decideFolder` already refuses to make a notebook of one whose `rmdir` is queued, but it matches the op by id **and** path, which is what keeps it from dropping a folder another device has moved since; a subdirectory with no op of its own matched nothing. So the whole subtree came back — the notebook at its old path, ancestors conjured to hold it — and the outermost `rmdir` was then refused, because the device held a row under it again. The duplicate was permanent and on the remote as well as in the sidebar. Found by re-parenting a notebook that had been dragged into place a round earlier (2026-09-22): a directory this device made in the round before is exactly what its own next pull reports, which is why it needed a drag, a sync, and another drag to show up at all.

### Re-arranging is moving

The sidebar's tree is the user's actual directory structure, and the note list is sorted by when each note was last edited. Neither has a position stored anywhere, and there is nowhere on any provider to store one: a directory listing has no order of its own, and the app reads the folder with whatever tool the user also reads it with. So dragging a notebook or a note **re-parents** it — it answers "where does this live", which is `moveFolder` and `moveNote`, both of which existed for this and until now had no caller in the UI. Dragging a row to a position among its siblings is deliberately not offered: it would mean an invented order living either on the device (two devices then disagree about a tree they are both looking at) or in a sidecar file in the user's folder (a new format, a new conflict surface, and a file the user did not write). If hand ordering is wanted later it is that decision that has to be made first, not this code that has to be extended.

`apps/web/src/store/rearrange.ts` holds which drops are allowed, with no DOM in it, because each refusal is a gesture the pointer can really make and each is worth a test: a notebook into itself or into one of its own descendants (`moveFolder` throws, but a drop is not a way to find that out — the row has to say no while the pointer is over it); anything into the folder it is already in; and a note onto the top level, since notes outside a notebook exist only because a remote folder can arrive holding them and the app never *makes* one (§12.6). That last one is one-way on purpose: a loose note can be dragged into a notebook and not back out. A destination already holding a notebook of that name is *not* refused there — the tree is not given to that module, and `moveFolder` already answers it with the `FolderExistsError` the route renders for a duplicate name elsewhere, in the same words.

The mode is one piece of state in the route, because the two ends of a note's move are in different panes: the row is in the note list and every destination is in the sidebar. It is set by `dragstart` **or** by a command, and nothing downstream knows which — that is how the pointer gesture and its alternative stay one implementation. The alternative is not optional: WCAG 2.2 SC 2.5.7 asks that whatever dragging does be doable with a single pointer that does not drag, so `notebook.move` and `note.move` are registrations like any other (§7, "Commands are declared, not collected"), the destinations are ordinary buttons a click or Enter activates, and Escape — listened for on the document, since a move started from the palette leaves the focus nowhere near the tree — puts the thing down, as does the `Cancel` link in the hint above the tree, which a pointer or a thumb can reach where a key cannot. The hint's live region is its sentence alone, so the way out is not read out as news. While a move is on, every row says in words where the thing would land or that it cannot go there, rather than leaving that to a highlight; a row that cannot take it is `disabled`, which also takes it out of the tab order for the length of the move.

The URL names the open notebook by path, and a move changes that path — for the notebook itself and for everything under it. So a notebook move rebases the open folder, or moving the notebook you are in throws you out of it and into the first one in the tree. A note move follows the note only when it is the one open in the editor: a note dragged out of a list the user is reading has left, which is all they asked for, but the note they are *writing in* would otherwise sit beside a sidebar lighting up the notebook it has just left — the same disagreement opening a search result has to avoid.

### Conflict rule (concrete)
Remote wins the original path. Local content is saved as a new note at `<path minus .md> (conflict <YYYY-MM-DDTHH-mm>).md` with the same frontmatter except a fresh `id`. Both appear in the UI; a small banner links to the pair.

The stamp is UTC and minute-resolution, with the `:` replaced — a colon is illegal in a filename on Windows and rejected outright by several provider APIs, and a copy the provider refuses to store is the lost edit this rule exists to prevent. UTC so two devices in different zones name the same conflict the same way rather than producing two copies that look hours apart and unrelated. A minute is not unique enough on its own, so a second conflict on the same note inside one minute gets `-2`, `-3`, and so on; the comparison is case-insensitive, because Drive, Dropbox and macOS all are. The name is deliberately **not** slugified: the copy has to be recognisable as the note it came from and sort next to it.

Implemented in `packages/core/src/sync/conflicts.ts`.

### Edits the editor has not saved yet
"Local dirty" is the `dirty` flag, and an edit reaches it only when autosave runs, up to 2 s after the keystroke. Until then the row is clean, and a pull may replace its body or delete it. The store cannot see the edit, so the save decides instead (`saveNoteBody`, `apps/web/src/store/notes.ts`), with the same outcomes as the table above:
- **The note's origin.** `bodyOrigin` is a fresh random token each time a body is written in from outside the editors: a pull, an import, or the remote side of a conflict. Edits made here leave it alone.
  - It is a token rather than a count, so a note deleted and written again in one batch can't come back matching an origin an editor still holds.
  - A file that changes only frontmatter keeps the row's body and origin, so a tag or title changed elsewhere, or our own push completing, is not a conflict. The body is compared both as stored and as read from the row's own file, so a note that had no frontmatter until this app wrote it doesn't count as changed. `serializeNoteFile` puts a blank line after a new block, which reads back as part of the body, on that pull and every later one.
- **What an edit carries.** Each editor remembers the origin of the body it holds: the one it opened with, or the last one it adopted (`useIncomingBody`). A body with a new origin is always adopted, even when its text is something the editor wrote or was shown before, as in a remote revert, and the editor then forgets its own earlier saves. The editor's origin moves only once it actually holds the body. If the rich editor can't parse it, the old origin stays and it is asked again. Every edit carries that origin, plus the note as shown when it was typed.
- **Autosave never merges edits from different origins.** An edit typed before a pull is saved on its own, before an edit typed into the pulled text replaces it.
- **Same origin:** the save is written as usual.
- **Different origin** (the body was replaced): the edit becomes a conflict copy beside the note, written from the note as the user had it, with their frontmatter and the title their text gives it. The note keeps the pulled text. If the text is identical, nothing is written.
- **Note gone** (deleted by a pull): the note comes back as shown, holding the edit, dirty, with no `remoteId` and a `write` queued, so it is re-created on push like any dirty note deleted remotely. If a pulled file has taken its path, it takes the conflict name beside it.
- **Note deleted here:** the edit is written into the tombstone, which stays deleted, whatever the origin.
- **A save that fails is said, and kept.** `flush` calls `save` at once, every time, whatever is still being written — a mode switch or a delete that follows has to find the write begun, and on `pagehide` there is no later; ordering is the store's, since IndexedDB runs overlapping transactions in the order they were opened. A rejected save is held and the note view shows an alert until nothing is. A retry round happens on each flush and every 10 s while the editor is mounted: it writes what is pending first, then retries each failed edit once, oldest first. A failed edit is let go as soon as a newer one issued for the same note, in the same sitting, stands for it, so an older body is never retried while anything newer exists — retried on its own it comes back through the live query as a body the editor may adopt over newer text. A sitting ends when the editor's text is replaced from the stored body (another note, a mode switch, a body adopted from a sync pull or another tab): text typed after that does not contain an edit that never reached the store. An edit from an earlier sitting or another origin is never merged; if something newer was issued for its note it is saved as `displaced`, beside the note as a conflict copy. Deleting a note forgets what is held for it, so a retry cannot bring back a purged row; a note deleted from this tab by any other route (its notebook, from the sidebar) is remembered for the life of the tab (`store/deletedHere.ts`), and an edit to a vanished row is let go rather than brought back when the note is one of those, or the edit is a displaced one. A note seen here again — a live row at a save, a file a pull brings in under that id — is no longer one of those: another device restored it, and an edit to it that finds it gone later is kept. A body adopted while something was still pending flushes it as overtaken, which is saved as `displaced` whatever is issued after it: it was typed into the text that has just been replaced. Known limit: a displaced edit that reaches a tombstone, or a purged row, is dropped — it takes a failed save, a rebuilt editor and a delete together. There are no retries after unmount, and a save that fails only at the unmount flush is still lost silently.
- **A newer build in another tab ends this one.** Dexie answers `versionchange` by closing with auto-open left on, and the next operation reopens against the newer database without an error — so old code goes on writing into a store a newer build has migrated, and where the newer schema lacks something the old build declares, the old tab bumps the version and puts it back. The app instead finishes what autosave holds (bounded at 2 s, since the other tab's upgrade is blocked until this one closes), closes for good, and puts the tab behind a notice offering Reload (`store/staleTab.ts`, `StaleTabGate`, outside the router so the error screen cannot replace it). The notice can be put aside with "Copy my text first" — a failed save's banner says to copy the text out, and a block over the page made that impossible — after which a bar goes on saying the tab cannot save. The same check runs on every open, not only on the event: a tab that was not open when the upgrade happened (back-forward cache, a dropped connection, an old build from a stale cache) hears nothing, and Dexie opens it against the newer database without an error. That tab closes at once and finishes nothing: the newer schema is already live, and what the editor holds would be old code writing into it — it stays on screen to be copied out. A `versionchange` with no new version is a delete, not a newer build, and is left to Dexie. A tab whose own upgrade is blocked says so after a second rather than hanging.
- **Delete can be undone for about ten seconds.** The shell keeps the note as it was deleted, including text the store never confirmed, and shows a notice with Undo that does not take focus (`DeletedNotice`; also a palette command while it is up). While the tombstone exists, undo restores it — the queued delete withdrawn, a write owed. Sync pushes a delete within seconds and purges the row, so past that the note is made again from the kept copy: same id, dirty, no `remoteId`, a write queued, a conflict name if its path has been taken — and in the source it was deleted from, not whichever is showing by then, since the notice outlives a change of source. If that source has been let go inside the window, the note is restored under it all the same. A tombstone the remote was still owed is one of the things a detach keeps; where the whole source went, its row is made again detached to hold the note (`ensureDetached`, reason `interrupted`) — never the device's own pile, which nothing shows while another source is connected. Where the user moved what the source never sent into another one, the tombstone was dropped rather than carried, and the undo follows the move (`movedRows`) and brings the note back there, which is the only place the device still has for it. The notice then says the note is back in a source that is disconnected, to be reconnected or downloaded. A note restored from its tombstone keeps its path, as the remote does in a conflict (its file is still there), and whatever took the name meanwhile — compared folded, as every writer compares — moves to a free one beside it. Undo is one transaction. The kept text is what autosave still held unstored once every save had come back, asked for by note: a save that went into a conflict copy is stored, and is not offered again. Where that text is older than something stored after it — an edit held from before a body arrived from outside, and typed over since — it is not the note's body: undo brings the note back as it was stored and keeps the held words beside it, as a conflict copy. Deleting waits for the saves that were out, so the note is closed only if it is still the one showing by then. A body a pull put into the tombstone meanwhile is never overwritten; the kept text goes beside it. A failed undo keeps the notice up until it is dismissed. A second delete replaces the notice and the first stays deleted.

**Still open:**
- A dirty note that the engine resolves as a conflict while an edit is pending gets two copies: the engine's, holding what had been saved, and the save's, holding that plus the pending edit. Nothing is lost, but the second contains the first.
- Copies made by a save are not counted in the status line's conflicts, which comes from the engine. The copy appears in the note list, and the open editor shows the pulled text.
- A note another tab deletes, pushes and purges before this tab's live query hears of the delete looks the same as a remote delete, so the note comes back. That errs toward keeping the words.
- Two tabs typing into the same note is not covered: edits never change the origin.

### What the loop above left open, and how the engine answers it

The branch table is the specification; these are the cases it does not mention, each decided in the direction that cannot lose an edit. They live in `packages/core/src/sync/engine.ts`.

- **A file that is not a note is ignored**, as is anything at a hidden path. The app owns the folder but not everything in it: a PDF the user dropped beside their notes would be corrupted by being read as markdown and written back, and `.notesapp.json` is our own bookkeeping. Two separate checks, because the marker happens to satisfy both and would otherwise hide the loss of either.
- **Same bytes, new version → adopt the version, do not conflict.** This is our own write coming back, or two devices that saved the same thing. Keeping the old version would make the next push send an `expectedVersion` the remote has moved past, manufacturing a conflict over a file that already agrees with us.
- **A move reported as a deletion plus an entry** — which is what Dropbox and Graph do — must not act on the deletion. Applied after the move it deletes the note outright, and which order they arrive in is the provider's business. A remote id the batch says is somewhere *else* has been moved, not deleted.
- **A deletion is settled by a write-back only if the write pointed the note at a *different* file.** A note is written back by an entry about the very file a deletion names all the time — our own push echo arriving beside the other device's delete, which is what a rename here plus a delete there looks like. Reading "this batch mentioned the note" as settled drops the deletion for ever and leaves the row pointing at a file that no longer exists; the next queued move for it can then never succeed, and the ordered queue strands every op behind it. Asked of the *file*, the two cases separate cleanly. A deletion carrying no id names no file, so there it stays a question about the note, and the provider is asked whether the file the note now points at is there: a rename queued here adopts the version without reading a byte, so the write-back says nothing about whether the file outlived the deletion behind it, and a note kept on suspicion points at nothing for ever. Only "not found" lets go of it; any other failure fails the pull.
- **Alive elsewhere, not alive anywhere.** A batch routinely carries the state of a path before it was removed: our own write coming back, and then the other device's deletion of that same file. Reading the earlier entry as evidence the file survived drops the deletion — and a deletion dropped here is dropped for ever, leaving a row that points at a file nobody will ever mention again. The rule that entries are deduplicated to the last one about a thing applies here too: only an entry at a different path, or a later one at this path, says the file is still there — and an entry elsewhere counts only if it came after the thing was last listed at this path, since a round read whole carries a history (moved to `A`, back to `C`, deleted at `C`). Where the batch has already carried the note or folder to the path the deletion names (edited at `B/c.md`, `B` renamed to `C`, `C/c.md` deleted), only an entry after the deletion does.
- **A move may or may not change the version**, so the path is followed on both routes through the decision. Dropbox's `rev` survives a move; OneDrive's `eTag` does not. **And followed from where the batch has the note, not where the store last saw it.** `A` renamed to `B`, a new `A` made, and `B/x.md` moved back to `A/x.md`, all in one round: the folder's rename carries the note to `B/x.md`, and the file's entry names the very path the row still shows. Compared with the row, that reads as nothing having happened, so the pull reports `ok`, the cursor moves, and the note sits under the folder's new name over a file that is not there. Its next write then finds nothing at the path, finds the file by id, finds no rename of its own to follow, and blocks the ordered queue. The same holds for a file gone by the time it is read: whether the entry "would have moved" the note is asked of the batch too.
- **The version a move hands back is not the note's until its bytes are known.** A move changes no bytes, so it is tempting to keep the version it returns — but that is the version of the file as the move *found* it, and the engine has read nothing. Another device can have edited the file since this one's pull. Held as the note's own, the new version says "in step" about text this device has never seen: the pull skips the file as the version it already has, and the note shows old text until the file next changes; and a write checked against it is checked against the other device's edit, passes, and overwrites it with no conflict anywhere. Every provider had this, the ones whose version survives a move included — there the version handed back *is* the other device's edit. So after a move (`runMove`, and the move `followTheRename` makes ahead of a write) the engine keeps the returned version only if it is the one the note already held (Dropbox's `rev` and Drive's `headRevisionId` survive a move, so an unchanged file costs no read), or if the file, read by id, hashes to the note's `syncedHash` — and then it keeps the *read's* version, the one those bytes were seen under. A row with no `syncedHash` uses its own text if it is clean. Otherwise the note goes on holding the version it had, which is always safe: the next pull meets a version it does not know and reads the file. `followTheRename` fails the write instead of sending it; the file has been moved, the retry finds it at the note's path under a version the note does not hold, and `resolvePushConflict` reads it. If it did change, that is an ordinary conflict, which keeps both. If it holds the bytes the note last synced, nobody edited it — the version moved because the file did, and the read that would have said so failed — and the write goes again under the version those bytes were read under, rather than demoting the user's edit to a copy beside a file with no other editor. A read that fails in `followTheRename` fails the op as itself, so a rate limit is waited out and not counted; in `runMove` the rename has landed, and it is "cannot say". A dirty row with no `syncedHash` at all (databases from before v0.1.0) cannot be told either way, and gets the conflict copy: a copy nobody needed, where the other guess is an edit nobody can get back. The cost is one download per rename on OneDrive, whose `eTag` a move renews — no more than the pull would have spent on a version it did not hold. Graph's PATCH takes `If-Match`, so a `move` with an expected version would make the check atomic and drop the read; not done. The two-browser soak found both halves (seeds 578 and 461), where they turned on timing; `tests/sync/overProviders.test.ts` puts the other device's edit exactly where it has to land, over every remote.
- **A deletion that names the file is believed.** The rule above it — that a folder alive elsewhere in the batch means its children are not deleted — exists for a deletion carrying nothing but a path, and must not be applied to one carrying an id: the provider knew the file well enough to identify it, and "some folder above it is also in this batch" is not evidence against that. A deletion dropped here is dropped for ever, because the cursor moves on and nothing mentions it again.
- **A folder move is addressed by where the folder is now.** Renaming `A` and then dragging `A/sub` out of it lands as two entries in one window, and the second decision is reached after the first has already rebased everything under `A`. Naming the folder's pre-batch path moves nothing at all and says nothing about having failed, so the notebook keeps a position the remote abandoned until the next cursor reset — and a write into it then fails for ever. Same rule as for notes, applied to the one decision-maker that was still asking the store alone.
- **A folder move gets the folder in its way out of the way first.** Two folders cannot share a path — the store keeps one row per path — so a move onto an occupied one overwrites that row and merges both notebooks' notes into whichever name survives. Which of the two the engine does depends on what the rest of the batch says. If the batch also reports the occupant deleted (the user deleted `Archive` and renamed `Archive 2024` onto its name), it is deleted first, which is the order the remote did it in and lets the store cascade its subfolders. If nothing says it is gone, it is on its way somewhere else — two drags in one window — and it is moved aside under a conflict name, exactly as a note in the same position is, for the entry that says where it went to move it on from there. Deleting it on suspicion would take notes nobody asked to lose.
- **Which folder is in the way is a question about the batch too.** By the second claim on a path, the folder standing there may be one an earlier decision moved in. Reading the occupant off the store answers with the one that used to be there — and if *that* one is the one the batch deletes, the delete takes the newcomer's notes instead.
- **A folder created and deleted inside one window is forgotten.** Both halves arrive in the same batch, and the store — asked as it was before any of it — has never heard of the folder. Without counting what the batch itself has just made, the notebook sits in the sidebar with nothing behind it.
- **A remote folder delete keeps the dirty notes inside it**, detaching them so the next push re-creates them, and takes the clean ones and every subfolder with it. Which of the two a note gets is decided against the batch as well: a conflict earlier in the same batch hands the local edit to a copy and leaves the note clean, so it goes with the folder rather than surviving it. The folder is the user's remote layout; the note is their writing, and losing the second to a change in the first is not a trade worth making. The store does the cascade in one transaction, because a provider that reports only the folder gives the engine nothing else to send.
- **Decisions are reached against the store as it was, and applied in order**, so a later decision can be about a note an earlier one has already taken away. A provider that reports a folder deletion recursively produces exactly that — the folder, and then each file that was inside it. The engine tracks what the batch has already removed and says nothing twice; a note that turns up again afterwards (moved out of the folder in the same batch, or a file deleted and re-created at one path) is written back under the id it already had, so the user keeps one note rather than watching one vanish and another appear. Belt and braces: `delete-note` and `detach-note` for an id the store does not hold are defined as no-ops, because a batch that rejects is a batch that is retried for ever — the cursor moves only with it, so a single unanticipated ordering would leave the user with a sync that never recovers on its own.
- **One note per path, and one `remoteId` per note, once the batch has been applied.** A note of ours can be sitting exactly where a remote one is about to land — two devices both writing an `Untitled.md` offline is the ordinary way to get there. Left alone, the two share a path: the sidebar shows one row twice, the queued write for ours eventually lands on the other one's file, and both rows end up carrying one remote id — after which `noteByRemoteId` only ever hands back one of them and the other is stale for ever. So ours moves aside first, under the name a conflict copy would get, because that is what it is. That applies whether or not it has been pushed: a pushed note has no claim to the path either, since the remote has something else there, and it keeps its `remoteId` so the entry saying where its file went puts it back. Duplicates are therefore possible *during* a batch, which is why the store must not put a unique index on the path, and must not make room by deleting what is there.
- **Whether a path is occupied is a question about the batch, not the store.** By the time a change runs, an earlier one may have moved the occupant out, deleted it, conflicted it onto the remote's path, or carried it off with a folder — and one the store says is nowhere near may be about to be carried *in* by a folder move, which re-lists no children, so nothing else in the batch mentions it. Asking the store alone either moves a note that has already gone — which fails the batch, and a failed batch is retried for ever — or leaves two notes on one path. So does asking it what names are free: the same folder move can bring in the exact name a conflict copy was about to take. More than one note can be in the way of a single file, and each gets a name of its own.
- **A displacement carries the note's queued ops with it**, exactly as a folder move does. A queued `move` is the user's rename and its target is the very path the remote has just taken: left pointing there it conflicts on every push and can never succeed, and since the queue is ordered and a dead op stops the drain, every later op for every other note is stranded behind it.
- **A file can be gone by the time we read it.** `changes` and `read` are separate round trips on every provider, so a file the feed named can be deleted in between — the other device editing a note and then deleting it inside one cursor window is enough. The entry is skipped rather than thrown on: unwinding the pull leaves the cursor where it was, so the next attempt fetches the same batch and dies the same way, and push never runs either because `sync` stops on a pull that is not `ok`. Nothing is imported and nothing of ours is moved aside; the deletion arrives as an entry of its own. Except for a note held by that very file which the entry would have moved: the deletion, in this batch or a later one, is at the new path, where the note never got to, and one with no id has nothing else to find it by — so the note whose file is gone is let go of there and then. At its own path the deletion finds the note, and nothing is decided on the read alone. Only "it is not there" is survivable — a refused or broken read is a batch nobody has decided, and moving the cursor past it would skip the changes for good.
- **A file that is not UTF-8 is left alone.** Latin-1, UTF-16, a binary named `.md`: decoded anyway it arrives as a note with U+FFFD for every byte that would not read, and the next push, even the app adding an `id`, replaces the user's bytes with that. So `read` refuses it (§4), nothing is imported, and **no row holds the id of a file the engine could not read**, so no write or rename from here can land on it once a pull has seen it. A clean note whose file became unreadable goes from this device and nothing is queued against the remote — a note the user had deleted included, whose delete is dropped *when the pull sees the file first*: it was of text they had seen, not of these bytes. A delete pushed before any pull has seen the re-save still removes the file — `runDelete` asks nothing of it, and a download before every delete is not worth what it would close — which is the window an edit made on another device has always had. The dropped delete stays queued until the next push finds no note for it, and a delete names its note by id alone; so a file arriving meanwhile that carries that id — another device's edit to the same note, set aside — is given a fresh one rather than the id a delete is queued for, or the delete would be re-aimed at it. A dirty one is cut loose and moved to a conflict name, and its write creates a new file beside the one it could not read; one the user has renamed meanwhile is cut loose and left where they put it, since nothing is in its way there. A note never pushed that has the same name moves aside, as for any arriving file. A push that meets such a file — in the way of a note with no file of its own, or as the note's own — does the same and finishes in that drain, with no attempt spent and the op counted as pushed, since it reached the remote as a new file. Where the conflict name is taken on the remote by a file this device has not pulled (another device setting its own edit aside in the same minute), the create says so and the next name is tried, bounded as a rename's is; the store is moved first and the remote second at each step, so a process that dies between them leaves an unbound dirty note whose write is still queued, never a file no row knows of. A note with a readable file of its own elsewhere steps aside still bound to it, as it does for any file that is not its own. A probe that only asks whether a file exists takes unreadable as yes, so a rename of such a file is carried out (it changes no bytes) and the pull that next reads it lets go of the note. None of it throws, since a pull that throws never moves its cursor and these bytes read the same way every time. With no row, every entry for such a file is read again, so the file is picked up as a note on the first pull after it is saved as UTF-8. **The rule never turns on the app's own notes, because the app never writes a U+0000**, and that rests on there being two things a push can send and no way for either to hold one. A file the app serializes is stripped where it is made (`noteFileContents`), whatever part of the note the NUL was in. A `source` kept verbatim came through one of two doors: a pull, where a file holding a NUL is refused before it is a row, or `importNoteFile`, which drops it on the way in. In front of both, neither editor's document ever holds one (`editor/noNul.ts`): it is dropped in the transaction that brought it, so that what the editor reports is what the store keeps. Stripped only in the store, the save comes back as a body the editor never wrote, is taken for a change from outside, and what was typed meanwhile is saved as a conflict copy of the user's own note. `saveNoteBody` and `createNote` strip as well, as the backstop. **And it is said.** Each such file is kept per connection with the cursor — `syncState.unreadable`, its `remoteId` and the path it was last read at — and the storage panel lists them by path under the sync status, with what to do about it: save it as UTF-8, or delete it. Without that a clean note goes from the device with nothing said. A record is a `PullChange` (`unreadable`, `forget-unreadable`), so it commits with its batch and cursor or not at all, and only a change to the list is one: a file listed already at the same path is read again and nothing is emitted, so `pulled` counts a file when it is first listed, when it is renamed and when it is let go of, and not every time the feed names it. A note moved aside because such a file has its name rides on the record (`movedAside`) and is said in that notice — "a note of yours had that name; it is now at …" — and not as a conflict, which it is not: nothing was edited twice and no copy was made, and the conflicts line is gone by the time the user wonders about the new name. Every note the file has moved aside is kept, not the last of them, and the list keeps saying so when the file is later renamed, since nothing else ever explains the name. A file stops being listed when it reads — by its id, or by its path, which covers a tool that saves by writing a new file over the old name — or when a note this device already holds is renamed onto its path; when the same id turns up as something that is not a note, or is hidden; when its own entry finds it gone; when a deletion names its id, or, naming only a path (Dropbox), names its path; and when a rescan does not return its id — except a rescan that may be missing things (`uploadDifferences`), which proves nothing gone. Nothing clears the list when a rescan *starts*: an interrupted one would leave the notice blank. A rename is the same id recorded at the new path. A folder's move carries the paths under it along and a folder's deletion drops them, in the store, because a feed that reports a folder alone says nothing of what was in it; a deletion of a folder this device holds no row for drops them in the engine, whether or not it also carries an id, so long as it names a path. A path-only folder deletion is **not** taken at its word for what is under it until the engine has ruled out the other half of a move, or a rename told as `old path deleted, folder listed` would forget files nothing in the round lists again; where it is a move, a deletion naming a file at its old path is read against where the folder went, so the file is forgotten only when nothing in the round says it moved too. A deletion naming a folder by **id alone** (Graph, for a folder it can no longer place) says nothing at all about what was inside it, so where this device holds no row for that folder its files stay listed until a re-scan does not return them — a notice left standing for a path that is gone, which is the cost of not guessing at a deletion's reach. With a row, the `delete-folder` takes them as it takes the notes. A push that meets such a file lists it too where the conflict names the file and its path; where the file is known only by the note's id (`runWrite`, `followTheRename`, a note's own file behind another's name) it is left to the next pull, which reads it and lists it where it is. **The list is a notice and nothing else.** No decision reads it: with no row, every entry for such a file is read again, so a list that is stale, or lost, costs the user a line of text and never a file. A file already imported lossily before this rule is not looked for.
- **A batch sees the notes it has itself created.** A file created, deleted and re-created at one path inside one cursor window arrives as three entries, and each of the last two has to know what the ones before it did: the deletion is about a note only this batch has made, and the second file lands on a path only this batch has filled. The store can say nothing about either — none of it has been applied — so the decisions already taken are read back as rows.
- **A path can be reused.** A note is identified by `remoteId`; the path is a fallback, and it is what lets a note created here be recognised when its own first push comes back. The one note the fallback must not claim is one whose own remote copy is alive elsewhere in the batch: that note has been moved and the path merely reused, and claiming it would hand two notes each other's contents. Nor, found by a model of two devices syncing at random over every provider (`tests/sync/overProviders.test.ts`), four more, each of which hands one device's file to a note that is not its note:
  - *a note the user has renamed onto the path*, not pushed yet — its file is still at the old name, and claimed it forgets that file, which the feed has no reason ever to mention again;
  - *a note whose own file is still there* — unmentioned because unchanged, so this is a different file that took the name. The batch usually says when the note's file went (and a full scan, which never says what was removed, is taken on trust); when it says nothing, since a provider need not report the deletion of a file replaced at its path, the provider is asked by id;
  - *a note the user has deleted here*, when the batch has removed it — written back under its id, the new file is still a deleted note, and the queued delete takes it from the remote;
  - *a note never pushed, deleted here or clean, whose bytes and frontmatter `id` are not the file's* — the store reports a deleted note clean, and claimed, its queued delete has a file to aim at. It moves aside instead.

  A deletion is matched the other way about — by id when it has one, and by path only when it has not, since a deletion whose id we have never seen is about a file that is not ours. By path, it is not about a note the user has renamed *onto* the path (often this is this device's own delete of the note that had the name, coming back) but about one renamed *from* it, whose file was there when the rename was queued — ahead of a note at the path that has never had a file, but behind one that has. Another device may have moved that file on since, and the queue still names the old path, so the note found this way is let go of only if the provider says its file is gone.
- **A note moved aside does not take the old name of a rename queued here.** The file is still there until the rename runs, and the rename may be queued behind the moved note's own write, which then conflicts with it on every push.
- **An id in a file is adopted only if nothing else holds it.** The `id` in frontmatter is what makes two devices agree which note a file is, so it is adopted by default. But duplicating a file is an ordinary thing to do in a folder the user can see, and the copy carries the original's id: adopting it blindly writes the copy over the note it came from, unpushed edits included, and leaves the two files fighting over one row on every sync afterwards. The second file to arrive is a new note.
- **An id names a note within its connection.** The id in a file is whatever the remote says. A folder copied from one account into another, or an account connected a second time after its notes were copied elsewhere, brings files that name notes a different connection holds. While `notes` was keyed by `id` alone that was one key space for every connected source: adopted, the store had to refuse the write (taking the row would take the other account's unpushed edits), identically on every retry, so the cursor never moved; and the workaround — asking the port whether the id was held elsewhere and naming the file's note afresh — had two connections each writing their own id into a shared file, turn about. So the key is `[connectionId + id]` (schema versions 4 and 5), as `folders` was always keyed, and the question is not asked: another connection's note of the same id is another row, neither shown to a store nor in its way. IndexedDB cannot change a store's key, so the rows go out to a second store in one version and back in the next, inside the single `versionchange` transaction an open gets; a failure leaves version 3 untouched, and a tab still running the old build is stopped by the stale-tab gate rather than reopening against it. Every lookup by id says which source: the store functions take a connection and default to the one showing, the editor names the note's own, and the push queue's per-note lookups filter by connection. State the UI holds across renders — autosave's held edits, the deleted-note notice, "this note needs raw mode" — is keyed the same way (`noteRef`). An edit or an undo that arrives after its note's source was let go finds the row where it was if the remote had not been sent it (a detach keeps those in place), follows it if a reconnect has since taken it home under a new connection id (`store/movedRows.ts` remembers this tab's moves, new id included; a move made from another tab is followed by id), is kept as an unsent note under the source made again if the row was removed with its source (the remote has the *note*, not the edit — `detachConnection` marks nothing in `store/deletedHere.ts`, whose marks are only the user's own deletes, and only under the binding they were made under: `SyncStateRecord.boundAt`), and is **never** looked for under the source showing, nor by id under any other connection than its own — only a note of the device's own pile is, since the pile's rows move once, into the first source bound, and a bind from another tab is not in `movedRows`, which with two sources connected is another account: found there, the text would be uploaded into storage it has nothing to do with. A note that has to be made again goes to its own source, brought back detached if it has gone (`ensureDetached`), and never to the device's own pile. Rows change connection only in a bind, which is a delete and an add; two notes of one id can meet there (a detached source's rows going home to a connection that has already pulled the same file), and the one arriving is given a fresh id, its queued ops with it, and is otherwise the row it was.
- **One entry per file, keeping the last.** Dropbox documents that a path may appear more than once in a batch and that the last entry is the current state. Decided twice against the same pre-batch store, one edited note produces two conflict copies wanting the same path — which the store cannot tell apart, and the push then writes one over the other and gives them one remote id. Deletions and live entries are keyed apart, both by id, because a file deleted and another created at that path in one batch is two things happening, not one thing said twice. Only files: a feed that tells a round in order (`B` renamed to `A`, a file moved into `A`, `A` renamed to `C`) needs the first rename for the file to land anywhere real, and a folder decided twice is a move from wherever the first decision put it. A deletion with only a path is kept each time too — `C` deleted, `A` renamed onto `C`, `C` deleted again is two folders — and the second one is about whatever the batch has put at the path since, not the folder the first took.
- **A rename need not re-list what is inside it.** The children's bytes did not change, so a provider may report a renamed folder as the folder at its new path plus the old child paths as deleted, with nothing at all about where the children went. An id-less deletion of a folder the batch has alive elsewhere is that rename (unless the batch has since put a different folder at the path, which the deletion is then about). One *under* such a folder is ambiguous: a file deleted before its folder was renamed reads exactly the same. Dropped, the note is carried along and held over a file nobody has; taken, a file the provider never listed again is lost here. So the provider is asked — a note's file by its id, a folder by listing where the rename puts it — and only "not found" lets go. The provider answers for now, not for where the round ended, so neither a missing parent nor a listing without the folder is taken as proof: the folder goes only when none of the notes under it is found by its id, and those not found are let go of.
- **A round is one batch.** From a stored cursor every page is read before anything is decided, and the round is decided once and applied with its cursor. Graph asks for exactly that, and page boundaries fall anywhere: between a folder's deletion and the move of a subfolder out of it, whose cascade would take the subfolder's clean notes; between a folder's two renames. The decisions already reason about a batch as a whole, so a round over many pages gets the answers one page would. The cost: a failure on any page redoes the round from the stored cursor (as a failure before the first page always did), and one round's decisions, note contents included, are held in memory until it is applied — rounds are normally a few changes, and an import of thousands on another device is one round too. Deciding stays near the round's size squared rather than cubed: what the store said is kept with the decision that asked, and a note's place is replayed from its own changes and the folders' rather than from every decision. Two thousand new notes in one round decide in about a second in the tests, and a test holds the store reads to a few per note. A path already in normal form is not split again to be compared, which was most of the cost of a renamed notebook re-listed note by note. A scan keeps applying page by page with no cursor until its last, since it reports no deletions until `reconcile` and a first sync of many notes shows as it arrives.
- **A folder's deletion waits for what the round moves out of it.** `C` deleted, and later in the round `C/A` moved to `B` (or up to `C` itself): the subfolder's last entry is decided first, then `C` goes from wherever that left it. Outermost first, and each entry is decided again in its own turn, which replays the round's history from where the rescue put the folder. Folders only — a note moved out has an entry of its own that finds the note by id, and a note with unpushed edits decided twice would be copied aside twice. A folder moving up to take its parent's name is moved out of a parent displaced aside, never deleted with it. The same holds when the deletion is reached early, clearing the way for a folder made at or moved onto the doomed folder's path. A subfolder whose own entry is the decision that reached the deletion — two folders deleted, each one's subfolder moved to the other's name — cannot be decided again, and is moved out beside the folder for that decision to move on.
- **A folder arriving where another is leaving.** A new folder at a path whose folder the round goes on to move or delete gets that folder out of the way first, as a folder move does; merged into one row, the move that follows would carry the newcomer off with the other's notes. Where the one in the way is the folder the arrival is moving out of (`Z/X` moved up to `B` while `B` is renamed to `Z`), the arrival is asked where it is again after the displacement. A folder that is not mentioned again stays merged, as before.
- **Two notes meeting at a path neither ends up at.** A folder rename can land a note on a path another note has just arrived at, when the round goes on to rename the landing note elsewhere. Displacing either leaves a conflict copy of a note that never conflicted, so the landing note is left to its later entry.
- **A conflict copy is named against the folder the note ends up in**, not the one it came from, and avoids every name the batch is bringing in, every name already in the store, and every name the batch has already chosen — one entry can need both a displacement and a conflict copy, and both are named from the same path. Two devices syncing on the same interval conflict inside the same minute, so the copy one of them made arrives in the very batch that decides to make the other; landing on the same name overwrites the edit the copy exists to save. Naming it against the old folder is the same bug in a different direction — the old folder may be one this batch is deleting.
- **A full scan reconciles, folders included — and only once it is all in.** A scan says what exists, never what was removed, so after a `CursorResetError` every note deleted while the cursor was dead would come back, and a notebook deleted then would sit in the sidebar for ever with nothing behind it. Notes and folders carrying a `remoteId` the scan did not mention are treated as remotely deleted; anything never pushed is left alone. Two things make this the most destructive rule in the file. It runs on the last page only, because no page before it has seen everything and reconciling against one would delete nearly the whole store — and the pages after would put a note back at each path, so the app would look right and every note would be a different note. And it exempts whatever the same batch has just re-established: a file replaced at one path while the cursor was dead leaves the row carrying the *old* `remoteId`, which a scan that only saw the new one never mentions.
- **A scan sweeps up only what the batch has not already settled.** Reconciling names the notes a scan never mentioned, and a `delete-folder` in the same batch names none of the notes it cascades over — so without asking where each note stands once the batch has run, the sweep deletes them a second time.
- **The app folder is never a folder row, and never a folder change.** Several providers report the root as an entry of its own — Graph's `delta` returns the root item. There is nothing above it to hold a row, and a row for it would be reconciled away after the next cursor reset as a folder the scan did not mention. Since every path is within the root, that one `delete-folder` is every note on the device. Guarded where the row would be made and again where it would be deleted.
- **A deletion of the app folder itself is ignored.** An adapter that reported the root by mistake would otherwise wipe every note on the device in one batch, and if the folder really is gone it is the connection that needs attention, not the notes.
- **A note that changed while it was being pushed stays dirty.** The outcome handed to the store carries the exact bytes that were sent, and the store clears the flag only if the note still holds them. Otherwise the last thing the user typed is marked as saved and never sent.
- **A failed push stops the queue rather than stepping over it.** The queue is ordered because later ops depend on earlier ones — a write into a folder whose `mkdir` failed would land nowhere, or resurrect a folder on a provider that creates missing parents. An op that has failed five times is surfaced rather than retried.
- **Same bytes, new version is not a conflict on the push side either.** An interrupted push looks exactly like one: the write reached the remote and the store could not be told before the tab closed, so the op is still queued carrying a version the remote has moved past. Conflicting would hand the user a copy of the note they already have.
- **The op that hit a conflict is finished, not re-queued.** Its content is preserved in the copy; replaying it would overwrite the remote with the very bytes the user has just been handed a copy of. Only a `write` is answered this way: a `move` that finds its target occupied and a `mkdir` that finds a file in the way carry no two versions of anything, and resolving them would point the note at somebody else's file. They fail, and stop the queue like any other failure.
- **A push that finds nothing at the path asks whether the file merely moved.** `write` is addressed by path, so a file renamed remotely reports exactly what a deleted one reports, and §7's answer to a deleted file — re-create it — would leave the user with two notes where they had one. The engine reads by `remoteId` first; if the file is gone it re-creates, and if it is still there it asks *who* renamed it. A remote rename is left for the next pull to rebase. A local one — the user edited and then renamed, so the queue is a write and then a move — can never resolve itself: no pull will move a note over a rename the remote has not heard of, and the ordered queue cannot reach the `move` while the `write` in front of it is failing. The queue is what tells the two apart, so it is asked, and the rename is performed there and then.
- **A move whose file is gone is finished, not retried.** Nothing will make it succeed, and failing it blocks the ordered queue for ever over a rename — the least of what the user has waiting behind it. The note keeps its contents, and the pull that reports the deletion cuts it loose or takes it away.
- **A transient failure is a status, not a rejection.** Offline, a 500, a store that could not commit: the batch rolled back and the cursor did not move, so `pull` answers `retry` exactly as `push` does. That covers every store call, not just the batch — reading the cursor and reading the queue are store calls too. Rejecting instead would make every caller wrap `sync()` in a `try` to discover something `status` exists to tell them, and one that forgot would take the app down on a flight.
- **A locally deleted note keeps its row until the remote copy is gone, and every read sees it.** The queued `delete` carries a note id and nothing else; the `remoteId` it needs lives on the row, so the row *is* the tombstone. A store with a `deleted` flag and filtered indexes is a natural reading of "every live note", and it loses a note the first time one is deleted here and edited on another device: the pull cannot see the row, mints a second note at that path, and the queued delete then removes the file that was just imported. Where both happen in one window the delete wins — the row is written back by the pull and purged by the op behind it. That is a decision, not an accident: the delete is something the user did, and the remote change may be their own from the other device.
- **A push is addressed by where the note is now.** A pull between queueing an op and running it rebases the note and leaves the op's own `path` behind. Invisible where `remoteId` identifies the file, and the whole address where it does not (WebDAV, deferred).
- **A move with no target fails rather than being marked done.** It is a store that lost the column, not a move with nothing to do, and completing it would discard the user's rename with nothing said anywhere.
- **Nothing is reported that did not happen to the user.** A deletion that matches no note and no folder we hold — a PDF beside the notes, a file never imported — is not news, and counting it puts a number in front of someone for an event that was never about them.
- **A folder move clears the notes in its way, not just the folder.** A cascade keeps a dirty note and merely cuts it loose, so a deleted folder can leave notes behind at their paths with no folder row above them. Moving another folder onto that path then drops its notes on top of theirs: two rows at one path, which the sidebar shows twice and which the next push has overwrite each other for ever. The local note is displaced to a conflict copy — the remote keeps the path — at whatever depth under the destination it sits.
- **A folder deletion says which folder, not which path.** Two drags in one cursor window name one path and mean two folders: delete `A`, rename `B` onto `A`, delete `A`. Matched by `remoteId` where the provider gives one and by the row that was at the path where it does not, and answered with the position that folder ends up at once the decisions in front of it have been applied. A deletion dropped here is dropped for ever, because the cursor moves on and nothing says it again.
- **Two files deleted at one path are two deletions.** Keyed by `remoteId` rather than path, so a file replaced and then removed inside one window does not fold into a single event that lets go of only the second.
- **An entry is not matched by path to a note the batch has already moved.** A folder rename carries every note under it and the feed says one word about the whole subtree, so the store still shows the note at its old path. A different file arriving there would otherwise be written into it, while its own file goes on existing under the new name. A note the batch merely *removed* is still matched: it has nothing of its own left and becomes the arriving file, which is what keeps one note rather than two when a path is reused.
- **A `move` that reports not found asks which end was missing.** A provider answers the same way for a file that is gone and for a destination folder that was never created, and a note dragged into a notebook made on this device hits the second every time — nothing queues a `mkdir` for a folder that has only ever been moved into. The folder chain is created and the move retried; only a genuinely missing source finishes the op.
- **A conflict discards the losing edit's queued write.** That op carries the content the copy now holds, and the note itself holds the remote's bytes. Replaying it puts the remote's own content back under a new version, which every other device pulls as a change that changed nothing — and which can lose a race against a real edit made in between. The user's rename is left queued: the conflict rule is about content.
- **A rescan names the outermost vanished folder only.** `delete-folder` cascades, so naming a nested one as well is a second delete of a row the first has already taken.
- **A rescan names a vanished folder by where its row ends up.** A scan is one batch like any other, and a `move-folder` decided in front of it has already rebased the row; naming the pre-batch path deletes nothing and leaves the notebook the remote no longer has in the sidebar under its new name.
- **A note the rescan only moved aside is still a note the rescan did not find.** Moving ours out of the way for a file arriving at its name says nothing about the file our row holds — a scan can do that without ever mentioning it. Exempted from the reconcile on the strength of the displacement, a clean note whose file is gone keeps its row and a dead `remoteId` until the next scan, and what the user is left with meanwhile is a conflict copy of a note that never conflicted — a scan being the only thing that can put it right, and one that need not come for weeks. So the exemption covers what the batch wrote back or took away, and a note it merely displaced is asked after like any other: its own file among what the scan returned is what keeps it, and nothing else. A dirty one is cut loose and keeps its edit, as everywhere else. **Not on a rescan that uploads**, and not because absence proves less there — that rescan acts on absence all the time, by sending the note back up. It is sending a *displaced* note back up that is wrong: `reupload-note` strips the row and queues a create-only write at the note's path, which by then is the fresh conflict name the displacement gave it, so the create cannot fail the way it would at the note's own path, where a file that was there all along conflicts and puts itself right. It simply lands, and the user has two files where they had one.
- **Every batch-aware question about notes includes the ones the batch has moved by name.** A folder is not the only thing that carries a note somewhere: a `move-note` brings one in from anywhere at all, and its row is still at the old path in the store. Missing it means nothing is displaced when a second file lands on the same name — two rows at one path, which the sidebar shows twice and the next push has overwrite each other.
- **A write that finds nothing makes the folder before re-creating the file.** A provider answers not found for a missing file and a missing parent alike, and the second is the ordinary case of a notebook deleted on another device while a note inside it had unsaved work: the pull keeps that note and cuts it loose, leaving nothing on the remote above it. Without this the write fails identically on every attempt and the ordered queue strands every op behind it, for every note.
- **A cascade leaves the notes it keeps a notebook to be in.** `delete-folder` takes the folder rows on the way down but not the dirty notes, so the rows a surviving note needs are re-established — at the end of the batch, because whether a note is still there is not known until the batch is over.
- **A rename the user has queued is not undone by our own echo of it.** The feed cannot say whose rename an entry describes; the queue can. Moving the row back undoes what the user just did in front of them and frees the path they renamed *to*, so a file arriving there in the same batch is imported rather than displaced and the queued move then conflicts on that path for ever. The version is still adopted; only the path is left alone. `followTheRename` asks the same question from the push side, and only about a queued move whose target is where the note now is.
- **A push conflict over a file another note already holds is not that note's conflict.** The path is simply taken, by a file whose own row is elsewhere because its rename has not been pulled yet. Adopting it would give two rows one `remoteId` — `noteByRemoteId` hands back one of them and the other is stale for ever. The note moves aside instead and its write is retried where it now is — unless it has no file of its own left to stay bound to, in which case its edit goes up as a new file at the new name in this drain, as it does for a file that cannot be read. **Either way the name is asked of the remote, not of the store alone**, which has never heard of the file another device set *its* edit aside to in the same minute. Where the note's edit is being written, the write is the asking and a refusal moves on to the next name. Where the note stays bound to a file of its own there is nothing to write — the path belongs to somebody else's file and ours may be perfectly good — so each candidate is read for instead, at a request apiece on a name that is almost always free at the first ask. Without it the retry meets that file, steps the note aside again from a name that already carries a suffix (nothing strips one back off), and leaves `x (conflict …) (conflict …).md` behind having spent a second of the op's five attempts with the ordered queue stopped. A read by path is no more proof than a listing is on a provider that hides what the app did not make (§5.1); what it settles is the case it is for, since the file in question is one another device of this app wrote.
- **A queued rename onto a path the remote will not give up lands beside it.** A `move` is not a `write`, so the conflict rule has no second version to reconcile, and nothing will ever free that name: left queued it fails on every attempt and strands every op behind it over a rename. The remote keeps the path and the rename takes a conflict name, where the user can see what became of it.
- **A directory the user's notebook left is removed by an op of its own, and only when five things agree.** The notes' moves and deletes go up first; the `rmdir` behind them carries the folder's `remoteId` as the queue recorded it. It finishes without deleting anything unless all five hold: the provider's listings are the whole truth about a folder (`listsEverything` — see the bullet below); it has that id at all — without one the folder it is about cannot be told from whatever holds the name now; the store has no folder row at the path and no live note at or under it — the user made the notebook again, or a pull brought it back, and it is a folder to keep; the parent's listing has a *folder* at that path whose id is the one recorded — a folder renamed or replaced elsewhere is not ours to remove, and only the id says which it is, since the name alone is the same either way; and a walk of the folder finds no file anywhere beneath it, hidden files and files this device has never pulled included. The walk goes one subfolder at a time and stops at the first file: it is the only walk in the engine whose depth the user chooses, and in parallel a deep notebook would put an unbounded number of listings at the provider at once. Not found at any step is finished rather than retried: the folder is already gone.
  - The row check is exact where the note check is "at or under" because every path that makes a folder row makes its ancestors too (`ensureFolderChain`, and the memory store's `putFolder`), so a row under the path cannot exist without one at it.
  - **Known gap:** a file written into the folder between the walk and the delete goes with it. That lands in the provider's trash or recycle bin on all three, and on Dropbox in deleted files, so it is recoverable — but this device will not report it.
  - **Known gap:** a notebook deleted while its own `mkdir` is at the network leaves the directory behind. The answer arrives to a store with no row at that path, so the id has nowhere to go and no `rmdir` can name it. It shows up as an empty notebook after a re-scan.
- **A folder is removed only where a listing can prove it empty.** Deleting a folder takes everything under it, seen or not, so the `rmdir` above is refused outright on a provider whose `list` is not authoritative: `StorageProvider.listsEverything` is false on Google Drive, where `drive.file` shows the app only the files it made and a PDF the user dropped into the notebook through drive.google.com is invisible (§5.1). There the directory stays, as it did before the op existed, and the notebook can come back empty after a re-scan — the cost of not trashing a file the app cannot see. True on Dropbox and OneDrive, which give the app its own folder and everything in it.
- **A dead `rmdir` is given up on rather than surfaced.** Every other op that runs out of attempts stops the queue and asks for help (the ordered-queue rule below), because what is behind it depends on it. Nothing depends on an `rmdir`: it tidies an empty directory away, and an empty notebook nobody asked for costs the user nothing next to every note they write from then on waiting behind it. So at the limit it is completed, and the directory stays.
- **A folder this device is removing is not made again by our own echo.** A sync pulls before it pushes, so the round after a notebook's deletion routinely carries the `mkdir` this device's own push landed, reported as a folder that exists — which re-creates the row, and the `rmdir` behind it then finds the store holding the notebook and finishes without removing anything. A folder change is dropped when a queued `rmdir` holds its `remoteId` *and* names the path the entry is at. Scoped to the path, because the same folder renamed by another device meanwhile is a notebook to keep at its new name, and a folder that device made fresh at the name we are removing is not the one the queue is about.
- **A folder deletion with no id is not about a notebook the remote has never heard of.** Dropbox reports a deletion as a path and nothing else, this device's own included — so the round after an `rmdir` lands carries the deletion of a name the user may well have made a notebook at since, which is the ordinary sequence of deleting a notebook and making another with the same name. Matched by the path alone it deletes the row the user has just made and cascades over what they have put in it, while the `mkdir` queued behind it makes the directory again, and the two fight every round. A row with no `remoteId` is one no `mkdir` of ours has landed on, so no deletion of ours can be about it — strictly, a row `ensureFolderChain` made for a directory the remote does have is id-less too, and is now beyond the reach of a path-only deletion until a pull reports the directory and gives the row its id; the alternative, deleting by name, is the notebook-the-user-just-made case above — and nothing else at that path can be either: whatever the batch has put there arrived after the deletion was recorded.
- **A notebook the remote no longer has does not take the notes whose files were never in it.** A note is in a notebook here as soon as the user moves it there; its file moves when the queued `move` runs, which may be days later if the device is offline. Another device removing that directory meanwhile is reporting something true — the directory is gone — but it says nothing about a file that was never inside it. Cascaded over, the note's row goes with the notebook while its file stays on the remote with nothing here naming it, and since the cursor has moved past that file nothing mentions it again: the note is gone from this device until a re-scan. So a `delete-folder` carries the notes the cascade must leave alone (`keep`), read from the queue — the same place that says which renames are the user's — and a rename left in the queue makes the directory again at the far end when it runs, as every push does. A note whose file *is* inside the directory is taken as before. Found by the two-device soak, at seeds 378, 427 and 591 of 600.
- **A notebook gone before its `mkdir` was sent withdraws it.** Queued and sent, that `mkdir` makes a directory on the remote that this device can never ask to have removed: the row it would read the id onto is gone, so no `rmdir` can name it, and the next pull that reports the directory makes the notebook again, empty — the very thing the `rmdir` exists to prevent. So a delete or a rename withdraws every queued `mkdir` at or under the path it is leaving, and a notebook renamed twice before a sync sends one `mkdir`, for the name it ended at. The notes' own ops stay: a note in there may have been moved out rather than deleted, and a write that finds no parent makes it.

- **A rate limit is not an attempt.** An op stops being tried after five failures, and a provider refusing every request while a quota resets would spend all five in half a minute on an op there is nothing wrong with — the user's note, blocked, with every op behind it waiting. A `RateLimitError` says nothing about the request, so the engine reports it as a retry without counting it, on the pull side as well as the push side. Everything else is counted, including a 5xx: it may be the request. The same goes for a rate limit met while *resolving* a push conflict — reading the remote entry the conflict rule needs is a request like any other — so the resolution's own error, not the conflict that led to it, decides which branch the failure takes.
- **Known gap: a rate limit that never ends is never *named*.** Nothing counts an uncounted retry, so a provider that answers 429 for ever leaves the op retrying for ever — every five minutes at the least, since the wait is the longer of the backoff (capped at five) and the provider's own answer (capped at fifteen) — and the status says `retrying` with the provider's message rather than naming the op that is stuck behind it. Retrying for ever is the *right* answer while the limit is real: the op is fine and the provider will serve us again. What is wrong is only that it is never named, which matters most for the cases that do last — Drive's daily quota, or a full Drive answering `RESOURCE_EXHAUSTED` with no reason we can read. An attempts-ceiling (after N rate limits in a row, count the next one) is **not** the answer and is deliberately not built: it would block a note over a quota that was about to reset, which is the worse failure. The answer that fits is the one `blocked` already uses — a "throttled since" clock beside `blockedSince` that, after some minutes of consecutive rate limits, publishes `attention` with the op named, without ever touching `attempts`. That closes the visible half and leaves "a rate limit is not an attempt" intact. It is not built yet because nothing in the phase needs it and the threshold wants a real quota to calibrate against; it goes on the live-check list.
- **The provider's own answer for how long to wait wins, but never shortens the wait.** A `Retry-After` is the only informed answer to when the remote will serve us again, so the scheduler waits for it — but takes the longer of it and its own backoff, since a one-second `Retry-After` on the fifth failure in a row is not an invitation to come straight back. Capped at fifteen minutes: Drive's daily quota says a day, and a device asleep past any horizon the user can make sense of looks broken. Coming back sooner costs one request refused the same way, and the wait starts again from what it says then. The cap is also the ceiling on what a *misread* header can ask for, which is the half of its job that is easy to lose: `parseRetryAfter` (`packages/core`) takes the longer of two values `Headers.get` has joined, and `Date.parse` will make a date out of most things, so a malformed `Retry-After` can cost fifteen minutes and never more. Anyone weighing raising the cap, or dropping it, is weighing both.
- **A tombstone owes the remote its delete and nothing else.** `queueWrite` refuses to queue one for a deleted note, and `queueDelete` withdraws the writes already queued for it. Both halves matter, and the second was missing: a note made and deleted before either op was sent still had its write run, so the file was created and then removed. That is only waste while the path is this device's own — but a path is not. Another device that made a note of the same name meanwhile finds a file there when its own write runs, binds its note to that file rather than making one, and loses it when the delete behind it lands. Nobody deleted that note, and it is gone from every device. A queued **move** is not withdrawn: the file is still at the name it had, and while every provider the app syncs to deletes by id, the queue is not the thing that should be deciding that. A write already at the network loses its queue row only, which is what `completeOp`, `failOp` and now `resolveConflict` all tolerate: the file it creates is still recorded on the row, so the delete has the `remoteId` it needs.
- **A stuck op is named, with the path the user gave it.** "Some changes could not be sent" leaves the user with nothing to act on, and the queue is ordered, so the first op out of attempts is also why everything behind it is waiting. The status carries that op — what it was doing, the path (a rename's destination, which is the name the user is looking for), how many attempts, and what the provider said — and the panel offers to open the note it is about, where the note is still there. There is no "discard": dropping a queued write leaves a dirty note that never syncs.
- **A rescan that uploads.** A scan says what exists and never what was removed, so reconciling treats a note it did not return as deleted. That is right when the provider's copy is the authority — but a provider can say it is not. Graph's `resyncChangesUploadDifferences` means "Upload any local items that the service didn't return", which is what a server-side restore answers, and there the scan looks exactly like a user who deleted everything: trusted, it deletes every clean note on every device that syncs after it, quietly, and the words are gone. So a `CursorResetError` carrying `uploadDifferences` starts a rescan that **infers no deletion from absence**. Each note the scan did not return forgets its `remoteId`, `remoteVersion` and `syncedHash`, is marked dirty and is owed a `write`; each notebook the store had bound to a remote folder forgets its `remoteId` and is owed a `mkdir`, outermost first and ahead of the writes this rescan queues. Not ahead of every write: a *dirty* note's write was queued when the user typed, so it has a lower `seq` than anything here and still makes its own parent through `runWrite`'s not-found recovery, which this does not make unreachable. This is the one place a pull marks a note dirty, against §3's rule that only a user's editing transaction does: the row genuinely is ahead of the remote now, and the unsynced dot the sidebar paints on it is true until the push drains. A deletion the scan *proves* still stands — a file it listed that is gone by the time the engine reads it is a positive answer, not an absence, and is still forgotten. A note the user deleted here is left alone entirely: its tombstone is reported clean, so the scan names it for reupload, and the store declines — it owes the remote its delete and nothing else, and forgetting the `remoteId` would leave that delete addressed at nothing and the file back on the next pull. A notebook the store holds with **no** `remoteId` is not named either: the reconcile asks only about folders bound to a remote one. An empty local-only notebook therefore stays local-only, as it was before the rescan; one with notes in it is made by the writes of the notes inside. Forgetting all three matters: a write against a `remoteVersion` for a file that is not there is refused, and a kept `syncedHash` says these bytes are already up, so nothing would ever send them. No folder cascades, since the notes inside are named one by one — the cascade exists to stop notes floating at a path with no folder, and here neither is going anywhere. A note the scan *did* return with different bytes needs no special case: a clean note's bytes are what it last synced, so the remote's are the newer ones, and a dirty note takes the conflict rule as always. The flag survives an interruption for free — the stored cursor is left in place, so the next pull meets the same refusal and is told the same thing.
- **Reading everything again is offered, with what it costs said first.** A cursor the provider has lost, or a store that disagrees with the remote about what is there, is otherwise a dead end the user cannot get out of. "Re-scan from scratch" drops the cursor and gives every op its attempts back, in one transaction so a scan cannot start against a half-reset queue, and keeps `rootId` — it is the same folder. The confirm says what a scan means: notes the provider no longer has are removed here too, unless they hold edits that have not been sent.

**Renames of notes holding unpushed edits, on providers with file ids.** A note renamed remotely *while it holds unpushed edits* arrives under a new path, and — on OneDrive, whose `eTag` changes on a move — a new version too, which on its own reads exactly like a remote edit. So every note records `syncedHash`, the `contentHash` of the bytes it and its remote file last agreed on: set by every pull that writes a note (`upsert-note`, and a conflict's remote side) and every push that lands (`pushed`, whether or not the user typed meanwhile — the remote holds what was sent), passed on `adopt-version` and `move-note` (read afresh when the version moved, carried over when it did not), and dropped with the remote (`detach-note`, a deleted folder's dirty notes, a copy into another account, a note brought back from a pull's delete, a note restored while its delete was in flight). A dirty note whose remote file's bytes hash to it — read at the version the feed named, since a read that answers with another version proves nothing about that one — was not edited over there: the engine follows the rename (`move-note`) or takes the version (`adopt-version`), the edit stays dirty and goes out against the new version, and no conflict copy is made. A note with no hash — rows from before it existed — cannot say, and takes the conflict as it always did, so nothing is migrated. WebDAV is not helped: its `remoteId` is the path, so a rename arrives as a deletion and a new file, the dirty note is detached and re-created on push, and the renamed file becomes a second note — nothing is lost, but the user sees two. The engine computes every hash and the store only writes it, since a Dexie transaction cannot wait on `crypto.subtle`.

**Search is a question, not a place.** Every note is already on the device, so search is answered here and nothing about it goes near a provider or `apps/api`. Not by Dexie either: IndexedDB indexes whole keys and their prefixes, so it can find a title that *starts with* what was typed and nothing else — a word in the middle of a body is invisible to it, and a scan for a substring would rank nothing and miss "meetings" for "meeting". So the words are indexed in memory, by MiniSearch, over the title, the tags and the body, with the title and the tags weighted above the body. Prefix and a light fuzziness are on, because the last word is still being typed and a plural is not a different question; a second word narrows rather than widens, since that is what typing more means. The index is built when a search opens, follows the notes while it is open — it is fed from a live query, so a note edited in another tab moves in the results — and is emptied when the field is: the words of every note are a second copy of the corpus, and carrying one for a feature nobody is using is a cost nobody goes looking for. Rebuilding costs one pass over the rows, and a row whose indexed fields have not moved is left alone, so a keystroke costs the search and not the corpus — the search, and at most fifty excerpts, because a short query can match every note there is and each answer walks a body and renders a row. The list says when it is showing fifty, so the answer to a list that is cut short is another word rather than a scrollbar.

Two things the highlight has to get right, both of which were wrong first. It marks the words *the index* matched, not the words that were typed — a prefix or a fuzzy hit means the two differ, and marking what was typed leaves the actual match plain — and it marks them longest-first and only where a word begins, or `meet` paints itself inside "meeting" and `he` inside "there". The query is cut into words by MiniSearch's own tokenizer rather than by a rule of ours, since a query split differently asks for terms that were never indexed. What is dropped from it is a one-letter *piece of a word the tokenizer broke up* — the `t` of "don't", the `e` of "e-mail" — which is a letter nobody typed as a word, and which with prefix matching on matches most of the notes there are and most of the words inside them. The unit is the chunk the user typed, and that distinction is the rule: dropping every one-letter word instead made "plan b" return exactly what "plan" returns, against the promise two sentences above that a second word narrows, and made a single-character CJK word unsearchable beside any other. And the excerpt is centred *tightly* on the match and wraps over a few lines rather than being one clipped line: the column is a little over forty characters wide, so a generous run-up put the highlight reliably past where the line clips — the one thing the row exists to show, off screen, with every test still green, because jsdom has no layout.

**The answers hang from the field, and choosing one ends the search (2026-09-23).** They used to take the notes pane over — and, in a compact window, the notes dropdown — which left the notebook the user had been reading hidden behind a query, and a chosen answer left the query standing, so the field stayed active and the pane stayed a search until it was emptied by hand. Now `SearchField` is a combobox with its own listbox, the pattern the command palette already uses: the cursor stays in the field, the arrows move the highlight, Enter opens the highlighted note, a press on a row opens that one, and Escape or a press outside puts the list away. On a wide screen the list is a card under the field; in a compact window it fills everything under the bar, as the compact panels do — the first version of search in a narrow window capped the list at 14rem and gave it 60dvh, which left the result count at the mercy of the viewport's height, two of four on a 320×568 SE, and filling the space has none of that arithmetic. Choosing an answer opens the note, empties the field and takes the focus out of it, and in a compact window gives the bar back to its dropdowns, so a phone's keyboard goes with the list. The notes pane is only ever the open notebook's notes, and making a note no longer has to clear a search to be seen in it.

**The layout follows the window, in two steps, and everything inside it follows its own room.** Wide, it is three columns: 15rem of notebooks, 19rem of notes, and the note, with a 13rem outline inside the note view. Below **1250px** the two side columns narrow together, as `clamp()`s whose `vw` terms meet their full widths at exactly 1250px, so the note keeps the room it would otherwise lose. Below **60rem** the window is compact: the source tabs and the `+` become one dropdown — the sources as a list at the top, and the storage panel (what is syncing, and the way to disconnect) and the providers to connect another account at the foot, as the storage panel sits at the foot of the sidebar — the notebooks and the notes become dropdowns beside it showing the open one's name cut to fit, the search becomes an icon that takes the bar over while it is in use, and the rich editor's toolbar is hidden until the note's `Format` button asks for it, and then sits below the note, where the thumb is, with its menus opening upwards. All three fill the window under the bar and scroll inside themselves: a panel sized to its content left a strip of note beneath it, too short to read and easy to press by mistake. The notebook and note dropdowns are not copies of the columns: they are the sidebar and the note list themselves, positioned as a panel under the bar and kept mounted while shut, so the notebook menu and a move's destinations work in a compact window without a second implementation. The storage panel moves from the sidebar's foot to the source dropdown there, since that is the one about storage — and the palette's commands that live in those components still find them. The widths are decided in one place, `components/layout.ts`, and reach the stylesheet as `.compact` on the frame rather than as a media query of its own, because the compact width also decides which bar is *rendered*, and two answers to that question could disagree by a pixel and show the sidebar as a column and a dropdown at once. A test holds the stylesheet to having no width media query. Renaming a source is the one thing a compact window does not offer; on a tab it is a second press on the name, and a menu row has no room for the name to become a field.

**Inside the window, each part goes by the room it has, not the window's width.** The same window gives the note very different room with the columns beside it and without them — a 1000px window leaves the note 35rem beside the columns, and a 900px one, compact, leaves it all 56 — so a rule keyed to the window hid things that had room for them. What only changes how something looks is a container query: `.note-view` is a container, and its header keeps to one row — the path narrowing first and going below 36rem, the title taking a row of its own below 20rem. The header's controls are icons, to cost the title as little as they can: the outline and the compact `Format` toggle are pressed while what they show is shown, the two editors are a pair of tabs with the one in use pressed — a single button named for the mode it was in read as the mode it would switch to — and moving and deleting the note are in a `Note options` menu at the end, the same `OptionsMenu` the notebooks' header uses, with the outline's toggle just before it (2026-09-23): what it opens is the note's, at the right-hand edge as the menu is. **The outline is a flyout where a rail would cost the note too much (2026-09-23).** It used to be not offered at all below 36rem of note, which was every phone. There, and in a compact window on a touch screen, it now opens over the editor from the right instead of narrowing it, shut until asked for, and shuts again once a heading is chosen, on Escape, on a press anywhere else, or on opening another note: it covers what it is for. On a touch screen a jump scrolls to the heading and leaves the caret alone, since focusing the editor raises a keyboard over it. Each keeps its name for a screen reader and in its tooltip, and each is the title's 1.75rem high, so the header's bottom rule still meets the pane headers' beside it.

**Spacing is a handful of variables, and density is setting them.** `styles.css` builds every inset from `--space-*` steps and three variables blocks agree on: `--gutter`, how far a block's words sit from its sides; `--bar-block`, above and below the words of a header bar; and `--row-block`, above and below a row. Every block that holds words takes its inset from `--gutter`, so the words line up down the screen however many blocks they cross — the note's title over its first line and over the toolbar's first label, a pane's heading over its rows, the first tab over the notebooks' heading — and a bar that starts or ends with a borderless control pulls its padding in by that control's inset (`--control-inline`), so it is the words or the glyph that sit on the gutter, not the control's invisible edge. A compact window sets `--gutter` and `--bar-block` tighter on `.app-frame.compact`, and a note narrower than 36rem sets its own `--gutter` tighter in `@container note`; the bar's height stays, so its rule still meets the pane headers'. Tests hold the blocks to the variables. What is on — a pressed toggle, the editor tab in use, a mark already applied — is `--on-bg` and `--on-fg`, in the accent, rather than a darker grey than hover: a grey only a little darker than hover is not told apart from it while the pointer is still over the toggle. Hover lights only under `@media (hover: hover)`, since on a touch screen `:hover` sticks to the last thing tapped and a toggle just turned off stayed lit; keyboard focus is a ring outside the control, in the accent, apart from its state. What changes what is rendered, or what a control says it is doing, is measured (`useElementWidth` in `components/layout.ts`), since a container query has no answer a component can read. The outline starts open beside a note 53.5rem wide or more (the room a 1400px window gave it beside the columns), starts collapsed below that — an `Outline` button in the header, and a palette command, away — and is not offered below 36rem, where the rail would leave the note narrower than itself; once the user has pressed it either way it stays as they left it for the session. The compact bar shows the search as a field beside the dropdowns once the bar is 40rem wide, and as an icon that takes the bar over below that. The formatting toolbar keeps to one line at any width: what does not fit goes into a `More tools` menu at its end, least used first — the code block, the indentation, the rest of the inline formatting, the task list, the link, the lists, italic, bold — and the text style never, since it says what the cursor is in. Widths are measured on the bar and remembered once a control has gone, so the bar knows when one would fit again without drawing it to find out.

**A finger gets 44px (2026-09-23).** An audit on a touch phone and tablet found almost every control sized for a mouse: the editor's tabs 24px, the header and pane icons 28–32px, menu, slash-menu and list rows 30–35px, the code-block tools 24px, the task boxes 15px. Where the primary pointer is coarse (`@media (pointer: coarse)`, at the end of `styles.css`), each is at least `--tap`, 2.75rem, both ways — Apple's 44pt and WCAG 2.5.5 — by setting `--control` and `--control-inline` from it and giving the rest a `min-height`. Grown in place rather than given invisible hit areas, since most sit shoulder to shoulder; the bars take `--space-2xs` above and below instead, and the note header's gaps close to it, so a phone's header still fits and the three headers still meet. Two things are smaller on purpose: a task's box is 24px (WCAG 2.5.8's minimum; a list's lines are closer than 44px apart) with the task's words stepped in to clear it, and a link inside a sentence is its words, which 2.5.8 exempts. A mouse keeps the dense layout at every width. Fields under 16px were raised to it, since iOS zooms into a smaller one on focus.

The query itself is deliberately *not* in the URL, unlike the open folder and note: those are where the user is and a reload should land there, while a half-typed query is not a place to come back to. **Known ceilings.** The corpus is read and indexed in the tab that searches, so a first search over a large library is one pass over every row — 3k notes of ~300 words index in about 150 ms on the reviewer's machine, which is the same order as the ~2k-note cold-start scan above, and it is revisited by persisting the index (or feeding it deltas rather than rows) if it ever shows. And the tokenizer decides what a word is, which leaves three things unfindable that look like words: it splits on `[\n\r\p{Z}\p{P}]`, so a **tab** is not a separator and `heron\tstood` is one term that neither half finds; a run of **CJK** is one term, so `東京` does not find `東京都に住む`; and a backtick is `Sk` rather than punctuation, so `` `heron `` keeps its backtick, is reached only by fuzziness, and carries it into the excerpt. All three are fixed in the same place — a tokenizer of our own, given to the index and to `wordsOf` together — and none is worth guessing at before somebody's notes show which matters.

**Commands are declared, not collected.** Every shortcut and every palette entry is one registration — id, label, chord, whether it can run now, and what to do — held in a registry the shell provides (`apps/web/src/commands/`). One list serves two things that must never disagree: the keyboard, which runs a command when its chord is pressed, and the palette, which is where a chord is *discovered*. A shortcut living only in a listener is one nobody can find; a palette entry with its chord typed into the label is one that goes stale the day the listener changes. Here both come from the same value, so they cannot drift.

Registration belongs to whoever owns the action. Switching a note between rich and raw has to flush the pending edit first, and what is pending is known only inside `NoteView` — a central list of commands would mean hoisting that state to reach it. So each screen declares what it can do and the registry holds the union. Declaring into a registry that is not there is allowed and does nothing, because a screen rendered on its own is not wrong for having nobody listening; *reading* the list without one throws, because `useShortcuts` and the palette exist only to serve a registry, and the shell is where a missing provider shows up.

The keyboard reads the registry when a key is pressed rather than subscribing to it. A command's `run` is a fresh closure on every render, so a component re-registers as it renders — and a subscriber that re-renders on registration is a loop: register, notify, render, register. Asking at the moment of the keystroke is also the only way to get the commands as they are *then*, which is what a shortcut wants.

A command that cannot run now stays visible and is shown as unavailable rather than disappearing. A palette whose contents move about as the user does cannot be learned, and "why is it not there" is a worse question than "why is it greyed out". Its chord is still swallowed: letting it fall through to the browser's own `Mod+N` would open a window, which is a stranger answer than nothing happening.

**A chord fires only when nothing else has a better claim on the keystroke.** Four questions, all in the one listener. Has something nearer already handled it (`defaultPrevented`)? CodeMirror's default keymap binds `Ctrl+K` to kill-to-end-of-line on a Mac and calls `preventDefault` while letting the event bubble, so without this the raw editor deletes the rest of a line *and* the app opens the palette over it — and the undo that would put it back is no longer reachable from where focus has gone. Is it an auto-repeat (`event.repeat`)? Holding `Mod+E` would otherwise remount the editor several times a second, each remount flushing a pending edit. Is a dialog up? While the palette is open every chord is held: a dialog is the app asking for an answer, and a shortcut that fires behind it acts on a screen the user cannot see. And is the chord *reachable* from where the keystroke landed — which is the bare-key question below.

**The chords are the ones a browser leaves alone.** `Mod+N` opens a window and `Mod+Shift+N` a private one, in Chrome, Edge and Safari alike, and the page is never asked, so "new note" is the bare key `n`. Printing a chord that cannot fire is exactly the drift the registry exists to stop — the listener and the label would agree with each other and both disagree with the machine. A bare key is why `reachable` is there: it is ignored inside an `input`, a `textarea`, a `select` or anything `contentEditable`, and that last case is the one that matters, because both of this app's editors are contentEditable hosts rather than form fields. An unknown modifier in a spec throws rather than being ignored: `parseChord('Ctrl+K')` read as the bare key `k` would fire on every `k` typed outside a field and print itself as `K`. Alt is asked the same question as a bare key rather than waved through with `Mod`, because on macOS `Option+<letter>` types a character.

What a bare key costs, and it is accepted rather than unnoticed: every button in the app is a place where `n` now means "new note" — focus the sidebar's "+" and press `n` and you get a note, not a notebook. That is the price of the only chord a browser leaves alone, and it is small: the surfaces where the key means the letter are exactly the ones `reachable` covers, and the app has no text entry that is not an `<input>` or a contentEditable editor.

Focus returning is decided by where focus *is* when the palette closes, not by whether a command ran. Asking the second was wrong for every command that does not touch focus — which is most of them — and those are the ones a user runs from the palette and then wants their place back.

**The palette is a dialog, and honours the contract it claims.** `aria-modal` says the rest of the page is inert, so focus has to agree: the field is the only thing inside that takes focus, Tab is refused, and the rows are `option`s with nothing focusable in them — ARIA gives `option` presentational children, so a button in there is announced as plain text while still sitting in the tab order, which is how focus escaped. Focus is returned to whatever had it when the palette closes, because removing the focused element does *not* put focus back: the browser drops it on `document.body`. Unless a command moved it deliberately — `app.search` exists to put the cursor in the search field, and taking it back would undo the only thing that command does.

`Mod` means Cmd or Ctrl and both are accepted wherever it is asked for — on macOS the Ctrl chord is free and on Windows the Meta one belongs to the OS, so taking both costs nothing and a browser reporting a platform we did not expect still gets a working shortcut. Only the *label* cares which keyboard it is, and it is allowed to be wrong: a wrong label is a smaller failure than a dead key. Chords without a modifier are ignored while the user is in a text box, or every one of them would be unreachable from the one place people spend their time.

### Getting a library out (2026-09-24)

**"Download all notes" writes the source showing as one zip of markdown**, from the palette (`app.download`) or the storage panel. It reverses §14 for export only (issue #133). That entry said export mattered more when the store was the only copy of anything, and for a device with nothing connected the store still is: no provider client to zip its folder, no other device to open it on, and nothing between it and a browser clearing its storage. For a source that syncs it is a copy of the folder without a trip to the provider's client, which costs nothing to offer, so it is offered there too.

The archive is the one the disconnect download already made (`store/exportNotes.ts`): each live note as `noteFile`, the bytes a push would send, at the path it would have, under `entryName`'s zip-slip-safe names with duplicates numbered. So it is the tree a push would make in the provider folder, and unpacking it into a newly connected account's folder gives the same notes back — which is why import needs no feature of its own. One addition: **an empty notebook is an entry of its own** (`name/`, no bytes, the MS-DOS directory attribute). A folder with a note in it is implied by the note's path; an empty one has nothing to imply it, and would be the one thing the user made that the archive did not give back. It takes its name before any file does, as every implied folder already did, so a file clashing with it is the numbered one. With no empty notebooks the bytes are exactly what they were.

The editors write what they are holding before the source is read (`settleEditors`), as they do before a disconnect's list: the store alone would leave out the sentence typed a second ago. A stored ZIP without ZIP64 stops at 65,534 entries and 4 GiB; `zipOf` refuses from there with an `ArchiveLimitError` naming which limit, and the user is told in words (`downloadProblem`) rather than handed a file that will not open. The panel hides the button while a later source's first import is filling it, when the archive would be whatever part had arrived, and while the disconnect question is open, which has a download of its own.

### Editor

Two modes over one markdown string. Default is rich text; a toolbar/shortcut toggle (`Cmd/Ctrl+E`) switches to raw markdown. The mode is remembered per note and there's a global "default mode" preference.

**Rich mode:** Milkdown (ProseMirror on top of a remark AST). Chosen because its document model *is* the markdown AST: parse/serialize are the core of the editor rather than an add-on, unsupported syntax stays in the tree instead of being dropped, and the same remark pipeline can serve as the normalizer in `core`. Presets: `@milkdown/preset-commonmark`, `@milkdown/preset-gfm`; plugins: slash, tooltip (inline formatting), history, listener, clipboard. React via `@milkdown/react`. Known trade-offs: smaller community, mostly single-maintainer, React bindings are functional rather than polished, majors have had breaking changes — pin the version. Fallback if maintenance state or React integration proves a blocker: Tiptap with its official markdown extension, accepting a lossier serializer and relying harder on the fidelity suite.

**Raw mode:** CodeMirror 6 with `@codemirror/lang-markdown`, same autosave path.

**Packaging:** the presets and plugins are taken from `@milkdown/kit`, the aggregate package Milkdown publishes, rather than as a dozen separately versioned dependencies. Same code, one version to pin — which is what "pin the version" was asking for.

**Menus.** The slash menu (`/`) and the floating selection toolbar are ProseMirror plugin views written in React, mounted through `@prosemirror-adapter/react` — the adapter Milkdown's own React examples use. The formatting toolbar across the top of the editor is not one of them: it sits above the text rather than over it, so it is an ordinary component beside `<Milkdown />` that reads the selection through a store the editor pushes to (`editor/format.ts`, Phase 7 polish). Both offer only constructs the fidelity suites already cover, so nothing reachable from a menu can put something in a note that the file format cannot hold. Picking a command is a user edit like any typed one: it removes the `/query` the user typed and marks the note dirty, which is the point.

**Empty paragraphs become `<br />`.** Markdown has no way to say "a blank paragraph here" — blank lines are separators, not content — so Milkdown writes an HTML break for one and reads it back as an empty paragraph. It is the one place the editor puts something in a file the user did not type. It stays because it is a bijection and loses nothing in either direction: stripping it instead would delete a `<br />` that came from the user's own file, which is the worse failure. Pinned by a test in `apps/web/tests/rich.test.ts`.

Only the shape it writes is read back that way: a paragraph whose one child is exactly `<br />`. Milkdown's own reader (`remarkPreserveEmptyLinePlugin`) took every `<br>`, in four spellings and anywhere in the note, and deleted it — `first<br />second` became `firstsecond`, and the fidelity check below rightly sent the note to raw mode. `editor/rich.ts` leaves that plugin out and puts a narrower one in its place, keeping the plugin's options slice, which is what the paragraph serializer asks for before it writes `<br />` for an empty paragraph. Every other break is the author's and stays in the document as an inline html atom — the same line `previewLines` draws below, for the same reason.

It is removed where it is *read*, not where it is stored. `previewLines` in `packages/core/src/markdown/preview.ts` is the one rule for turning a body into the lines a list can show — line-leading markers, task checkboxes, thematic breaks and setext underlines, a line that is only a `<br />`, whitespace collapsed, blanks dropped, and and a line inside a fenced code block keeping its markers — and both the note list's preview and the search excerpt are cut from it, so neither can find a different set of words in a note than the other. A preview is the worst place to meet the one thing in the file the user did not type: it sits in grey text beside their own words, looking like a mistake they made.

Only a *whole line* of it, which is the only shape Milkdown writes. A `<br>` inside a sentence is the user's own text — in prose, or in `` `<br>` `` in a note about HTML — and the first version of this removed the tag wherever it appeared, turning "She wrote `<br>` in her HTML lesson" into "She wrote in her HTML lesson". A rule for hiding what the editor added must not delete what the author wrote.

The note list drops the title from the front of those lines so the row does not print it twice, and it does so by comparing against the title rather than by taking line one. Position was wrong in both directions: a note beginning with the editor's `<br />` has no heading on its first line and lost a line of real writing, and a note whose heading follows an introduction had the introduction eaten instead.

It is a pass over a string rather than a parse, and that was measured rather than assumed. Running the real pipeline — `parse` plus `mdast-util-to-string` over the top-level nodes, which is the same markdown the editor reads and gets every case right — costs about a millisecond for a 300-word note, so about 52 ms for the fifty-one excerpts a search can ask for. That is the cost on the first keystroke of a search and again whenever a note changes under it; a cache keyed on `contentHash` would make the later keystrokes free, so the honest figure is 52 ms of jank at the moment a search opens rather than 52 ms per letter. It is still the wrong price for a line of grey text, and it grows with the note: a 3000-word note parses in 10.6 ms, so fifty-one of those is over half a second. The cheap pass costs 0.016 ms a note.

What that buys is paid for in syntax left on screen. Inline markup survives — `**bold**` keeps its asterisks, a link keeps its brackets and its URL, a table keeps its pipes — because removing it without a parser means guessing at the user's own punctuation. Two smaller things go the same way: a marker is stripped once, so `> > deep` reads as `> deep`, and a lone `=` line is read as a setext underline wherever it sits.

Fenced code is the exception, and it is kept rather than stripped. Inside a fence none of these markers is markdown: a `# comment` in a shell example is a comment, a `---` in a YAML sample is a document separator, and a `<br />` in an HTML example is the thing being written about. Stripping those is the same failure as deleting a `<br>` from a sentence. It needs no parser either — the body is split on fence lines, and the pieces alternate, so a piece's position says whether it is inside one. What a fence line is has to be exact: a backtick fence's info string cannot itself hold a backtick, and without that rule a paragraph opening with an inline code span is read as a fence, which loses the line *and* flips the parity so the rest of the note is read as code. A fence that is never closed leaves the rest of the note shown with its syntax intact, which is the right way for it to fail. Indentation inside a fence does not survive: whitespace is collapsed there as everywhere else, this being one line of grey text and not a listing.

The bias is deliberate and runs one way throughout: when in doubt, show the characters. A preview with a little syntax in it is a smaller wrong than one that has quietly deleted a word. If this ever needs to be better, the fix is that cached parse, not a longer regular expression.

**Not `@milkdown/plugin-listener`.** Its `markdownUpdated` is the obvious way to hear about changes, but it debounces on a timer of its own and, more importantly, hands over a markdown string with no way to tell whether a person or the app caused it. That is exactly the distinction the dirty rule is made of. A small ProseMirror plugin — the one in `editor/dirty.ts`, which reads transaction metadata — answers it directly, and the serialization happens where the answer is already known.

**Source-of-truth rules (these matter more than the editor choice):**
- The note record stores `body` as a markdown string. Neither editor persists its own document model.
- Frontmatter is stripped before the body reaches either editor and re-attached on save. Editors never see it.
- Switching modes serializes the current editor to markdown, updates `body`, and loads the other editor from that string. There is exactly one dirty-tracking path.
- A note becomes dirty only on an editor transaction that changes the document, never on load, mode switch, or re-serialization. Opening a note in rich mode and closing it must not rewrite the file. This prevents normalization churn on notes authored by other tools. A change another plugin makes in answer to one of those — Milkdown's heading ids, `prosemirror-tables` squaring up a ragged table — belongs to whatever it answers: the app's after a load or an adopted body, the user's after a keystroke. Appended transactions are attributed by their root; a follow-up a plugin dispatches for itself carries nothing to say what it answered, so edit reporting is held for the length of the app's dispatch and while the view is built (`editor/dirty.ts`). Counted as the user's, such a change is an edit nobody typed, carrying the origin of the body just replaced — and it saved as a conflict copy of any pulled note with a heading in it.
- A body adopted from outside (a sync pull, the other mode) is not undoable and empties the undo history, in both editors. The editor now shows a different document, and an undo into the old one would be reported as a user edit against the new body and pushed — quietly reverting what someone else wrote. Rich mode clears through the meta `prosemirror-history`'s own undo uses, since it has no public clear and rebuilding the state rebuilds every plugin view; a test pins the undo depth at 0 so an upstream change to that shows up.
- On first *user* edit in rich mode, the whole file is re-serialized through remark-stringify, so some normalization (list markers, emphasis style, blank lines) is accepted at that point. Configure `remark-stringify` for the most conventional output: `bullet: '-'`, `emphasis: '*'`, `strong: '*'`, ATX headings, `fences: true` with language tag. Use the identical options in `core`'s normalizer so editor output and test expectations agree.
- Anything the rich editor can't represent (raw HTML blocks, footnotes, unknown syntax) must survive round-trip as an opaque block rather than being dropped. If the parser can't guarantee that for a given note, open it in raw mode with a banner explaining why. Checked per note against the editor's own parser and serializer before the user can type, because ProseMirror's schema is a narrower model than mdast and is where a construct would actually be dropped — `core`'s remark suite cannot see that. The comparison (`sameMarkdownStructure`) reads a line ending just before inline html as a space, because that is how `mdast-util-to-markdown` writes it — deliberately, so the html cannot be read back as a block — and the two render the same; without that, a `<br />` on a line of its own failed the check in both `core` and the editor. **The banner says what, and where** (`components/unsupported.tsx`): the check answers with the first node of the note the editor's document lacks (`firstStructuralDifference` in `core`, `whatIsLost` in the editor), and the banner names it and its line — the line of the body, which is what raw mode shows, frontmatter being stripped before either editor sees it. A type it has no word for is described as markdown, as before. **And the lock lifts on the user's say-so, never by itself.** Once the body is not the one that failed — typed into, or replaced by a pull — the rich tab is offered again; pressing it (or `Mod+E`) settles autosave, reads the stored body back, and mounts the rich editor only once that body is the one on screen, so the check runs on what the user just wrote rather than the version before it. The mount check then runs as it always does, before anything can be typed, and a note that still fails is back in raw mode with nothing written. Typing never lifts it: the editor must not change under the user mid-sentence. Reference-style links are the one construct known to fail today — Milkdown writes them back inlined and drops the definition. Nothing in the corpus fails it today.
- A body arriving at a mounted editor is loaded only when it is genuinely new and did not come from that editor. Autosave is debounced, so the note's stored body is always a little behind what is on screen; reloading the editor from it — when the save echoes back, or on any re-render that happens to carry the same stale prop — silently deletes everything typed since. This is the rule with the sharpest teeth in the editor layer and it has its own tests.

**Fidelity test suite** (`packages/core/tests/markdown/roundtrip.test.ts`): a corpus of markdown fixtures — CommonMark spec samples, GFM tables/task lists, nested lists, code fences with languages, hard breaks, HTML blocks, files from Obsidian/iA Writer/Bear exports. For each: `serialize(parse(md))` must equal `md` after both sides pass through the same normalizer, and `parse(serialize(parse(md)))` must be structurally identical to `parse(md)`. And none of it may depend on how the file's lines end: the parser folds them first, so a note written on Windows is the same note. It did not, and the carriage return remark left inside a soft line break made every CRLF note fail the fidelity check in §7 and open with the banner saying the rich editor could not show it. Because Milkdown uses remark, `core`'s `pipeline.ts` wrap the same remark plugins the editor is configured with, so this suite exercises the editor's actual pipeline headless in CI. Add a second layer that mounts Milkdown in jsdom/Vitest browser mode and round-trips through the editor instance itself.

Title is derived from frontmatter `title`, else the first `# ` heading, else the filename.

## 8. PWA specifics
- `vite-plugin-pwa` in `generateSW` mode to start (switch to `injectManifest` only if a custom worker becomes necessary): precache app shell, `NetworkOnly` for `/api/*` (never a cached answer: binding follows what `/api/connection` says, see Phase 2), `NetworkOnly` for provider API origins, `registerType: 'prompt'` with an in-app "update available" toast.
- Manifest generated by the plugin: standalone display, icons, `share_target` (later) for "share to notes".
- Dev: enable `devOptions.enabled` so the SW runs under `vite dev`; `wrangler dev` serves the API on `:8787` and Vite `server.proxy` forwards `/api` to it so cookies stay same-origin. Prod is genuinely same-origin (SPA served as Worker static assets).
- All note data lives in IndexedDB; the app boots and renders from local state before any network call.
- Tokens: keep provider access tokens in memory (React state) with a copy in IndexedDB `syncState` so a reload doesn't force a backend round-trip. Never in localStorage.
- Installability is a checklist the browser applies silently — a missing 192px icon or a bad `start_url` and the install option simply never appears, with nothing in the build to say why. The manifest and Workbox options live in `apps/web/pwa.ts` rather than inline in `vite.config.ts` so that checklist can be a test (`tests/pwa.test.ts`), down to reading each icon's real dimensions out of its PNG header.
- With `registerType: 'prompt'` the worker does not claim the first page load, by design: the page that registered it keeps running the build it was served, and the next navigation is the first one the worker controls. So "works offline" means from the second visit onwards, which is the only thing it could mean — the first visit is the one that downloads the app.

## 9. Security checklist
- PKCE + `state` on every OAuth flow; `state` bound to the browser that started it by the signed `__Host-skysa_flow` cookie, which also carries the device's credential hash (§6, "Per-connection credentials"). `/start` is a same-origin POST, so neither the hash nor `state` can be planted by a link.
- `SECRETS_KEY` only in server env; secrets table encrypted at rest. A device's credential is never stored at all — only its SHA-256.
- Authorization is a per-connection bearer, never a cookie, so nothing is sent ambiently and CSRF stops being a class of bug here. The cost is that IndexedDB has no `httpOnly`: a stolen credential works until the device is revoked. `script-src 'self'` is therefore a hard requirement rather than a good default, HSTS is set on the shell, `GET /api/connection/grants` makes a theft visible, `DELETE` makes it revocable, and a grant unused for 180 days expires on the next read. Revoking nulls the grant rather than deleting it, so the hash stays spent: a deleted row would free its hash for whoever holds the credential behind it — the thief being revoked — to claim against storage of their own (§6).
- HSTS on the static shell: `max-age=63072000`, with neither `includeSubDomains` nor `preload` — each is a commitment for whoever self-hosts (from an apex domain the first takes in every subdomain they own, for two years), and theirs to make; `docs/self-hosting.md` says how. The credentials are origin-bound in IndexedDB and the flow cookie is `__Host-`, so subdomains were adding little. Held by `tests/csp.test.ts`.
- A rate-limit seam (`createApp({ rateLimiter })`, no-op by default) on the two connect routes and `/api/token`, which are the endpoints that spend an outbound provider call per attempt.
- *(Only if WebDAV is built, §5.4.)* WebDAV proxy: allowlist methods, reject paths that escape the configured base URL after normalization, strip hop-by-hop headers, 30s timeout, 20 MB body cap.
- *(Only if WebDAV is built, §5.4.)* WebDAV proxy SSRF hardening (on by default; protects operators who expose their instance to the internet): HTTPS only; resolve the host and reject private/loopback/link-local/cloud-metadata ranges (10/8, 172.16/12, 192.168/16, 127/8, 169.254/16, fc00::/7, ::1); reject IP-literal hosts; re-validate on redirect (or disable redirects); per-user rate limit and daily byte budget. Self-hosters can relax the private-range rule via `WEBDAV_ALLOW_PRIVATE=true` for LAN Nextcloud.
- CSP: `connect-src` limited to self + `www.googleapis.com` + `*.dropboxapi.com` + OneDrive's `graph.microsoft.com` and its download hosts (`*.files.1drv.com`, `my.microsoftpersonalcontent.com`, `*.sharepoint.com`, §5.2) — each provider's hosts added with its adapter, never ahead of it (WebDAV goes through the proxy, so it adds none). Each run, one at a time per connection — a trigger mid-run asks for one more after it, and the run holds a Web Lock named for the connection, so a session ended mid-run and another tab cannot put a second engine at the network beside it (which is why every provider request has a 60 s deadline, `sync/providers.ts`: a request left hanging would otherwise hold the lock, and every tab's sync, for as long as the browser let it): offline does nothing until `online`; then `verifyResume` (every run, since it answers at once when there is nothing to check, and a re-bind to the same id may never show as a change), `ensureRoot` once per connection (`rootId` in `syncState`), then pull and, if the pull reached the end, push (`engine.sync`, split so `lastSyncAt` records the last pull that reached the end whatever the push did). A run the device was bound or unbound during — a store refusing with `UnboundConnectionError` or `UnverifiedResumeError` reads to the engine as a transient failure — is not shown; it is run again. Triggers are §7's less Background Sync: open, focus, becoming visible, `online`, every 60 s while visible (a hidden tab waits for `visibilitychange`), and 2 s after the last local edit, seen as a new highest op `seq` for the connection (a queued write covers later edits until it runs, and the store queues a fresh one for an edit made while it was in flight, so the seq is enough; the engine's completions and failures never raise it, and the ops a conflict or an in-flight edit queue cost one more sync). Access tokens come from `/api/token`, kept in memory and in `syncState` (`accessToken`, `accessTokenExpiresAt`, written with `update` so a connection let go of meanwhile does not get its row back) and replaced a minute before they expire; `expiresAt` is moved onto the device's clock by the response's `Date`, since a device clock hours out would otherwise mint a token per request. A provider `AuthError` gets one fresh token, then `paused` — before the engine runs (`verifyResume`, `ensureRoot`) as well as inside it. A server refusal to mint (`reauthorize_required`, `sign_in_required`, `not_entitled`, `not_found`) is not retried on a timer and is not asked again inside the same run; the status says `attention` with the refusal, and the next trigger tries again. The refusal is forgotten as soon as a token is had from anywhere (another tab's, in the row) or the server fails to answer at all, so it never outlives what it describes. Transient failures retry after 5 s, doubling to 5 min — and while a retry waits on its timer, edits, focus and visibility leave it to that timer (only "Sync now" and `online` go first), because every failed push is an attempt against its op and a keystroke's debounce would otherwise spend them all in seconds — reset by a sync with nothing left failing that time can fix (`ok` or `blocked`); a failure that finds the browser offline reads as `offline`. Conflict copies accumulate in the status for the session, whichever sync made them. `blocked` is `attention`, but pulls go on every minute, and it is not for ever: the engine counts every failure an op has, an outage's included, so an op gets eight (about ten minutes of the backoff), and a blocked op gets its attempts back when the user presses "Sync now", on `online`, and on its own fifteen minutes after it first blocked. *How connecting works:* the server is the authority on whether an account is connected, and the device follows. On open the panel asks `/api/connection` with the credential this device holds, which reaches exactly one connection: a credential a flow has just consented for claims that connection (`claimConnection`), and otherwise the binding the device already has is confirmed, and let go of only on `credential_revoked` or `not_found`. A signed-in empty list unbinds (it was disconnected from another device), but no session changes nothing: an expired session is not a disconnect, and the panel offers "Connect again", which keeps the connection's id for the same account. Offline, the panel shows what the device is bound to. Disconnect asks the user first and the server second, and the device lets the source go only once the server has (or no longer has the row); letting go first and failing to reach the server would leave a live refresh token that the next open binds to again. The connect button is a navigation to `/api/auth/connect/:provider/start` with `returnTo` set to the current URL, and the callback's `?connect=` outcome is shown once, then taken out of the URL. Only storage-first instances offer it: account-first needs the sign-in of Phase 9. The old `/auth/callback` route is gone, since the API owns the callback. Because binding follows the server's answer, that answer must be current: the service worker never serves `/api/*` from a cache (an hour-old list replayed after a disconnect would bind the device again), and nothing else may store one either: every `/api/*` answer says `Cache-Control: no-store` and the client asks with `cache: 'no-store'`, since before that no answer carried any freshness information at all — no `Cache-Control`, no `ETag`, no `Last-Modified` — which leaves an HTTP cache to guess, and the same replay would unbind a live connection or hand back a revoked access token. A connection row the app cannot parse fails the list rather than reading as no connections (only a provider it has no adapter for is left out), and a bind or unbind decided from an answer runs only if the device has not been bound or unbound since the question went out (a count in `prefs`, `sync.bindings`, bumped by every bind and unbind, since the connection itself can come back to where it was), checked in the bind transaction — otherwise the server is asked once more. Disconnect is disabled until the answer on open is in. When disconnect is refused for want of a session (possibly after the server let go and the answer was lost), the panel offers to stop syncing on this device alone. `safeReturnTo` in the API checks the path as resolved, so `/.//evil.example` cannot become a protocol-relative redirect. *How binding works:* the app shows and writes exactly one connection, the one `syncState` row (or `LOCAL_CONNECTION_ID` when there is none), and every store reader and writer not told a connection resolves it — each writer inside its own transaction, so a write cannot land under a connection a bind has just replaced. Binding moves every row onto the new connection in one transaction, cut loose from any file it had, dirty, with `source` pinned, a `mkdir` queued per notebook and a `write` per note; the old queue and cursor go, and a tombstone is dropped (its delete was owed to an account nothing is sent to now — not true when the same account is connected again, below). Disconnecting touches nothing remote. (Until 2026-09-19 it moved the rows back to `LOCAL_CONNECTION_ID` the same way; it now removes what the remote has, and what the remote was never sent is the user's to keep, move or discard, asked before anything is said to the server — §6, "Letting a source go".) A sync still at the network when the connection changes writes nothing: the Dexie `SyncStore` refuses every write once its connection has no `syncState` row, checked in the transaction binding locks, since a late cursor would otherwise put the old row back and make it the app's connection again, with every note under another. Rows under two connections that spell a notebook two ways (`Work`, `work`) move onto one spelling, the target's if it has one. *Reconnecting and switching accounts* (the follow-up to the connect UI, `accountId` end to end): a connection id is not an account — disconnecting deletes the server row, so the same account connected again gets a new id — so `/api/connection` returns the provider's `accountId`, and the device keeps it on the `syncState` row, which outlives a disconnect whenever anything is kept (`detached`). Disconnecting keeps what the remote has not been sent — each such note's `remoteId`/`remoteVersion`/`dirty`, the tombstones it is owed and the queued ops — under the source's own id, where the user has not asked for it to be moved to another source or discarded by name; binding the account of a detached source *resumes*: the rows and their queue move over unchanged and only the cursor is new, so the first pull is a full scan that sees edits, renames and deletes made on either side while disconnected, and nothing is re-uploaded or turned into a conflict copy. Binding any other account takes nothing from a detached source: its rows stay where they are, a source of their own, because the likeliest way to get there is picking the other of two logged-in Dropbox accounts on the consent page, and notes that belong to one account are never copied into another unasked. (There was a prompt for it, `other-account`; it went with the pile it asked about.) The device's own rows — written before anything was connected, so no account's — are *copied* into the first source bound: cut loose, dirty and owed a write as above. Clicking Connect was the asking. A row that has to change path on the way (only when rows already sit under the target) is copied even when resuming, since its file is at the old path. A resume trusts the first scan to say what was deleted while the device was away, and an app folder emptied or replaced in that time looks the same to a scan — every unedited note would be deleted here. So a resumed bind that carries remote ids is marked `resumeUnverified`, the Dexie `SyncStore` refuses every write for it, and `verifyResume` must run first: it reads up to eight of the notes' own files by id, the most recently edited of each notebook in turn, at any depth, loose notes as one (so one notebook deleted elsewhere cannot stand for the folder). One found and the resume stands, whatever the others said. None found and none failing, and the rows are copied instead (cut loose and written back). None found but some failing — offline partway, rate limited — and it throws and the flag stays, to be asked again: half an answer does not decide a copy. The one way that can hold sync up is a file that always fails while every other sample was deleted elsewhere; the scheduler shows the error. Notes deleted elsewhere across every sampled notebook can therefore turn a resume into a copy, which brings them back — the safe direction. A device bound before the API named accounts learns its account on the next reconcile. A source detached before its account was named is resumed only by its own connection id coming back: with no account to compare, no other bind takes its rows. A notebook moved or renamed locally drops its `remoteId`, since a full scan would otherwise read the id at the old path as a remote rename and undo it (the old notebook reappearing empty remains the Phase 6 gap). A note deleted here while disconnected, however long, still wins over edits made to it elsewhere (§7). The scheduler (next PR) must stop the old engine on every bind and unbind, call `verifyResume` before a connection's first push or pull (the flag stops the store recording results, not the provider calls), refresh the token if it fails with an `AuthError`, re-reconcile the account panel when another tab changes the binding, and not show `UnboundConnectionError` or `UnverifiedResumeError` retries as a sync failure. Two things the connect flow must guarantee, because the store refuses rather than guesses: no note row may be left under a connection other than the one being synced when its notes can reach the remote — the store refuses to pull a file over another connection's row with the same frontmatter `id`, and since the engine decides the same way on every retry, sync stops there until the rows are moved — and rows moved off `LOCAL_CONNECTION_ID` get `source` pinned as they move, so their bytes stop depending on `updatedAt` and path before the engine ever reads them. A deleted note's queued `write` and `move` ops are kept, not dropped: a write already at the network when the delete lands may be the one creating the file, and dropped, the store would never learn its `remoteId`, the delete would purge the row with nothing to remove, and the file would come back on the next pull. The connect flow must also queue a `write` for every rebound row the remote has never had — notes made before connecting have no ops, because nothing queued any until this PR — and a `mkdir` for every notebook.

Fixed by saves that carry the origin of the body they were typed into (§7, "Edits the editor has not saved yet").

### Phase 6 — Sync hardening
- Conflict rule implemented and tested for every provider. `packages/core/tests/sync/overProviders.test.ts` runs two devices — each an engine over its own store and adapter, sharing one remote — over the fake in both folder modes and each adapter over its wire stub (each at one entry per page as well): the §7 rule for an edit on both sides, an edit against a delete each way, an edit under a remote rename, two `Untitled.md`s made offline, a conflict found by the push, and a copy reaching the other device; then 120 seeded runs of random creates, edits, renames, deletes and syncs, after which both stores must equal the remote and every edit must be in some file unless a delete may have taken it. It found ten ways two devices stopped agreeing — two where a note deleted on one device took the other device's new file at its name and its queued delete then removed that file, the rest a note kept on one device whose file was gone, or a file taken by the wrong note — each fixed with a test in `engine.test.ts` (§7, "A path can be reused" and the bullets around it). **Known gap (issue #123):** a second rename of a note sends its `move` to the back of the queue (`store/queue.ts`), behind a note the user has since made at the old name. That note's write finds the file still there, so the push moves the new note aside to a conflict name (§7, "A push conflict over a file another note already holds") and answers `retry`; the next sync writes it there. Nothing is lost, but the note the user just named is renamed.
- Rename/move handling, folder rename cascading. A notebook renamed or deleted here goes up as its notes moving or being deleted one by one, as it did, with one `rmdir` op queued behind them for the directory they left (`store/folders.ts`, `store/queue.ts`); a `mkdir` that lands now records the folder's `remoteId` (the `made-folder` outcome, where before only a pull set it), which is what lets that `rmdir` say which folder it means, and one withdrawn before it was ever sent leaves no directory to remove. So on Dropbox and OneDrive the old directory no longer stays on the remote, and a notebook renamed or deleted here no longer comes back empty on the next pull (§7, "A directory the user's notebook left", "A folder is removed only where a listing can prove it empty", "A folder this device is removing", "A folder deletion with no id", "A notebook gone before its `mkdir` was sent" and "A notebook the remote no longer has"). Making the notebook again withdraws the `rmdir`, at its path or above it. **On Google Drive the directory stays**, and the notebook can still come back empty after a re-scan: `drive.file` hides files the user put there themselves, so no listing can show the folder is empty and deleting it would trash what the app cannot see. Review found five ways the first cut of this went wrong, each now tested: the Drive blindness above; a notebook made and then deleted or renamed before its `mkdir` was pushed leaked a directory nothing could ever remove, and came back as an empty notebook; this device's own id-less folder deletion, coming back on the next round, deleted a notebook the user had made again at that name and cascaded over what was in it; a notebook moved up into the notebook it was in left its directory behind; and an `rmdir` for a directory the provider kept refusing stopped the queue, so every note written afterwards waited behind a tidy-up. The two-device soak then found a sixth, on the pull side rather than in the op: a directory removed on one device took, on the other, the notes whose files had never been in it, because their renames into it were still queued (§7, "A notebook the remote no longer has"). **Not done, deliberately:** a single "move the folder" op. Note ops queued ahead of it would run against a folder that has not moved yet, and reordering the queue is the riskiest change on offer here — so a rename is still N requests for N notes, and other devices see N moves rather than one rename.
- Retry/backoff, poison-op surfacing, "reset connection" (re-scan from scratch). Backoff and blocking were already there; what was missing was the provider's own answer, a way to see which op is stuck, and a way out. All three adapters now raise `RateLimitError` with the `retryAfterMs` the provider gave (§4) — 429 and Graph's 509, and never a 503, which is an outage the op has to be allowed to reach `blocked` over — the engine retries without counting it against the op, and the scheduler waits the longer of that and its backoff, capped at fifteen minutes. A `blocked` sync reads the first op out of attempts and the panel names it — "Dropbox would not take the rename of Work/Plan.md after 5 tries…" — with a link to the note where there still is one. "Re-scan from scratch" drops the cursor, resets every op's attempts and runs, behind a confirm that says notes gone from the provider are removed here too unless they hold unsent edits. It drops the cursor inside the lock a run holds, not beside it: a run already at the network writes its own cursor back when its round lands, and clearing outside the lock would put that cursor back after ours went — the re-scan silently never happening, since the run that overwrote it reports success (§7, "A rate limit is not an attempt", "The provider's own answer", "A stuck op is named" and "Reading everything again is offered"). **Not settled without credentials (issue #121):** the real `Retry-After` formats and Drive's 403 reason strings — an unreadable value falls back to the ordinary backoff, and an unrecognised refusal stays the transient error it is today.
- Apply a round of remote changes as Graph asks — the whole round decided and applied as one batch (§7, "A round is one batch"). `packages/core/tests/sync/randomRemote.test.ts` changes a remote at random underneath one device — files written, edited, moved and deleted, folders made, renamed, nested and deleted, a few at a time — and requires the store to equal the remote after every pull, over the Dropbox, OneDrive and Drive wire stubs, the fake in both folder modes, and the fake told as Dropbox tells it (§5.3), at one to three entries per page. After every pull each note must be bound to the file at its path, and the store must have forgiven nothing. CI runs 100 seeds, and 2000 pass. It found, besides the page-by-page cascade: both same-page orderings (a folder swapped with its own child, and a note displaced by a folder renamed onto it); a folder renamed twice in a round losing the first rename; a new folder merged into one the round moves away; a subfolder moved up to its deleted parent's name; id-less deletions under a renamed folder dropped (§7, "A rename need not re-list"); a second id-less deletion of one path dropped; deletions of something the round had already carried to that path dropped; a Drive page listing a file ahead of the rename of its folder; the in-memory test store forgetting a folder's id on an `ensure-folder` without one (the Dexie store keeps it); and the Drive wire stub hiding an edit to a file whose folder was renamed between two looks. Review found four more, each now tested: a folder renamed away and back with both old names deleted by path lost its notes; a doomed folder deleted to make room for a new one at its name took a subfolder the round moves out; an id-less deletion under a renamed folder was taken when the provider could not list the folder above it, or listed it without the folder, which may only have moved on since; and two deleted folders each receiving the other's subfolder lost one of them. The feed told as Dropbox tells it then found two in the fix: the folder above a deleted path was taken outermost first, so its place was looked for under a folder the round had renamed, and a folder the round carried to the deleted path counted its earlier entry, where it had been, as somewhere it lived on. Each has a test in `engine.test.ts`, `idTree.test.ts`, the store contract or `gdrive.test.ts`.
- A rescan that uploads rather than deletes what the remote did not return, when the provider says the remote may have lost it (OneDrive's `resyncChangesUploadDifferences`, §5.2). `CursorResetError` carries `uploadDifferences`, the adapter sets it for that code alone (§5.2), and `reconcile` then says `reupload-note` where it would have said `delete-note` and `reupload-folder` where it would have cascaded a `delete-folder`. Each forgets what the remote gave the row — a note its `remoteId`, `remoteVersion` and `syncedHash`, a folder its `remoteId` — and queues the `write` or `mkdir` that puts it back, so the next push creates the file afresh rather than writing to one that is not there. A *dirty* note needs none of this: `detach-note` already keeps it and its write already exists, and a note the user deleted needs the opposite — the store declines the reupload and leaves the tombstone its `remoteId`, or the delete behind it would have nothing to remove. No folder cascades, so every notebook is named and not the outermost only, and the `mkdir`s go ahead of the writes. Nothing is inferred deleted from a scan's silence, though a file the scan listed and the engine then could not read is still forgotten. **Not settled without credentials (issue #121):** the exact shape of Graph's 410 body, which is why the code is read from `innerError`, `innererror` and `details` alike and an unrecognised 410 takes today's path.
- Multi-device soak test: two browsers, edit same note offline, reconnect. `apps/web/tests/soak.test.ts` runs two complete instances of the app — two Dexie databases, two schedulers, an install id each, one remote — and makes every edit through the writer the UI calls, over the fake and the OneDrive and Drive stubs. "Offline" is `SchedulerEnvironment.isOnline` and the `online` event. Scripted: the item's own case (both edit one note offline, reconnect, and the remote keeps the path while the other edit lands beside it under a conflict name, on both instances, with the banner naming it); a notebook renamed and deleted; an edit meeting a delete; a rename made on the provider itself, which is the only way to reach the `syncedHash` rule from here; and both instances making a note of the same name at once. Then seeded runs of random work per remote — 40 in CI, and `SOAK_SEEDS` widens the search (600 has been run) — which must end with both instances equal to the remote, nothing dirty, no op stuck, no tombstone left, no notebook without a directory behind it, and every edit's token still somewhere — bar the ones a delete is allowed to take (§7). The *scripts* replay: the steps pick from notes and notebooks in path order, because Dexie answers by primary key and a UUID-keyed order chose different notes on every run, which made a failing seed unreproducible — the run that found the bug below could not be replayed from its own printed trace until this. The two instances are also let back onto the network *together* rather than one after the other: reconnected in turn, each run finishes alone, the two schedulers never meet, and the runs can only say that the stores end up equal — they lose every bug that lives in an interleaving, which is what they are for. But the *timing* is not pinned, and a seed is not a guarantee: two schedulers going at once are ordered by the event loop, and a conflict copy's name carries the clock. So a seeded failure is a lead, and the regression test it earns is written where the order can be set — at the engine, as `queue.test.ts` does for the one below. **What it found** (seed 39, on every remote): `queueDelete` left a note's queued `write` in place, so a note made and deleted before either op was sent still had its write run — creating the file and removing it again. Alone that is waste; where another device had made a note of the same name meanwhile, that file is what the other device's write bound its note to instead of making one, and the delete behind it took a note nobody deleted, from every device. A tombstone owes the remote its delete and nothing else — the rule `queueWrite` already applied from the other end — so the delete now withdraws the writes, and `resolveConflict` tolerates an op withdrawn while it was at the network, as `completeOp` and `failOp` already did (a contract test now asks both stores for that, and the in-flight write that earns the tombstone its `remoteId` has one of its own). A queued **move** is kept: the file is still at the name it had.

**What a wider search found.** Running 600 seeds rather than 40 turned up four things. One is the app's: `createFolder` refused a notebook whose name only a *deleted* note still spelled, because the check counted every note row while `listNotes` — and so the sidebar — leaves tombstones out. Removing a notebook and making one of the same name again, which this section says withdraws the `rmdir`, was answered "already exists" with nothing shown there, and offline that lasts as long as the device is away (seed 443). Two were the script's own fault. It excused a token a delete is allowed to take only when the deleted row carried a `remoteId`, so a note deleted *before* its create had ever been pushed excused nothing — while the other browser, which had pulled the same note and did have a file for it, went on writing edits into it that a delete may take; the script now also remembers the note's id, but **only for that case**, because §7's `detach-note` gives an id a second life and excusing by id after that would excuse every later edit of a note §7 promises to keep. And it asked for a notebook it had just checked was free while the scheduler pulled one of that name in between, which the store is right to refuse — the script now takes the refusal, and checks the name really was taken, so a store that refused *every* notebook would still be caught. The fourth was recorded here as **seeds 318 and 578 failing every time, and 253, 302, 461 and 597 sometimes**, all differing in a conflict copy's `updated:` line alone. That understated it, and a review on 2026-09-18 found what it was. Seed 578 left one browser clean and holding a note's body *without* an edit the remote and the other browser had; seed 461, intermittently and only over the OneDrive and Drive stubs, **lost edits outright** — four tokens in no file anywhere. Both were one fault: a move's returned version adopted over bytes nobody had read (above, "The version a move hands back"). With that fixed, all six seeds pass, over the fake and both stubs. They turned on timing — 578 passed over the fake on CI while failing on a laptop — which is why they are held by the scripted tests in `packages/core/tests/sync/overProviders.test.ts` rather than by pinning a seed: a pinned seed that fails only sometimes is a suite that goes red by itself.

The traces also carry where a rename or move went, and not only where it started: a rename onto a path the other browser is also using is how two notes come to share a name, and a trace that stops at the old path cannot show it.

### Phase 7 — Polish
- Search (local full-text over IndexedDB; MiniSearch). The field is at the right-hand end of the source bar, and it searches every source on the device and every notebook in them, not the ones showing; the answers drop from the field (they took the middle pane until 2026-09-23 — §7) and say where each match is: the source, when there is more than one, the notebook, and a line of the body with the matched words marked. The way to another account sits with the tabs, right after the last one, and the search takes the rest of the bar (2026-09-22). `store/search.ts` holds the index and never touches the database — it is handed rows and told to agree with them, which is what lets `useNoteSearch` decide when, and keeps the matching and the excerpting testable as the pure things they are (§7, "Search is a question, not a place"). Opening a match takes the user to the source and the notebook it is in — the source first, since the URL names the notebook and the note inside whichever source is showing — so the tabs, the sidebar, the list and the open note never disagree; Escape empties the field, and choosing an answer does too.
- Rich-editor polish: find/replace, outline panel. (Find and replace is one bar over both editors, and one engine under them: `@codemirror/search`'s `SearchQuery` decides what matches in *both*, because a shared bar whose two halves disagree about the count is worse than two separate bars. The package is used for that and nothing else — its own highlighter draws only while its panel is open (`if (!panel || !query.spec.valid)`), and its panel is the thing being replaced — so the decorations are ours on both sides. The rich half maps text offsets to document positions with a one-character stand-in for every inline leaf, since an image takes a position and no text. Stepping between matches never takes focus: an editor that took it would swallow the next keystroke, turning Enter-for-next into Enter-typed-into-the-note. Scrolling in rich mode is done by asking the match's element, not `tr.scrollIntoView()`, which walks up from the DOM selection — in the bar — and scrolls the bar. A replace is a user edit and marks the note dirty; finding and moving are not. Verified in Chrome in both modes, including the bar keeping its query across a mode switch.) (The outline panel is done: `headings` in core reads the note's markdown with the same parse the editor does, so a `#` in a fenced code block is not a section, and it reports a **line** rather than an offset because `parse` folds CRLF and offsets move with it. The rail lives inside `.note-view`, not as a fourth child of `.app-shell`'s grid. A click is sent by the class the open editor puts on its own root — not by trying `findFromDOM` first, which is the same thing today only because no Milkdown code-block component is installed, and would otherwise hand back the CodeMirror *inside* a fenced block. Raw goes through `findFromDOM` and `doc.line`, since a heading below the viewport has no element yet; rich goes to the *n*th top-level heading child, both walks being top-level-only and that being the whole agreement between them — and a heading carries its `ordinal` among **all** top-level headings, because an empty `##` has no row in the rail but is still an `<h2>` in the document. `note.outline` in the registry makes it a palette command.) (Image paste is in §14: it needs attachments, and attachments are in no phase, so it was sitting in a checklist as though it were scheduled.) (The `<br />` Milkdown writes for an empty paragraph is done: one rule, `previewLines` in core, now decides what a readable line is, and the note list's preview and the search excerpt are both cut from it — §7.)
- Keyboard shortcuts, command palette. One registry behind both (§7, "Commands are declared, not collected"): `Mod+K` opens the palette, a bare `n` makes a note, `Mod+Shift+F` puts the cursor in the search field, and `Mod+E` — which `NoteView` used to listen for itself — is now a registration like any other, so it appears in the palette with its chord printed from the same value the listener matches.
- Several connected sources on one device, each its own silo. Not the relaxation this line used to describe ("multiple connections per user"): there is no user to hold them. The device generates a credential per connection, keeps it, and sends the server only its hash; `storage_connections` is keyed on `(provider, account_id)` and `grants` on that hash; `sessions`, `holdsAnotherProvider`, `session_mismatch` and the `conflict`/`signin`/`occupied` outcomes are gone. §6, "Per-connection credentials", records what was decided and what was deliberately not done — including the XSS trade that `script-src 'self'` now has to carry.
- **The sources are tabs across the top, named for what they are (2026-09-21).** A device can hold several accounts at once and the only way between them was a list at the foot of the storage panel, which answered "switch me" but never "which of these am I looking at" — and the panes below mean something different for each, since every source is its own notes, notebooks, queue and cursor (§6). `SourceTabs` sits in the frame above `app-shell`, for the reason the grid's three children give, and carries everything `connectedSources` knows: the live sources, the detached ones — which hold work their remote was never sent and are editable, so a bar without them would be a bar that hides notes — and the device's own pile when it holds anything. The bar shows from the first source rather than the second, so the `+` is where it was last time instead of appearing only once the user has somehow reached two.

  **Names are short, derived, and the user's to overrule.** "Dropbox", and "Dropbox 2" for the next one of the same provider, numbered per provider in `boundAt` order with no 1 on the first; `renameSource` writes a `label` on the `syncState` row and that beats everything. This is a better answer to what the disconnect work left open below — the source list naming live sources by account id because `displayName` is only written while a source is in front — by not needing the server's name at all: `displayName` is still the server's, still overwritten on every reconcile, and a rename would have been thrown away by the next one. Derived rather than written down at connect time so that every source already on a device gets a name with no backfill, and so that letting the first Dropbox go leaves the other called "Dropbox" rather than a "Dropbox 2" with no 1 above it. The cost is a name moving under the user when another source goes, and renaming is the answer to it. Numbering counts renamed sources too, or typing a name would renumber the rest.

  A press on the tab already showing turns it into its own name, which is what makes the name part of the tab rather than a setting filed elsewhere — and is reachable from the keyboard for free, since Enter on a focused tab is that press. Enter takes it, Escape abandons it, blur takes it, and the field is focused *and* selected (`select()` alone focuses in a browser and not in jsdom, which is how a field that swallows the first keystroke ships). The pile has no row to write a name onto and so is not renamable, rather than accepting one and losing it on the next render. Clearing a name puts the derived one back.

  `nav` and `aria-current`, not `role="tablist"`: the ARIA tab pattern owes arrow keys, a roving `tabindex` and an `aria-controls` pointing at a panel, and the panel here is the whole application. "Disconnected" is in the words of the tab and not only in its colour. The `+` opens the providers this deployment offers, read through `useInstanceConfig`, which is one `/api/config` per client shared between the bar and the storage panel — `/api/*` is `NetworkOnly` and must stay so, so nothing below de-duplicates it. **Left:** the storage panel still names sources its own way, with the account id, which is the fuller answer where two accounts at one provider are in question; the two lists say different things about the same sources and one of them should give.
  **The storage panel gave connection management up entirely (2026-09-21).** The source list and every "Connect another {provider} account" are gone from the sidebar, and with them `Sources` and `sourceLabel`; the panel now holds only what is true of the source in front — how syncing is going, the devices holding its credential, and Disconnect — with Reconnect kept on a detached source, since that is how unsent work gets home rather than a way to add an account. That closes the **Left:** above by deletion: there is one list of sources now, and it is the bar. The panel with nothing connected says so in a sentence and points at the `+`, which means the bar shows before there is anything to switch between — it is the only place a connection is made. The panel's focus landing after a discard lost its last button with the list, so the frame takes `tabIndex={-1}` and is where the focus goes: not the bar's `+`, which belongs to another component and is how two of them come to fight over it. And the notebooks now scroll inside the sidebar rather than the sidebar scrolling as one, so the panel sits at the foot of the pane instead of at the end of the content, where twenty notebooks used to push it below the fold. At phone width, where the pane is capped at 14rem and there is nothing to divide, it goes back to scrolling as one.

  **Two things the tabs got wrong, found by moving the tests onto them.** A source whose row no longer names a provider — one brought back by a late save (`ensureDetached`) — was named "This device", the same as the device's own pile, so a device holding both showed two tabs of one name; the pile is now told by its connection id and the other is "A source". And a tab's accessible name was left to be assembled from its two spans, which the name-from-contents rules do not join the way `textContent` does: the name is said outright with `aria-label`, in exactly the visible words.

- **Notebooks and notes are re-arranged by dragging them (2026-09-21).** A notebook can be dragged into another or out to the top level, and a note can be dragged from the list into any notebook — the first UI for `moveFolder` and `moveNote`, which have been in the store, tested, and uncalled since the folder work. §7, "Re-arranging is moving", records what dragging was taken to mean and why hand ordering within a level is not it: there is no stored order anywhere and nowhere on a provider to put one, so a drag re-parents rather than re-sorts. The rules are a module with no DOM in it (`store/rearrange.ts`) because every refusal in them is a drop the pointer can really make. Picking up is also a command, so the whole thing works from the keyboard and from a single pointer that never drags (WCAG 2.2 SC 2.5.7) with one implementation rather than two, and the destinations say in words where the thing would land. **Left (issue #125):** a notebook row's accessible name is its label and its note count run together ("Work1"), which is the same name-from-contents trap the tabs hit and is pre-existing — during a move the row says its name outright, so it shows only when nothing is being moved.

- **Notebooks can be managed, and a new one goes to the top level (2026-09-21).** The header's `+` put the new notebook inside whichever was open, and something is open whenever there is anything to open — so after the first notebook there was no way to make a top-level one at all. It is now unconditionally the top level, which is what a `+` in a pane header called "Notebooks" means; inside is the rarer thing and has two ways of its own to be asked for (the menu, and dragging it there afterwards). Beside it, `NotebookMenu` holds what can be done to the **open** notebook: a notebook inside it, Rename, Move, Delete. In the header and not on every row, because the rows are drag sources and a button inside a button is not a thing HTML has — each row would become a wrapper holding two controls, for chrome on every line to serve an action taken rarely. `renameFolder` and `deleteFolder` were in the same state `moveFolder` was: written, tested, and with no caller, so the only way to change a notebook was to edit the folder on the provider. `renameFolder` now hands back the path it moved to, because the caller cannot work it out — the name is sanitised on the way in — and the open notebook is named by path in the URL, which both it and a delete have just changed.

  A rename happens in the row, the same shape the source tabs use, so the name does not move as it becomes editable; Enter takes it, Escape abandons it, blur takes it, and a name that did not change asks for nothing rather than queueing a move on the provider. A delete is **asked** rather than reported — the rule the disconnect confirm exists for (§10) — and the question carries the count of every note beneath it, including those in notebooks inside it, because that is the part the user cannot see from the tree. A note has no confirm because it has the notice that follows it; a notebook takes every note under it, and there is no undo built for that. Cancel holds the focus, as everywhere else the app asks something it cannot take back.

  `role="group"` and plain buttons rather than `role="menu"` and `menuitem`, the same choice the tabs made about `tablist`. The menu's items are props rather than a `children(close)` render prop: handing the close out means handing out a function that touches a ref to be called while the items are still rendering, which React's own lint rightly refuses. **Left:** the menu is named for the notebook it is about ("Options for “Work”"), which is the right thing to say and does collide with any test looking for a row by a loose `/Work/`.

- **A re-parented notebook no longer leaves a copy of itself behind (2026-09-22).** Reported against Dropbox and not Dropbox's: the same duplicate appeared over the fake, the OneDrive stub and Drive. Moving or deleting a notebook queued one `rmdir`, for the outermost directory, and every directory below it was left with nothing naming it — so the pull that runs before the next push adopted them as notebooks, and the `rmdir` was then refused because the device held a row under the path again. §7, "Folder renames/moves", records the rule and why the op is about the pull as much as the removal. The soak now runs over **Dropbox** as well, which it never did — the provider this was reported on was the one provider the whole-app suite did not cover.

- **The editor fills its pane, with a formatting toolbar across the top (2026-09-22).** Two complaints in one place. The editable surface was only as tall as the words in it, so most of the pane looked like the note and was not: a click below the last paragraph landed on nothing. Milkdown puts a `.milkdown` container of its own between the root it is handed and ProseMirror's element; left auto-height, the surface's `min-height: 100%` resolved against no height at all. Every element in that chain now grows, including the one the app did not write, and the fix is pinned by a stylesheet assertion (`tests/editorFill.test.ts`) — jsdom has no layout, so nothing can measure the box, but the shape of the chain is what broke and is what is checked.

  **The toolbar is grouped the way Atlassian's editor is grouped**, because that arrangement is already in most people's hands: text style, then the inline marks, then lists, then indentation, then the link. What is absent is absent for one reason — markdown cannot hold it. There is no text colour, no highlight and no alignment in a `.md` file, and a button that wrote one would put something in the note that the next save loses. The insert menu is not duplicated either: `/` is where a table, a code block, a quote or a divider comes from here, and the sync block has no meaning in an app with no server-side document. Headings reach six in the style menu, two deeper than the slash menu offers, because that is the menu where picking one by level is the point.

  Indentation is list nesting and nothing else — an indented paragraph in markdown is a code block — and the two buttons are grey wherever nesting would not happen, which includes the first item of a list, where `sinkListItem` refuses. The question is put to the command itself rather than guessed at from the selection. A lit mark button means the same thing `toggleMark` means: the mark is somewhere in the selection, so the next press takes it off.

  **One tab stop for the whole bar.** Fourteen buttons between the note's title and its text would otherwise be fourteen presses of Tab in the way of anybody trying to reach the note; the arrows move within it, and which control holds the stop is read from the DOM so that the order on screen and the order the arrows follow cannot drift apart. The panels are `aria-haspopup` buttons with ordinary buttons and a text field inside, not `role="menu"` — the same choice the source tabs and the notebook menu made, for the same reason: claiming a menu owes arrow-key semantics this does not have.

  The bar is only in rich mode, which is the only mode with a document model to act on; raw mode is markdown, where the characters are the formatting. It reads one value — `format.ts`'s reading of the selection — pushed to it by a plugin built with the editor, through a store, so a keystroke that changes which buttons are lit redraws the buttons and not the component the editor is mounted in.

  **The menus opened where nobody could see them.** A toolbar that scrolls sideways is a scroll box, and a scroll box in one axis is a scroll box in both — `overflow-x: auto` makes the used value of `overflow-y` `auto` as well — so every panel hanging from a button belonged to the bar's own scrollable overflow instead of hovering over the note. The bar wrapped instead, at first — two rows on a narrow screen being a smaller price than a menu that does not appear — and now keeps to one line by moving what does not fit into a `More tools` menu at its end (§ "Inside the window", above), which is a menu hanging from the bar like the others and so opens over the note. The stylesheet assertion that pins the editor's height chain still holds the bar to no scroll box.

  **Changing a list's kind is changing the node, not wrapping it** (`editor/lists.ts`). `wrapInBulletListCommand` and its ordered twin are `wrapIn`: right for a paragraph, wrong inside a list, where they either fail or nest a second list inside the item — so switching between bulleted, numbered and task lists did nothing in most of the cases anyone would try it. One command now stands behind all three buttons: out of a list, into one; in a list of another kind, `setNodeMarkup` on the list and on each of its items; in a list of this kind, lift out, which is what a pressed-in button promises. A task list is a bullet list whose items carry a checkbox — in the schema and in the markdown alike — so bullet and task differ only in the items, and that is where the conversion happens.

  **A list item that has just appeared beside task items is a task item, and an unticked one** (`editor/tasks.ts`). Neither half is what ProseMirror does. Splitting an item copies its attributes, so Enter at the end of a *done* task handed back a second task already ticked; and the branch that runs when the item is empty — the second Enter, the one that lifts a nested item out — builds it with `createAndFill()`, taking the schema's defaults, which have no checkbox at all. Two levels deep in a checklist, a double Enter left a plain bullet behind. The rule is an appended transaction, and it is narrow on purpose: only on an item that has just appeared (the list it is in has more children than it had), never on a tick, and never on a body arriving from sync — emptying a finished task by deleting its words must leave the tick alone, and a pull is the file's text rather than an edit.

  **The checkbox can be pressed** — it used to be a `::before` character in the stylesheet, and nothing can press one of those. It is a widget decoration rather than a node view: the document is untouched by it, the tick lives in the item's `checked` attribute where the markdown is written from, and a node view would have to re-implement the schema's rendering for every list item in the note to add a box to a few of them. `Mod+Enter` does the same thing from the keyboard, because a checkbox inside a contenteditable surface is not somewhere the keyboard can go — Tab belongs to the editor and means "nest this item".

  **A checklist with items under items states a relationship**, and two things follow. Ticking a parent ticks everything under it: saying "Pack" is done says each thing packing consists of is done, which is the one direction where what the user meant is not in doubt. And nothing above an unfinished item is finished: unticking one child unticks its parent, and its parent, as far up as that goes. The other two directions are deliberately absent, each for the same reason — it would be a guess rather than something that follows. Unticking a parent leaves its children alone: it says the parent is not done, which says nothing whatever about work already finished, and wiping out a list of completed steps on an inference is not something the user can get back. Ticking the last of a parent's children does *not* tick the parent, because a parent is a task in its own right and may have a step nobody wrote down. The first rule is a constraint the list cannot be allowed to break; the second would be a guess about what the user meant. **Adding to what something consists of is saying there is more to do**, so a new sub-item unticks the item above it as well — the same constraint reached by the other route, whether the sub-item is typed at the end of its siblings or nested under its parent with Tab. That one is measured against the document as it *was*: only a parent this edit left standing over unfinished work is touched, because a note written somewhere else may well arrive with a finished parent over an unfinished child, and tidying that up would be the app rewriting a file it was only asked to show. The strikethrough moved to the item's own paragraphs at the same time: `text-decoration` reaches every descendant and no child can take it back, so striking the whole item struck a nested task that is not done.

- **Code blocks know what language they are in, and show it (2026-09-22).** A fence carried a language in the file and nowhere on screen: rich mode drew a bare `<pre>`, the info string was invisible, and setting one meant switching to raw mode and typing it. Every code block now has a bar of tools under it — language, wrapping, line numbers, copy, delete (`editor/codeBlock.ts`) — and both editors colour what is inside.

  **The grammars are CodeMirror's, and the list is curated.** Thirty languages in `editor/languages.ts`, not the hundred and sixty `@codemirror/language-data` knows, and the reason is the service worker: every language is a lazily imported chunk, every chunk is precached, so the list *is* what the app downloads in order to highlight a note opened offline. Thirty is about 550 KiB across twenty-six chunks with nothing added to the first load; a hundred and sixty would be several megabytes fetched on install for languages nobody here will open. CodeMirror's because CodeMirror is already here for raw mode — one set of grammars serves both editors — and because half the list (Shell, Ruby, TOML, PowerShell) has no Lezer grammar at all and arrives as a CodeMirror 5 stream mode, which `highlightTree` reads the same way. An info string this app does not know is not an error: `mermaid` keeps its word in the file, keeps a place in the picker, and goes uncoloured.

  **One highlighter, two editors** (`editor/highlight.ts`). ProseMirror gets the tokens as inline decorations over the real text and CodeMirror gets the same `tagHighlighter` through `syntaxHighlighting`, so `styles.css` has one palette of eleven colours to paint and neither editor has a colour of its own to disagree with. Classes rather than inline styles, which is also what `style-src` would rather (§9). What the palette deliberately names is short; what it deliberately does not name is any tag `@codemirror/lang-markdown` emits, because the same highlighter runs over raw mode where the document *is* markdown. `tags.meta` was in it until the test written for exactly that caught it colouring the brackets of every link in raw mode.

  **Not a nested CodeMirror inside the block**, which is how Milkdown's own code-block component does it. That would put the note's code outside the document the rest of the app reasons about: find and replace walks the ProseMirror doc, the dirty rule reads ProseMirror transactions, and undo is one history. Colour is worth none of those. (`@milkdown/kit/component/code-block` would also have pulled Vue into a React app, which is its own reason.)

  **Colouring is not editing.** A grammar arrives long after the document that wanted it, so the plugin asks for a redraw with a transaction that changes no text — which is exactly why it cannot mark the note dirty, a user edit being a document change first of all (§7). Tokens are cached against the ProseMirror node itself: a node is immutable, so the same object is the same text in the same language and a typed character makes a new one, which is a cache key with no invalidation to get wrong. A block over 20,000 characters keeps its words and loses its colours, because a pasted file is a code block too and the grammar runs on the keystroke that changes it.

  **The picker writes the info string, and that is an edit**, because it changes the user's file. A fence saying `js` shows as JavaScript without being rewritten to `javascript` — the picker shows the language the word names while the file keeps the word its author wrote. A `<select>`, deliberately: thirty names want type-ahead, arrow keys and a scroll that knows where the screen ends, and the platform's control has all three where a custom combobox would be another menu to make accessible.

  **The tools are under the block being edited, not across the top of every one** (`editor/codeTools.ts`). A code block is mostly read, and a permanent row of controls on each one is a permanent row of controls in the way of each one — so the bar is shown by a class on the block holding the selection, hangs beneath it over whatever follows, and is gone when the cursor leaves. From the selection rather than from focus, because the language menu takes focus out of the editor while it is open and a bar that vanished as it was being used would be a bar nobody could use. Two plugins rather than one: which block is active is recomputed on every cursor move and is a single decoration; the line numbers are a decoration per line of every numbered block and are rebuilt only when the document or the setting changes.

  **Wrapping and line numbers are the reader's, not the note's** (`editor/codeDisplay.ts`, `store/prefs.ts`). There is nowhere in a fence to write "wrap this one" — a fence holds a language and nothing else — so these are not per-block state that would have to live somewhere outside the file and be reconciled with it. They are one answer each for the whole app, kept in the prefs table beside the default editor mode, and read back through a live query so a second tab follows along. The buttons sit on a block because that is where the reader is when they want them, not because the block owns the answer. The numbers are widget decorations taken out of the flow, so a wrapped line's second row still starts under the first row's text and no number can be selected or copied with the code; past two thousand lines a block keeps its text and loses its gutter, because a pasted file is a code block too.

  **Inline code is a chip** — monospace, a tint, a thin edge, its own ink — the way Atlassian's editors draw one, so a `--flag` inside a sentence is visibly not the sentence. Not tokenised, and that is the whole of what "highlighting inline code" can mean here: there is no language on an inline span, and guessing at one colours English prose as if it were code.

  **A note that ends in a code block has a way out of it** (`editor/tail.ts`). Every click in the empty space below landed at the nearest position there was, which is *inside* the block, so typing added a line to the code sample and the only way out was a keyboard shortcut you had to know. There is now a strip under a trailing block — a real button, so the keyboard has the same way out the mouse does — and a click anywhere below the content means the same thing. What it is not is a trailing paragraph kept in the document: Milkdown drops an empty paragraph at the *end* of a document when it serializes (one anywhere else round-trips as `<br />`), so a paragraph parked there would be a difference between the note on screen and the note in the file that nothing would reconcile. The offer is made as the app's change rather than the user's, so clicking it and thinking better of it leaves the note unchanged and undirtied, and the paragraph is withdrawn when the cursor leaves it still empty — only ever the one this plugin offered, never an empty paragraph that came from the user's own file.

  **A block that names no language says "Detect language", and means it** (`editor/detect.ts`, `editor/autoLanguage.ts`). Select something, press the button, and the fence comes with a language already in it; a block started empty works it out as it is typed or pasted into. Three rules keep the second one from being a nuisance, and each is one line of the plugin: only the block holding the cursor, so a keystroke in a paragraph does not go off labelling a fence further down; only on a user transaction, because a body arriving from sync or from raw mode is the app putting text in and a note nobody edited has to come back byte for byte (§7); and only while the block names nothing, which is also what makes it terminate. The guess rides in the same transaction as the edit that prompted it, so one undo takes back both and the dirty rule attributes it to the user — it is their keystroke that put a word in their file.

  Signatures and a threshold, not a library: `highlight.js` does this by running every grammar and counting how badly each does, which means shipping every grammar — the cost `editor/languages.ts` exists to avoid — and it is BSD-3, which this repo does not take. What is here instead is about seventy patterns over twenty-two languages, one pass over at most four kilobytes, no dependency. JSON is not guessed at but checked, since a body that parses is JSON and a body that does not is not.

  **It is built to say nothing.** A language has to score four — one decisive giveaway like a shebang or `<?php`, or two or three ordinary ones — *and* beat the runner-up by two, so Java against C# and C against C++ come back blank from five lines rather than coming back wrong. The bias is the note preview's bias (§7) applied to a different question: a blank picker costs a click, and a confident `python` over somebody's pseudocode is a word in their file they have to notice before they can undo it. The suite that matters is the second one in `tests/detect.test.ts` — prose, a path, a number, a list of names, a sentence with a colon in it — because a notes app is mostly those.

  Two things the tests found and the patterns now say: a command with a `$` prompt in front of it is still a command, and JSX is evidence *for* JavaScript rather than for HTML — without that, a React snippet tied with HTML on closing tags and the margin rule sent both away empty-handed.

  **The floating toolbar stays away from a code block.** Selecting a few words of a code sample used to bring up the bold/italic/code bar over them, and every button on it was a no-op: the schema says a code block holds no marks. The bar across the top greys those buttons in the same situation, which is the option a permanent toolbar has; a bar that only exists when there is a selection has the better one, which is not to appear. Milkdown's `TooltipProvider` takes a `shouldShow` that *replaces* its own predicate rather than extending it, so `InlineToolbar.tsx` restates the four cases it already refused for — no focus, an empty selection, an empty text block, a read-only note — and adds this one.

  **The toolbar has one insert button now**, which reverses what its own comment said when it was written a day ago: insert belonged to the slash menu and was deliberately not duplicated. The code block is the exception because it is the construct people go looking for in a toolbar, and because the block has more to it than its own existence — a language, and the colours that follow — so somewhere to press is somewhere to start. It is a toggle: lit inside a code block, and pressing it again gives the block back as plain text. The mark buttons are grey in there, since the schema says a code block holds no marks and a lit button that does nothing is worse than one that is grey.

- **A `<br />` inside a sentence no longer sends a note to raw mode (2026-09-23).** Reported: adding one showed the banner saying the rich editor could not show the note. The check was right — the editor deleted it — and the cause was Milkdown's reader for the empty paragraph taking every `<br>` in the note (§7, "Empty paragraphs become `<br />`"). Now only the editor's own shape is an empty paragraph, and every other break comes back as it was written. A second, smaller cause sat behind the first: the serializer writes a line ending before inline html as a space, which the fidelity comparison counted as a difference, so a `<br />` on its own line inside a paragraph still failed; the comparison now reads it as the serializer writes it (§7, the fidelity bullet).

- **The raw-mode banner says what the rich editor cannot show, and the rich editor can be asked again (2026-09-23).** The banner said only that the note used "markdown the rich editor has no way to show", and the note then stayed in raw mode for as long as it was open, whatever the user did about it. It now names the first thing the editor would drop and its line (`the HTML <br> on line 3`, `a link reference definition on line 5`), and once the note has changed the rich tab is offered again and checks again (§7, the fidelity bullet).

- **A first import says how it is going, holds the app, and can be cancelled (2026-09-23).** Connecting on a device with many notes, or to an account with many, showed "Syncing…" for minutes and nothing else, and nothing could stop it. The import now counts what it finds, downloads and uploads — over the app for the first source, which is held until it is through, and in the storage panel for a later one — and Cancel puts the device back as it was. §6, "A source's first import"; §7, the sync loop.

### Disconnecting without an invisible pile (2026-09-19)
**A source that is let go must not leave notes where nobody can see them, and must not take unsent work with it unasked.** It used to do the first (the rows went under `LOCAL_CONNECTION_ID`, shown only when nothing else is connected); since the second change below it does neither (§6, "Letting a source go"). The owner's rule is that a disconnect removes the source's notes from the device — the remote has them — and that what the remote does *not* have is the user's decision: move it to another connected source, download it, discard it by name, or cancel. Where there is nobody to ask (a credential revoked from another device), the source is detached in place and stays on screen until somebody is. There is **no migration** for a pile an earlier disconnect left: nothing has been released, so the code that serves such a pile is deleted rather than carried.
- **Plumbing, with nothing the user can see.** `store/unsynced.ts` says what a source holds that its remote has not been sent — notes (dirty, never pushed, or with a `write` queued), renames (clean and pushed, a `move` queued), deletes (a tombstone with a `remoteId`; one without owes nothing), notebooks (a `mkdir` queued, or no `remoteId` *and* no fully sent note anywhere beneath: only `createFolder` and `moveFolder` queue a `mkdir`, and a notebook that came into being around a note is made by the engine's `ensureRemoteFolder` on push, which reports no id, so its row has none until a later pull — a sent note inside it is the proof the directory exists), queued `rmdir`s, and whether the queue is `blocked` — for one connection by name, since an id and an op's `noteId` mean nothing outside their source. A connection still `resumeUnverified` counts **every** live note and notebook and says `unverified`: its rows look sent, but `verifyResume` has not yet found the files, and a discard that believed the rows would delete the only copy. `blocked` is the scheduler's rule and not a second one: `outOfAttempts` and `MAX_OP_ATTEMPTS` moved to `store/queue.ts` and the scheduler reads them from there. It is never true of an `rmdir`, because the engine never stops at one: out of attempts, it is completed as done and stepped over (`drainOps`). `store/heldEdits.ts` takes over the `beforeClosing` registry from `store/staleTab.ts` and adds `settleEditors()`, because text an editor still holds is in no row and a count taken from the store alone would leave out the last sentence typed; `Autosave.settle` answers with the notes it still holds text for that the store would not take, named by `noteRef` — a count, until the change below had to keep exactly those rows and a number could not say which they were — and a flush that rejects is counted instead, since one that threw can say nothing about which note it was holding. **Still per tab, and still across sources:** a settle reaches the editors of this tab alone, and it settles every source they hold text for rather than the one being let go, so "this source has unsaved text" is answered from the refs where there are refs and from the rejection count otherwise, which cannot tell one source from another. `syncState.displayName` is written on every reconcile and on bind, and kept by every writer of the row, so a source the server will no longer answer for can still be named. `store/exportNotes.ts` is a store-only ZIP written by hand (CRC-32, UTF-8 names, no dependency, and no CSP change: a blob behind `<a download>` is neither a script nor a fetch) of each note as the file a push would send, at its path. The name written is the name compared: normalized, relative, never `..`, a backslash made `_` (a separator to some Windows extractors, so otherwise a way out of the folder it is unpacked into), and `untitled.md` where nothing is left; colliding names are numbered, a file that would sit where a folder has to be among them; and it throws rather than write a field that would wrap or mean ZIP64 (65,535 entries, 4 GiB, a name over 65,535 bytes). Linear in the number of notes, because it runs on the main thread at the moment the user most needs it to finish. It is deliberately *not* the export/import of §14, which stays unplanned: it exists for the one position sync cannot help with — text that is only on this device, in a source that cannot be reached — where "discard or cancel" would otherwise mean the user can never leave without losing it. Its first caller is the detached panel's Download, in the change below
- **Every disconnect is a detach in place, and the code that served the pile is gone.** `syncState.detached` (`at`, `disconnected` | `revoked` | `interrupted`; unindexed, so no schema version and — nothing being released — no migration), `detachConnection` on every unbind path, `releaseConnection` for the discard, the `activeConnectionId` fallback that prefers a live source, and the scheduler, sync-store, token-source and reconcile guards, as §6 now describes. The panel gains Reconnect, Download and the two-step Discard; the disconnect confirm says the notes are removed from the device and how many changes will stay behind; the undo notice says when a note came back into a disconnected source. `unbindConnection`, `NOTES_ACCOUNT_KEY`, `MIXED_ACCOUNTS`, `labelFor`, `heldLocally`, `needsAsking`, `adoptAccount`, the `other-account` state and its panel were deleted here rather than in the last change: with no disconnect filling the pile they were unreachable, and dead code that decides where notes go is worse than none. `LOCAL_CONNECTION_ID` survives as "nothing has ever been connected", and `bindConnection` still copies its rows into the first source bound. Two things found on the way: a save held for a row the detach removed could be matched *by id* to another account's note (`whereShown` now looks by id for the device's own notes only), and "stop syncing on this device" used to leave the credential behind (the connection transaction now covers `credentials`). **Review of the first cut (2026-09-19) closed what it had left open, and two ways text was dropped:** a detach marked every removed row as deleted-here, so text an editor still held for one — typed while the server was being asked, or a save that had been failing — was let go on arrival; now nothing a detach removes is marked, such a save makes the note again under its source (`ensureDetached`, with the account this tab remembers for it), the editors are settled immediately before every detach, and `settleEditors` answers with the failing notes' refs so that their rows are kept whatever they say. And Discard's `seen` named notes by ref alone, so a note written into after the list was shown went with the list; it now carries each note's `updatedAt`, the notebooks and `rmdir`s by path, and a mismatch is unseen. Also: `releaseConnection` refuses a source reconnected meanwhile; a resume into a connection that already holds the file yields to the pulled row (a kept edit becomes a conflict copy); marks in `deletedHere` are per binding (`boundAt`) so a reconnect's pull cannot be mistaken for the delete before it; a re-made source never takes the screen, and the device's own pile is listed and showable when it holds anything; both confirms close on Escape, the discard panel's focus is guarded and handed on when its source goes, and the tombstone warning is said plainly. **Left:** the source list names live sources by account id, not by the server's name — the name is written onto a row only when that source is reconciled, which is only while it is in front, so a list naming by it would rename a source the first time it was shown
- **The dialog before a disconnect, and moving unsent notes to another source.** The order is the rule: the editors settle, one last push runs where it could work (ten seconds, then the question anyway), what is unsent is read, and the user is *asked* — and nothing is said to the server until they answer, which a test pins by asserting the disconnect mock is untouched while the question is up. The four cases are the owner's: nothing unsent is the plain confirm; unsent with somewhere to put it offers Move, Download, Discard and Cancel; unsent with nowhere offers the last three; and offline or blocked adds why, with "cancel and try again later to keep them". Cancel has the focus in every step — the question, the discard step and the second step of a move alike, since the button that was pressed goes with the step it belonged to and focus left on the page is a user whose Escape reaches nothing — Escape closes, a failing save in this source disables Move and Discard and points at the note's own banner, and a count per category sits above five titles with the rest in a `<details>`. Every number the user sees comes from one rule (`countedFolders`): a notebook is counted only where no unsent note is inside it, so the headline, the breakdown and both steps of a move cannot disagree, and the empty notebook an unsent rename leaves behind is named rather than smuggled across. `moveUnsyncedTo` is the only operation in the app that carries writing from one storage account into another, so it names the account (a radio list where there is more than one) and says in a second step exactly what will be in each afterwards — including that a note pushed once ends up in both, and that unsent deletes and renames are not carried because each is about a file only the old account has. What it takes and what it leaves is set out in §6. It shares the `seen` rule with the discard: read again inside the transaction, and anything written since the list was made is kept rather than moved or let go, with the source detached around it. The same Move is on the detached panel. It is offered only where it means something — another live source, something movable on the list, and a source whose files have been checked against its remote — and the one confirm in the app that writes into another storage account names that account by the name the server gave it, falling back to the provider's id, rather than by the id the switcher uses. A source that is `resumeUnverified` says so in place of the headline, because “n changes have not reached X” is simply false of a list that is the whole library, and points at cancelling and connecting again as the answer. **Not done, and why:** the design asked for the editor to be made `inert` from the first settle until the release finishes; the panel does not own the editor, and what that was for is already covered — a keystroke landing while the question is up is kept by `seen` and the source stays around it, which is stronger than a guard one tab can hold
- **The sweep, and this plan.** Nothing here is anything the user can see. The deletion planned for this change — `MIXED_ACCOUNTS`, `NOTES_ACCOUNT_KEY`, `other-account` and the rest — landed with the detach change above, which is what made them dead, and a sweep for whatever the three changes left after them (a prefs key still read but no longer written, CSS for a panel that no longer exists, an export with no caller, a type with no user, a test helper nothing calls) found none of theirs. That is the tooling working rather than luck: `noUnusedLocals` and `noUnusedParameters` fail the build on a declaration the moment its last use goes, so the only dead code a change like this can leave behind is an *export*, and the exports that have none — `heldCredentials`, `useDirtyCount`, and the Phase 1 store functions the tests are the only callers of — all predate this work and are not its to delete. What was left was the prose, and §6, §7 and Phase 2 above now describe the world these four changes built rather than the one they replaced: in particular `LOCAL_CONNECTION_ID` is described again as what it has always been and nothing more — never connected, or nothing connected — since `bindConnection` copying its rows into the first source bound is the only thing that fills or empties it

**What the four together guarantee, so it need not be assembled from four entries.** The remote is the source of truth, so letting a source go takes off the device exactly what the remote has and nothing else; connecting the account again brings it back. What the remote was never sent is never discarded and never moved into another account unless the user says so: Disconnect settles the editors, sends one last push where that could work, reads what is unsent and *asks* — move it to another connected source, download it, discard it by name, or cancel, and on the only source discard, download or cancel — with nothing said to our own server until the answer comes, so a cancel leaves the device as it was and the connection standing. The last push is the exception, and it is not one really: it finishes what the user had already asked for, and a cancel after it leaves their notes further along than before, never behind. Where there is nobody to ask, because the server has stopped answering for the credential, the source stays on the device marked `detached`, holding what it was never sent, shown and editable and saying so in the list, until there is somebody. And no disconnect fills the device's own pile, so what the user has been told is on their device is somewhere they can see it. **Not done, and why**, each said with the change it belongs to: the editor is not made `inert` while the question is up, since `seen` keeps whatever is typed meanwhile and the panel does not own the editor; `settleEditors` reaches this tab's editors and every source they hold text for, not the one being let go; and §7's directory removal still names the folder by the id the queue recorded, and gives up where it has none.

Dependency rule: `core` imports nothing from `apps/*`. `web` and `api` may import `core`. The WebDAV adapter in `core` takes a `fetch`-like function so it can point at the proxy in the browser and at the server directly in tests.

A `.ts` and a `.tsx` may not share a stem in the same directory. TypeScript resolves the `.ts` and the `.tsx` is silently left out of the program: `tsc` is happy, the tests still run under Vite, and only ESLint complains — with "was not found by the project service", which names the symptom and not the cause. It happened to `tests/commands.test.tsx` beside the existing `tests/commands.test.ts`, and the shadowed file had a real lint error in it that nothing had been reporting. Rename one of them.

Source files are text. A control byte other than tab, newline or carriage return — a NUL written as itself rather than as `\u0000`, say — makes git call the file binary, and from then on it is absent from every diff, every blame and every three-way merge, while prettier, ESLint and `tsc` all pass it without a word. It has happened twice here, once to the largest new file in a PR, which went through three rounds of review without a reviewer ever seeing it. Write the escape. `apps/web/tests/noControlBytes.test.ts` walks `apps`, `packages`, `docs`, `.github` and the root files, and fails with the path, the byte and what to do about it. It lives under `web` because it needs `node:fs`, which `core` may not have even in a test. Two details are load-bearing, both learned the hard way in review: it walks rather than asking `git ls-files`, because git run inside a tree that some *outer* repository ignores reports no files at all and a guard with nothing to iterate passes silently — so it also carries a canary, and a walk that does not find the test itself fails. Git is asked only to *narrow* the walk, and only when its answer names that same file, which is what keeps a `.DS_Store` or a scratch file nobody committed out of the results without ever letting git's silence stand for "clean".

## 12. Resolved decisions (formerly open questions)

1. **App folder name:** `skysa-notes`, exported as `APP_FOLDER_NAME` from `packages/core/src/config.ts`. It governs the folder Google Drive and WebDAV create. OneDrive and Dropbox derive their app-folder name from the provider registration, so those registrations must be named to match; Dropbox's name is immutable after creation, so if the constant changes before launch, re-create the Dropbox app.
2. **Remote folder renames apply even when contained notes are dirty.** Metadata-only; see §7.
3. **Several connected sources on one device since Phase 7**, each its own silo, one shown at a time. There is no user to hold them: nothing on the server knows that two connections belong to one person (§6).
4. **Hosting: Cloudflare Workers** for API + static SPA, D1 for the database. See §6.
5. **Cold start is a full scan.** No remote index file. Revisit if cold start exceeds ~10 s at ~2k notes.
6. **Every note the app creates lives in a notebook; the root is not one.** The sidebar lists notebooks, and opens the first one when the URL names none. The root is the container notebooks live in, not a place to put notes, so the app will not create a note there — and it gets a row only in the case below.

   **Resolved (Phase 2).** A `.md` file sitting loose at the root of the remote app folder — put there by hand, or by another tool — imports to a note in no notebook, which the sidebar had no way to show. We do **not** move those files: relocating them would contradict "the user sees the same structure from any other tool" (§1) and quietly rewrite their remote layout. Instead the sidebar grows a **"Loose notes" row that appears only when the root actually contains notes**, below the notebooks, showing the count. It is not the "All notes" row removed in Phase 1: that one always showed and misdescribed what it held; this one names exactly what it holds and disappears when empty. Opening it lists those notes and leaves "New note" disabled, because the app still does not create notes at the root.

   Three consequences worth knowing about:
   - `ROOT` is `''`, and an empty search param is indistinguishable from an absent one, so the URL spells the root `/`. The translation lives in `apps/web/src/routes/search.ts` and nothing else in the app knows about the sentinel.
   - A notebook created while the loose notes are open goes beside them, at the root — the root is not a notebook and cannot be a parent.
   - The tree and the count of loose notes come from two independent live queries. Neither `undefined` may be read as "there are none", or the app opens one folder and jumps to another a frame later — with no notebooks at all it would briefly tell a user whose whole library is loose notes that they have nothing. `selectedFolderPath` takes the count, not a boolean, for exactly this reason.

## 13. Distribution and licensing

### Repo
One public repo, `skysa-notes`, containing everything in §11. It is self-hostable and complete: placeholders only in `wrangler.toml`, `.dev.vars.example` listing every key, no operator credentials or deployment-specific configuration in the tree. Defaults are `AlwaysAllowedEntitlementProvider`, `AUTH_MODE=storage-first`, and `ENABLED_PROVIDERS` defaulting to what an operator can run without registering several apps (`dropbox`). Anyone who needs different behavior composes it through `createApp` (§6) rather than forking.

### License: AGPL-3.0 + CLA (decided; confirm final CLA text with a lawyer)
- **AGPL-3.0** for all code — version 3 **only** (SPDX `AGPL-3.0-only`). `NOTICE` carries the grant and says version 3, the four `package.json` files say `AGPL-3.0-only`, and both CLAs promise version 3; they said "or later" until 2026-09-18, which this document never did, and a licence field that disagrees with the notice is two answers to one question. A later version can still be adopted deliberately — the CLA's relicensing grant allows it — which is the point of not granting it in advance. Standard posture for self-hostable web apps (Plausible, Cal.com, Ghost).

The grant includes the right to sublicense and relicense, which keeps future licensing options open. Individual CLA required from day one; an adapted Apache CCLA (entity CLA) is prepared but only requested the first time someone contributes on behalf of an employer. ### Self-hosting model
A self-hoster needs: a Cloudflare account (Workers Free is sufficient indefinitely for personal use; the daily limits are unreachable by one person), their own Google/Entra/Dropbox app registrations (named `skysa-notes` so folder names match), and ~15 minutes with `docs/self-hosting.md`. Their Google app is in "Testing" (at most 100 test users, refresh tokens expiring after 7 days) until they publish it. With only non-sensitive scopes, publishing needs no verification; brand verification is optional and only shows their name and logo (`docs/google-oauth.md`). Every storage provider needs its own app registration; WebDAV, which would not, is deferred (§5.4).

Operators running an instance for many users should know two things, both to be documented in `docs/self-hosting.md`:
- Workers Free hard-stops at 100k requests/day until 00:00 UTC, which would break token refresh for every user of the instance at once. Workers Paid bills per request instead, lifts the CPU limit (set `limits.cpu_ms = 50` in `wrangler.toml` to cap runaway cost), extends logs to 7 days, and enables Logpush. Capacity is not the concern: Free covers roughly 5k daily actives at ~20 Worker requests/user/day, and static assets are free and unlimited on both plans. Pricing verified 2026-09.
- Back up D1 with `wrangler d1 export` on a cron trigger. The database holds encrypted refresh tokens and connection metadata, never note content.

## 14. Not planned (possible future add-ons)

None of these are in any phase. Listed so the reasoning isn't lost if they come up.

- **WebDAV.** Deferred indefinitely (2026-09-17). The design is in §5.4, and what building it would take is recorded in issue #122, not scheduled.
- **Share target, and import from a zip.** Moved out of Phase 7 (2026-09-18). The share target is a manifest entry and a route that turns a shared URL or selection into a note; import is reading a zip of the markdown tree back in. Neither is hard, and neither is what the app is for: the notes are already plain markdown in a folder the user owns, which the provider's own client will sync and share. Import in particular needs nothing of its own — the export below is the tree a provider folder holds, so connecting storage and dropping its files into the app folder is the import. *Export was on this line and came off it on 2026-09-24* (issue #133, §7 "Getting a library out"). The reason for leaving it here was that export mattered more when the store was the only copy of anything, and on a device with nothing connected the store still is.
- **Image paste, and attachments generally.** Moved out of Phase 7 (2026-09-18). Pasting an image has to put the bytes somewhere — a sibling file the markdown links to — and that is an attachment story: a second kind of object to name, sync, conflict, deduplicate and delete alongside notes, on three providers. Nothing in the sync engine handles a non-markdown file today, and the checklist item that named it was blocked on a phase that does not exist.
- **Other encodings.** A file that is not UTF-8 is left alone rather than converted (§7). Reading Latin-1 or UTF-16 means guessing, and writing it back means either changing the file's encoding under the tool that made it or keeping an encoding per note. The fix is a "save as UTF-8" away, in the tool that wrote the file, and the storage panel says which files need it.
- **Sign-in separate from storage.** Was Phase 9; dropped 2026-09-18 (§6). Identity and data are coupled deliberately, so this is not "later" — it is decided against. What it would have taken, kept so the cost is not re-discovered: an `identities` table and `IdentityProvider` adapters for Google and Microsoft; merge-by-verified-email, whose hard part is that the *existing* user's email must be verified too, since a storage-first user is created with whatever the storage provider called the account and a Microsoft `email` claim is set by a tenant's admin — matching on the incoming provider alone lets a crafted tenant sign in as someone else; explicit in-session linking (`?link=1`) for Hide-My-Email relays and differing addresses; a second Google Cloud project, because Google revokes every grant to a project at once and disconnecting storage would otherwise sign the user out of their sign-in; and a reconciliation between two authorization paths, since a user would own connections that already have credentials of their own. The three add-ons that hung off it went with it: **Apple sign-in** (a `.p8` JWT client secret rotated every six months, `form_post` callback, name delivered only on first authorization, relay addresses), **Facebook sign-in** (email not guaranteed, so an email-confirmation step, plus Meta App Review and possible Business Verification), and **magic link** (an `email` identity type, transactional email with SPF/DKIM/DMARC, and a one-time-code fallback for the PWA's link-opens-in-another-browser problem).
